# game-sensei

> **泛型游戏辅助框架**：大模型当「老师」教学，量化小模型当「学生」自学习并实时操作。

一个**游戏无关**的辅助框架——靠纯视觉感知 + 模拟输入（**不读内存、不接封包**），由本地量化小模型实时操作，由大模型周期性评估教学，形成「学生操作 → 老师查岗 → 学生再学」的自学习飞轮。

---

## 1. 定位与愿景

- **泛型**：不绑定具体游戏，靠截图 + 键鼠模拟工作，换游戏只需换「目标定义 + 初始示范」。
- **自学习**：学生（量化模型）实时玩，老师（大模型）定期看回放、诊断错误、产出示范，回灌微调学生。
- **低延迟**：实时操作必须由本地量化小模型承担；大模型只做慢节奏的异步教学，不参与实时回路。

---

## 2. 自学习闭环（核心）

```
游戏画面截屏
   → 感知编码（CNN / VLM 视觉塔）
   → 量化学生 Actor（策略网络，int8 本地部署，实时低延迟）
   → 动作输出（键鼠 / 触控）
   → 游戏环境反馈（得分 / 胜负 / 状态）
   → 轨迹缓冲（状态 · 动作 · 结果）
        ↘（周期性）
   大模型教师（VLM / LLM）：检查回放 · 评估错误 · 产出示范 · 蒸馏微调学生
        ↘（示范数据 → 微调重装 onnx）
   学生变强 → 回到开头
```

- **实时执行回路**：`capture → agent → input`，必须几十 ms 级，学生必须是本地量化小模型。
- **异步教学回路**：`teacher` 每 N 局或 M 分钟触发一次，看一段回放 + 轨迹 JSON，诊断错误并产出正确示范动作序列。
- **蒸馏回灌**：老师筛出的「优质轨迹 + 示范」用于微调学生（模仿学习 BC + DAgger），导出新 onnx，Go 运行时热重载。

---

## 3. 角色定义

| 角色 | 实现 | 职责 |
|---|---|---|
| **学生 Actor** | 量化策略网络（onnxruntime-go, int8） | 实时感知 → 输出动作，低延迟、稳定、可复现 |
| **老师 Teacher** | 大模型 VLM（本地 Ollama / OpenAI 兼容） | 周期性评估回放、诊断错误、产出示范、定义评分标准 |
| **轨迹 Trajectory** | `(state, action, result)` 序列 | 自学习的数据飞轮燃料，存于 `memory` |
| **奖励 Reward** | 由老师按游戏类型生成的「评分标准」 | 泛型游戏无统一 reward，需可计算指标或老师 critic 打分 |

## 4. 技术栈

### 运行时（Go 单二进制）

| 模块 | Go 库 | 说明 |
|---|---|---|
| 截屏 `capture` | `github.com/kbinani/screenshot` | 跨平台抓屏；Windows 抓指定窗口可用 `github.com/AllenDang/w32` |
| 键鼠 `input` | `github.com/go-vgo/robotgo` | 跨平台模拟键鼠/触控（需 CGO） |
| 学生推理 `agent` | `github.com/yalue/onnxruntime_go` | 加载量化 int8 ONNX，仅需 onnxruntime 动态库 |
| 老师 `teacher` | 标准 `net/http` | 调本地 Ollama `/api/chat` 或 OpenAI 兼容接口 |
| 轨迹 `memory` | `chan` / ring buffer | goroutine 间解耦共享 |
| 配置 `config` | YAML/JSON | 目标 · 评分标准（按游戏可配） |

### 离线训练（Python 工具，`trainer/`）

- PyTorch 训学生网络 → `torch.onnx.export` → `onnxruntime.quantization` 量化为 int8。
- 这是一次性工具，**不进运行时**；Go 只加载产物 onnx 做前向推理。
- 关键边界：**Go 不能训练神经网络**，训练侧保留 Python 工具链。

### 感知端选择（Go 生态现实）

- **方案 A（推荐，实时）**：学生网络端到端——截图降采样直接进小 CNN → 输出动作，整体为 onnx，Go 仅推理，不依赖 CLIP 视觉塔。
- **方案 B（老师辅助）**：用大模型 VLM 做感知（老师既感知又教学），学生只学老师动作策略；简单但延迟高、成本高，仅适合慢节奏。
- 落地建议：**A 做实时、B 做老师辅助判断**。

## 6. 阶段路线图

- **Phase 0**：单游戏打通「截屏 → 学生 stub 决策 → 键鼠」实时回路（先用规则驱动验证延迟与输入链路）。见 `cmd/helper/main.go` 占位。
- **Phase 1**：接 `teacher`，先做**离线评估 + 文字反馈**，人工看反馈改进提示词，验证老师判断力。
  ✅ **第一版已落地**：`internal/teacher` 提供 Ollama `/api/chat` 客户端（多图送审、content/thinking 双字段兜底）、
  轨迹评估器（结构化反馈 + 评分解析 + Markdown 报告）与提示词构造；`cmd/helper -teacher` 开启异步教学回路，
  抽样抓帧不阻塞实时回路。已用本机 `qwen3.5:2b` 端到端验证通过（详见 §9.2）。
- **Phase 2**：老师产出**示范轨迹**，自动用示范微调学生（蒸馏 / bootstrapping），打通 `trainer/`。
- **Phase 2.5 ✅ 已落地**：**教学视频学习**——新增 `cmd/video` + `internal/video`，把人类高手的
  录像抽帧、去重、切成动作段后交给老师逐段判读，产出可读的策略清单，补上冷启动阶段
  「老师只能靠自己瞎猜」的短板；详见 §9.6。
- **Phase 3**：自动化飞轮——老师定期评估 + 选优轨迹 + 触发微调 + 回灌，形成自学习；**泛型化**（换游戏只需换目标定义 + 初始示范）。
- **Phase 0.5 ✅ 已落地**：**目标环境泛化**——新增安卓 ADB 后端（`internal/android` + `cmd/helper/backend.go`），
  使同一套实时/教学回路既能操作 PC 桌面窗口，也能操作真机手游（截图 → 触控/滑动/摇杆/按键）。
  动作空间升级为归一化坐标，跨分辨率复用；详见 §9.3。

## 7. 关键设计决策与待定项（设计阶段重点）

| 待设计项 | 说明 | 建议 |
|---|---|---|
| **状态表征** | 截帧如何编码进网络（降采样尺寸、帧序列长度、是否含 OCR 文本） | 端到端小 CNN，先定输入分辨率与帧栈 |
| **动作空间** | 离散键位 / 连续移动 / 组合技如何建模 | 先定最小动作集，再扩展 |
| **奖励/评分标准统一** | 泛型游戏无统一 reward | 老师按游戏类型生成可计算指标；或纯老师 critic 打分 |
| **冷启动** | 学生初始啥也不会 | 老师先示范 bootstrapping，学生纯模仿再探索 |
| **灾难性遗忘** | 小模型易过拟合某场景 | 老师定期查岗纠偏 + 保留历史优质轨迹回放训练 |
| **模型热重载** | 微调后不重启生效 | `agent` 检测 onnx 文件 mtime 变化，原子替换 |

## 8. 合规声明

- 本框架仅使用**视觉感知 + 模拟输入**，不读取游戏内存、不拦截/篡改网络封包。
- 但纯模拟输入仍可能违反多数联网游戏的**服务条款（ToS）**，存在封号风险。
- 建议仅用于**单机游戏、自研游戏、或个人研究**场景；请勿用于联网竞技或违反游戏方规定的用途。
- 使用者须自行评估并承担合规风险。

### 9.1 教师模型环境（项目自带 Ollama）

teacher 用的 VLM 默认走**项目内自带的 Ollama 实例**（独立端口 11435、模型库在 `.ollama/models`），
与系统安装的 Ollama 隔离，不依赖任何远程设备：

```bash
# 1. 启动项目自带实例（模型库落在 .ollama/models，已 gitignore）
bash tools/serve_ollama.sh

# 2. 另一个终端：拉模型（也可从别处拷贝 .ollama/models 整目录）
curl -X POST http://127.0.0.1:11435/api/pull -d '{"model":"qwen3.5:2b"}'

# 3. 评测：抓一张截图，跑延迟/速度/质量对比
python tools/screenshot.py -o shot.png
python tools/vlm_bench.py --image shot.png --models qwen3.5:2b --rounds 2
```

**远程老师（本机不跑 Ollama 时）：** 设置环境变量 `GAME_SENSEI_TEACHER_URL` 指向局域网内
另一台跑 Ollama 的机器，`helper`、`video` 与 `tools/` 下全部工具会自动跟随，无需逐个传参：

```bash
# PowerShell（当前会话有效）
$env:GAME_SENSEI_TEACHER_URL = "http://100.66.1.2:11434"

# bash
export GAME_SENSEI_TEACHER_URL=http://100.66.1.2:11434
```

优先级：**命令行显式传参（`-teacher-url` / `--url` / `--host`）> 环境变量 `GAME_SENSEI_TEACHER_URL` > 内置默认 `http://127.0.0.1:11435`**。

**实测选型（RTX 3060 12GB，1920×1080 截图，同一提示词，均为本机 11435 实例）：**

| 模型 | 体积 | 生成速度 | 单次评估 | 判定 |
|---|---|---|---|---|
| `qwen3.5:9b` Q4_K_M | 6.59GB | 40 tok/s | 22.5s（含 913tok 思考） | ✅✅ teacher 首选：窗口标题 / 中央内容 / 底部输入框+输入法全认对 |
| `qwen3.5:2b` Q8_0 | 2.74GB | 105 tok/s | 10.1s（含 975tok 思考） | ✅ 快速档：中央内容正确，窗口标题略偏 |
| `qwen3-vl:2b` Q4_K_M | 1.89GB | 147 tok/s | 14s+（2000tok）仍无正文 | ❌ 思考链死循环，不采用 |

同一个 `qwen3.5:9b` 在远程机器上实测 106 tok/s、本机 3060 只有 40 tok/s——
**模型速度强依赖机器，选型与延迟预估都必须以目标机器实测为准**。

**已知坑（teacher 客户端必须处理）：**

- qwen3 系列把推理写在 `message.thinking`、正文写在 `message.content`，**两个字段都要兜底解析**；
  400 tok 预算常被思考吃光，`num_predict` 需给到 **≥1500**，或提示词里明确要求直接给答案。
- **`think` 开关必须放在请求顶层，不能放进 `options`**（见 §9.4）。早前记录的
  「`think=false` 在本机 Ollama 0.34.0 上无效」是**错误结论**——原因是当时写成了
  `options.think`，Ollama 会直接忽略它。放对位置后效果立竿见影：
  同图同提示词从 **65s / 正文为空** 变成 **1.3s / 正文正常**。
- 同一模型在不同机器上速度差异极大（`qwen3-vl:2b` 远程 16~27 tok/s vs 本机 147 tok/s），
  **teacher 选型必须以目标机器实测为准**。

### 9.2 老师（异步教学回路）

实时回路只管跑，老师在**另一个协程**里按抽样节奏干活：

```bash
# 边跑边让老师查岗（dry-run，不发送真实键鼠）
go run ./cmd/helper -frames 3000 -teacher \
  -teacher-model qwen3.5:9b \
  -eval-every 300 -eval-frames 6 -eval-width 640 \
  -goal "把方块推到右侧终点" \
  -eval-out .workbuddy/eval-reports
```

| 参数 | 说明 |
|---|---|
| `-teacher` | 启用异步教学回路（默认关，避免无人值守时白烧算力） |
| `-teacher-url` / `-teacher-model` | 老师地址与模型。地址默认取环境变量 `GAME_SENSEI_TEACHER_URL`（见 §9.1），未设置则为本机 `11435`；模型默认 `qwen3.5:9b` |
| `-eval-every` | 每 N 帧抽一帧；30FPS 下 `300` ≈ 每 10 秒一帧 |
| `-eval-frames` | 攒够多少帧送审一次（`6` ≈ 覆盖 1 分钟） |
| `-eval-width` | 送审帧降采样宽度（`640`，比学生输入的 160 宽，让老师看清界面） |
| `-goal` | 游戏目标，写进提示词供老师判断动作合理性 |
| `-eval-out` | 报告落盘目录（Markdown，含评分与性能数据）；空则只打印控制台 |

**设计要点：**

- 抽帧与推理全在**教学协程**内完成（`capture.Grab` 无共享状态，可跨协程调用），
  实时回路每帧只是往缓冲通道做一次**非阻塞投递**，教学回路忙时直接丢帧——
  实测 40 帧运行中实时回路平均延迟 31.0ms，与不启用老师时一致。
- 老师不可达时**优雅降级**：启动自检失败只打印警告，实时回路照跑。
- 送审的是**学生自己的观测**（降采样灰度图），不是原始彩屏——评估的是
  「学生在它看到的世界里做得对不对」。
- 反馈要求结构化四行（局面 / 评价 / 建议 / 评分），评分会被解析出来便于 Phase 2 自动选优。

**端到端验证（本机 `qwen3.5:2b`，workbuddy 桌面为「游戏画面」）：** 老师 12.7s 返回，
正确指出「画面是聊天界面而非游戏主画面」，给出关闭窗口→进入游戏→再推方块的建议，评分 0；
报告落盘正常。`internal/teacher` 另有 mock 单测覆盖双字段兜底、图片编码、超时与错误路径。

### 9.3 双后端：PC 桌面 / 安卓 ADB

`backend` 接口统一了两类目标环境，实时回路与教学回路都只依赖接口：

```go
type backend interface {
    Grab(width int) (image.Image, error)   // 当前画面（灰度降采样）
    Size() (int, int)                      // 当前画面尺寸
    Describe() string                      // 人类可读的目标描述（进提示词 / 报告）
    Live() bool                            // 目标是否仍可操作
    Apply(act agent.Action) error          // 执行动作
}
```

| 后端 | 实现 | 画面来源 | 动作执行 |
|---|---|---|---|
| `pc`（默认） | `pcBackend` | `internal/capture` GDI BitBlt | `internal/input` user32!SendInput |
| `android` | `adbBackend` | `internal/android` `exec-out screencap -p` | `internal/android` `input tap/swipe/keyevent` |

**安卓后端能力（`internal/android`）：**

| 方法 | 说明 |
|---|---|
| `FindADB()` / `Devices()` | 定位 `adb.exe`（查 `ANDROID_HOME` / `ANDROID_SDK_ROOT` / PATH / 常见安装路径）；列出设备 |
| `Open(adbPath, serial)` | 连接指定设备；多设备且未指定 serial 时报错，不做隐式选择 |
| `Screenshot()` / `SavePNG()` | `exec-out screencap -p` 取 PNG 并解码，同时缓存画面尺寸 |
| `ScreenSize()` | **优先用缓存截图尺寸**（反映当前坐标系，横屏下为 2608×1200 而非物理 1200×2608）；退化时用 `wm size` + `rotationDegrees` 交换宽高 |
| `Tap` / `TapNorm` | 绝对坐标 / 归一化坐标（0~1）点击 |
| `Swipe` / `SwipeNorm` / `LongPress` / `LongPressNorm` | 滑动、长按（长按=原地 swipe） |
| `Joystick(cx,cy,dx,dy,dur)` / `JoystickNorm` | 虚拟摇杆：按住中心后推偏移量并保持 dur，再抬起 |
| `Key(code)` | 按键，键名归一化（`home`/`back`/`enter` 等 → `KEYCODE_*`） |
| `Launch(pkg)` | `resolve-activity` + `am start`，失败回退 `monkey -p` |
| `Foreground()` / `IsForeground()` / `WaitForeground()` | 前台包名解析（`mCurrentFocus` / `mFocusedApp` / `mResumedActivity` 三种输出格式都兼容） |

**关键约束与实测数据：**

- **横屏判定**：安卓游戏多为横屏，但物理分辨率是竖屏值。`ScreenSize()` 必须以当前截图尺寸为准，
  否则归一化坐标会整体错位（这是早期一次踩坑，已修复并有 `parseForegroundPkg` / `rotationDegrees` 单测覆盖）。
- **零 CGO 保持**：ADB 后端全部通过 `os/exec` 调用 `adb.exe`，Windows 下带 `CREATE_NO_WINDOW`
  （`0x08000000`）+ `HideWindow`，不弹黑窗口；核心仍然 `CGO_ENABLED=0`。
- **动作空间分层**：`agent.Action` 分 L1 语义层（`ActionMove` / `ActionPress`，
  跨游戏通用）与 L2 执行层（`ActionTap` / `ActionSwipe` / `ActionLongPress` /
  `ActionJoystick` / `ActionKey` / `ActionMouseMove`，平台相关），坐标一律归一化
  （0~1），由游戏档案负责两层之间的翻译。详见 §9.5。
- **安卓默认帧率自动降为 5 FPS**（`screencap` 约 0.94s/帧、`input` 约 0.3~0.6s/次），
  未显式指定 `-fps` 时由 `openBackend` 自动设置——**PC 的 30FPS 假设在 ADB 上不成立**。

### 9.3.1 PC 档案：洛克王国：世界（nrc_pc）

`internal/game/profiles/nrc_pc.json`——PC 键鼠版的洛克王国档案，与手游版 `nrc` 的差异：

- **移动走键盘**：`move.mode = keys`（WASD）；斜向由框架自动组合双键
  （右下 = 同时按住 S+D），`MOVE dir=down_right` 展开为 `keys:s+d/500ms`，实测解析正确。
- **按钮是键盘键不是坐标**：`Button` 新增 `key` 字段，PRESS 落成按键而非点击。
  键位来自游戏内标注与官方键位表（F 交互 / E 精灵球 / Q 星星魔法 / 空格跳跃·投球 /
  R 坐骑飞翔 / C 下降 / Shift 冲刺 / M 地图 / ESC 菜单 / X 取消 / F4 任务 / F5 精灵）。
- 档案 `name` 保持「洛克王国：世界」与窗口标题一致——`-focus-on-start` /
  `-minimize-on-exit` 靠它匹配窗口。
- 用法：`go run ./cmd/helper -game nrc_pc -live -demo`。

### 9.3.2 ⚠️ 实测结论：PC 版注入输入被游戏反作弊拦截（2026-09-12）

**PC 版洛克王国：世界（腾讯）对一切用户态模拟输入免疫**，完整的实验证据链：

| 实验 | 结果 |
|---|---|
| `GetForegroundWindow` | ✓ 游戏就在前台 |
| 进程完整性级别 | 双方都是 elevated（管理员），UIPI 排除 |
| `SendInput` 注入 W（带扫描码）| `GetAsyncKeyState(W)=true`——注入进了系统输入流，**角色不动** |
| `PostMessage` / `SendMessage` `WM_KEYDOWN` | 角色不动 |
| 鼠标 `SendInput` 拖动转视角 | 视角不动（同时段任务距离 7米→10米，游戏本身活着）|

结论：游戏反作弊（腾讯 ACE 类内核驱动）在输入到达游戏前丢弃了带 `LLKHF_INJECTED`
标志的键盘/鼠标事件，且窗口消息路径也被过滤。**修扫描码仍要保留**——那是 UE4/
DirectInput 类游戏的标准要求（见 §9.3.3），但对这个游戏不够。

可行的后续路线（按侵入度排序）：

1. **安卓版 + ADB 后端**（推荐，零额外成本）：`adb shell input` 在系统框架层注入，
   游戏进程侧无法区分，一般不受游戏反作弊影响；`nrc` 档案与安卓后端均已就绪。
2. **驱动级注入**：Interception 等过滤驱动——需要装驱动，复杂度与签名成本高。
3. **硬件级**：Arduino/CH552 模拟 USB HID 键盘——最接近真人输入，但要硬件。

### 9.3.3 注入必须带扫描码（SendInput 的坑）

`keyDown/keyUp` 现在带 `KEYEVENTF_SCANCODE` + `MapVirtualKeyW` 换算的扫描码：
只给 VK 的注入事件，系统消息循环（WM_KEYDOWN）认，但 UE4/DirectInput/Raw Input
这类**按扫描码轮询键盘的引擎直接忽略**。Vk 字段保留，两类消费者各取所需。
（用 `go run ./cmd/win press w 1000` 可随时自测注入链路。）


**PC 实测体验（`internal/overlay` + `internal/gamewin`，Windows only，均默认开启）：**

- **启动置顶（`-focus-on-start`）**：PC 实时控制的前提是游戏窗口**在前台且未最小化**——
  最小化的窗口 GDI 抓不到内容（截出来是桌面），后台窗口收不到键盘焦点（`SendInput`
  的按键会落到别的程序上）。第一版只有"退出最小化"没有"启动还原"，于是第二次跑
  Agent 就在对着桌面盲操作（实测：游戏明明在主屏，抓屏却只看到桌面）。现在启动时按
  档案名还原并置顶，与退出最小化配成一对。置顶绕开了 Windows 的**前台锁**：
  ① 先 `keybd_event` 补一次 Alt 按下+抬起，让系统认为"用户刚按过键"；
  ② 再 `AttachThreadInput` 把自身消息队列接到当前前台线程上借其前台权
  （`AttachThreadInput` 在 **user32.dll**，不在 kernel32——第一版挂错 DLL 直接 panic）。
  只作用于可见/最小化的窗口：同款游戏常有多个同名顶层窗（启动器、反作弊壳、隐藏消息窗），
  对隐藏窗口置顶无意义还可能抢到空壳上。
- **日志浮窗**：屏幕右下角一块置顶半透明黑框，实时滚动最近的运行日志（每步动作、
  执行结果、警告）。关键性质与踩过的坑：
  1. **游戏全屏也可见**——`WS_EX_TOPMOST` + 每 2 秒重新钉顶（防全屏切换后掉下去）；
  2. **抓屏时临时隐藏**——`WDA_EXCLUDEFROMCAPTURE` 对 Windows.Graphics.Capture 是
     「窗口消失」，但对 **GDI BitBlt 是「该区域变黑」**：实测截屏里留一块纯黑矩形，
     老师 VLM 每帧都看得到，感知照样被污染。所以 `pcBackend` 每次抓屏前 `Hide()`、
     抓完立刻 `Show()`，截屏完全干净（demo/教学秒级抓屏频率下人眼无感）；
  3. **不抢焦点不抢键盘**——`WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`；
  4. **渲染三坑**（2026-09-12 实拍「左上角黑块」的完整归因）：
     a. `UpdateLayeredWindow` 的 `pptDst` 参数传 `(0,0)` 不是「忽略位置」而是
        **把窗口移到 (0,0)**——浮窗跑到了左上角。必须传 NULL；
     b. `CreateFontW` 的返回值必须接住再 `SelectObject`——没接住选进去的是 NULL
        字体，浮窗只剩黑底没有字；
     c. **GDI（DrawTextW）不写 alpha 字节**：只改 RGB，alpha 保持底色值。
        半透明要靠 ULW 的整窗 `SrcConstantAlpha`（170≈67%），DIB 本身保持不透明，
        别指望逐像素 alpha。
  5. 关闭用 `PostThreadMessageW(WM_QUIT)` 向消息泵线程投递——
     **`PostQuitMessage` 只对调用线程生效**，第一版从主线程调它导致消息泵永远阻塞、
     进程退出不去（已修复并实测进程自动退出）。
     ⚠️ 若进程异常被杀，浮窗窗体不会自己消失（僵尸浮窗会一直糊在屏幕上并污染
     抓屏）——`tasklist` 找残留 `helper.exe` 杀掉即可，`go run ./cmd/win list` 能看到它。
- **退出最小化**：程序结束时按游戏档案名（如「洛克王国：世界」）枚举顶层窗口，
  `ShowWindowAsync(SW_MINIMIZE)` 最小化游戏，让用户立刻看到终端里的评估/对话输出。
  `ShowWindowAsync` 而非 `ShowWindow`：不等待游戏主循环响应，不卡退出流程。
- 浮窗可视化自测工具：`go run ./cmd/overlay-test -seconds 15`（打印示例日志 15 秒）。
- **窗口探照灯 `cmd/win`**：跑 Agent 前先看清"Agent 眼中的窗口是什么状态"。
  `go run ./cmd/win list [关键词]` 列出顶层窗口（含 hwnd/pid/可见性/最小化/矩形/标题），
  `go run ./cmd/win focus <关键词>` 手动还原+置顶，
  `go run ./cmd/win shot out.png` 用**与实时回路同一条 GDI 抓屏链路**存一张图——
  用它确认感知画面正常再起 LIVE，别对着桌面盲操作。
  注意 `list` 会先 `SetProcessDPIAware`：缩放 125%/150% 的屏上不调它，
  `GetWindowRect` 与抓到的图都是被虚拟化的"逻辑像素"，坐标会算错。

看图 → 出动作 → 执行 → 再看图，同时把 `(学生观测, 老师动作)` 存成示范数据集，

| `-demo` | 启用示范模式（蕴含 `-teacher`），与实时回路互斥 |
| `-demo-steps` | 步数上限，`0` = 直到 Ctrl+C |
| `-demo-width` | 送审老师的彩色帧降采样宽度（默认 1024） |

**示范数据集格式**（`trainer/` 的输入，字段名已用单测钉住）：

```
<dir>/
├── meta.json         目标/模型/屏幕尺寸/步数/解析成功率/平均耗时
├── trajectory.jsonl  每行一个样本
├── frames/step_0001.png   学生观测（灰度降采样）—— 训练时的网络输入
└── color/step_0001.jpg    老师看到的彩色帧（可选）
```

**关键实现细节：**

- **`think` 开关必须放请求顶层**（`teacher.Options.Think`）。这是本轮最重要的修正：
  早前记录的「本机 Ollama 0.34.0 上 `think=false` 无效」是**错误结论**——
  当时写成了 `options.think`，Ollama 直接忽略。放对位置后，同图同提示词从
  **65s / 正文为空** 变成 **1.3s / 正文正常**，老师才可能跑在在线回路里。
- **学生观测与老师视野是两个通道**：`backend.Grab` 给灰度小图（学生输入），
  `backend.GrabColor` 给全分辨率彩色图（老师判读）。混用一个接口必然有一方将就。
- **送审用 JPEG 不用 PNG**：1024 宽下 130KB vs 1.5MB，编码与传输快一个量级，
  界面判读并不需要无损。降采样在 `internal/vision` 里做**区域平均**，
  2608→1024 这种比例下最近邻会把小图标糊成色块。
- **动作解析容错**（`agent.ParseAction`）：大小写不敏感、全半角标点都认、
  键值顺序任意、允许和中文说明混在一行。但**必须要求坐标成对出现**——
  否则「建议：点击右下角按钮」「摇杆: x=0.21 y=0.69」这类**描述**行
  会被当成动作执行，机器人会莫名去点左上角。

**实测（Redmi 25102RKBEC / Android 16 / qwen3.5:9b 本机 3060）：**

| 指标 | 实测值 |
|---|---|
| 单步耗时（think=false） | **1.8~2.0s**（34 tok 输出） |
| 单步耗时（默认思考） | 60s+，且正文常被思考挤空 |
| 动作格式合规率 | 20/20 步（两轮实况） |
| 端到端 | 截图 → 老师出动作 → ADB 触碰 → 落盘，全链路打通 |

**已暴露的局限（诚实记录，别当成已解决）：**

- ⚠️ **提示词里的具体数字会被照抄**。早期 `ActionProtocol()` 的示例写成
  `ACTION JOYSTICK cx=0.21 cy=0.69 tx=0.81 ty=0.69 dur=1200`，
  模型 8 步输出的动作**与示例逐字节相同** —— 看着像「模型不会决策」，
  实际是「示例被当成了答案」。已改为 `<占位符>` 形式。
  小模型对提示词里的具体数值极其敏感，写示例时务必用不可直接复制的形式。
- ⚠️ **单帧决策没有记忆**，容易在原地重复同一动作。已通过 `Demonstrator.PrevAction`
  把上一步喂回去缓解（并把 `prev_action` 一并存进数据集）。
  **但实测只靠这一条没能打破重复**（8 步动作仍逐字节相同），别把它当成已解决——
  真正的解法是让动作空间本身更适合小模型，见 §9.5 的分层设计。
- ⚠️ **动作质量尚未达标**：模型能正确读出画面地标（8/8 答对「帐篷」），
  但读小号距离数字不可靠，且决策偏向提示词的结构先验，
  离「朝 24 米外的目标走过去」这种目标导向导航还很远。
  这正是需要采集示范数据 + 蒸馏学生的原因，不是靠调提示词能解决的。
- ⚠️ **dry-run 下采不到多样数据**：画面不变 → 老师给同一动作。要有多样性必须 `-live`。

### 9.5 基础操作层：一套动作跨游戏（`internal/game`）

这是框架「不为单一游戏设计」的落点。**换一款游戏，只换一份 JSON 档案。**

#### 为什么要把动作分成两层

早期动作空间是**平台原语**（`TAP x=.. y=..`、`JOYSTICK cx=.. cy=.. tx=..`），
于是每换一款游戏都要重新告诉模型「摇杆在哪、按钮在哪」——而小模型最不擅长
恰恰就是输出坐标。实测把摇杆四坐标交给 qwen3.5:9b，它在「`cx/cy/tx/ty`
到底是什么」上纠结到 **74 秒打满预算**，仍给不出动作。

于是拆成两层：

| 层 | 动作 | 谁输出 | 是否跨游戏通用 |
|---|---|---|---|
| **L1 语义层** | `MOVE dir=前`、`PRESS name=jump`、`TAP`、`SWIPE`、`HOLD`、`KEY`、`WAIT` | 老师 / 学生 | ✅ 通用 |
| **L2 执行层** | `JOYSTICK`（摇杆推杆）、`KEY`（按住某键）、`TAP`（某像素点）、`MouseMove` | 游戏档案展开 | ❌ 平台相关 |

模型只需要做一次 **8 选 1 的方向分类**（`up\|down\|left\|right\|up_left\|...`），
摇杆中心与推杆幅度交给档案——它本来就是个**设备常量**，不该每帧回归。

#### 一份档案回答四个问题

```jsonc
{
  "name": "洛克王国：世界",
  "package": "com.tencent.nrc",          // 填了就能用 -game 带出 -app
  "orientation": "landscape",
  "move": {
    "mode": "joystick",                   // joystick | dpad | keys | none
    "center": [0.21, 0.69],               // 摇杆中心（归一化，实测得到）
    "radius": [0.09, 0.08]                // 推杆幅度，留空用默认
  },
  "buttons": [
    { "name": "star", "aliases": ["星形", "交互"], "pos": [0.80, 0.81],
      "note": "右下角最大的圆形按钮。坐标实测，功能未完全核验" }
  ],
  "hints": ["横屏 3D 开放世界；左下角圆形区域是虚拟摇杆，中心约 x=0.21 y=0.69"]
}
```

`hints` 会**逐条拼进老师提示词**，`buttons` 决定 `ACTION PRESS` 的合法取值，
`move` 决定 `MOVE` 怎么落地。

#### 内置档案与「换游戏」流程

| 档案 | 用途 |
|---|---|
| `nrc` | 洛克王国：世界（真机实测坐标） |
| `mobile_generic` | 通用手游模板（虚拟摇杆在左下） |
| `pc_generic` | 通用 PC 键鼠（WASD + 鼠标） |

```bash
# 看看有哪些档案（也可直接读 internal/game/profiles/*.json）
go run ./cmd/helper -game 不存在的名字      # 报错里会列出全部可用档案

# 用手游档案跑在线示范
go run ./cmd/helper -target android -serial <sn> -game nrc \
    -demo -live -demo-steps 20 -goal "靠近任务追踪里的目标"

# 用 PC 档案跑实时回路（dry-run）
go run ./cmd/helper -game pc_generic -frames 100
```

**给一款新游戏做档案**（无需改任何 Go 代码）：

1. 用 `tools/grid_overlay.py` 给截图打上归一化网格，直接读出坐标：

   ```bash
   python tools/grid_overlay.py shot.png --region 0.58,0.45,1.00,1.00 --zoom 2 -o out.jpg
   ```

2. 把摇杆中心、幅度、按钮坐标填进 `profiles/<游戏名>.json`；
3. `-game profiles/<游戏名>.json` 跑一轮 dry-run，确认动作解析与展开无误；
4. 加 `-live` 实跑。

档案查找顺序：**`./profiles/<名>.json` → `.workbuddy/profiles/<名>.json` → 内置档案**，
因此外部文件可以覆盖内置档案，用来修某个游戏的参数而不必改代码。
字段名拼错会**立刻报错**（`DisallowUnknownFields`）——静默忽略会让摇杆中心
悄悄变成 `0,0` 而没人发现。

#### 后端能力矩阵

| L2 动作 | PC（SendInput） | Android（ADB） |
|---|---|---|
| `TAP` / `HOLD` | `SetCursorPos` + `mouse_event` | `input tap` / 原地 swipe |
| `SWIPE` | 分 12 步移动光标（瞬移会被游戏判定为「没动过」） | `input swipe` |
| `KEY` | 30+ 键名（WASD/空格/ESC/回车/数字/方向键/F1~F12） | `input keyevent`（兼容 `dpad_up` 等写法） |
| `KEY` 带 `Dur` | **异步按住**：按下即返回，到期抬起；同键重复下达不断刷新代次 | `input keyevent --longpress` |
| `JOYSTICK` | 无（PC 上由 `move.mode=keys` 落成按键） | 支持（推杆即 swipe）；⚠️ 曾因漏了分发分支被静默吞掉，见下方「动作分发」 |
| `MouseMove` | 支持 | **明确报错**（手机没有鼠标，静默忽略会掩盖上游 bug） |

两个设计决定值得记下来：

- **PC 的「按住」是异步的**。实时回路是 30FPS 节拍，一次阻塞 1 秒会让整条回路停摆。
  语义上也更对：持续移动是「状态」而非「一次持续 1 秒的调用」——每帧重复下达
  `MOVE` 会不断刷新代次，键就一直按着；停止下达后自然松开。
- **退出时必须 `ReleaseAll`**，否则最后一步的「按住」会把键卡在按下状态，
  回到桌面表现为键盘失灵（在记事本里一直输出同一个字符）。

#### L1→L2 是幂等的

`Profile.Resolve` 对已是 L2 的动作原样返回，所以后端可以无脑「先 Resolve 再执行」，
不必分辨动作来自模型还是来自别的环节。`backend.Resolve` 暴露给调用方只为打日志：
示范回路会把两边都打出来，左边是模型意图、右边是落到设备上的操作——

```
[ 3/20] 执行 move:up/800ms         → joy:0.210,0.690->0.210,0.610/800ms | 朝前（上）方向移动 800ms
```

#### 动作分发：设备层绝不静默返回 nil

`android.Device.Apply` 是按 `ActionKind` 分发的 switch。**每一个真机实测过的坑里，
代价最大的一个是它少了一支**：2026-09-12 的抓宠采集跑了一整晚，日志一路正常
（`执行 move:up_right/2500ms → joy:0.210,0.790->0.274,0.733/2500ms`，applied 计数照加，
无任何报错），但角色在地图上一步都没动——`ActionJoystick` 掉进了
`default: return nil`，不触摸、不报错。

现象与「被地形顶住」无法区分：画面变化量 Δ 恒在 1.4~2.7（只有角色呼吸、粒子等
环境动画），于是卡死自愈反复触发，脱困（无论地图脚本还是摇杆长推）也全都无效。

现在：补上 `ActionJoystick` / `ActionNone` 分支，`default` 改为**明确报错**。
`internal/android/apply_test.go` 钉死这条规矩——除 `ActionNone` 外，动作在无设备时
必须返回错误，「返回 nil 却什么都没做」正是要禁止的行为。

排查手法值得复用：**用裸 `adb shell input swipe` 手写同一手势做对照**
（`tools/movetest.py`）。同一位置、同一方向、同一时长，手写能走（Δ11~21）、
经回路发出去却不走，差别就只可能在分发这一层。

#### 界面态判定：不是「数几个按钮」，而是「按钮在不在标定位置」

老师的动作空间本该**按当前界面收窄**——战斗态只该出现「逃跑/背包/捕捉/替换/技能」，
大世界不该出现战斗按钮、也不该关掉 `MOVE`。这需要一个像素级的界面态判据。

`Profile.IsBattle` 的做法（在洛克王国：世界真机标定）：

1. 取底部检测带（`battle_detect` 的 band，归一化 `x 0.55~1.0, y 0.855~0.955`）；
2. 找「又亮又低饱和」的像素（`bright ≥ 150`、`max-min ≤ 70`）——战斗圆钮是浅奶油色；
3. 列投影 → 相邻亮列连通分簇（`runW ≥ 8`、簇内亮像素 `≥ 500`），并算每个簇的**归一化质心**；
4. **位置判据**：质心必须命中 `battle_detect.positions` 标定的圆钮位置（容差 `tol_x/tol_y`，
   缺省 0.015），命中数 `≥ min_hits` 才算战斗。

⚠️ **第 4 步是血的教训**：最初判据只做到第 3 步——「数够 3 个簇就算战斗」。
大地图上散布着大量又亮又低饱和的圆形图标（传送点、图标簇），在检测带里**同样能凑出 ≥3 簇**。
22 张真实帧交叉验证，旧判据**错 17 张**。后果是整轮采集都「以为」自己在战斗中：
老师动作空间被剥掉 `MOVE`、兜底又在图上乱点，40 步全部空跑（`pet_run8`）。

真实战斗圆钮固定在底部一条横排上（nrc 实测 `x≈0.664/0.728/0.786/0.847/0.908`、`y≈0.905`），
加上位置判据后散乱图标无法同时落位。**43 张真实帧全对**
（18 张真战斗 → 战斗，25 张地图/大世界 → 非战斗）。

标定与校验：

- 质心是**绝对坐标的均值**：列投影累计的是带内相对坐标，要补回带原点
  （`Σx = Σ(x−x0) + x0·像素数`），少补这一项只有单列簇才凑巧对。
- `tol` 上限 0.05（`normalize` 会拒绝更大的值）：相邻按钮间距约 0.06，容差过半就会互相串位，
  比不配位置更危险。
- `min_hits` 取 4（不是 3）：`min_hits=3` 时仍有一张地图帧误报。
- 没配 `positions` 的档案自动退回旧的「数簇」判据（兼容），但**给新游戏建档案请务必标位置**。

校验工具：`python tools/detect_state.py <截图> [x0,y0,x1,y1]` —— 打印簇质心、命中位置数、
新旧判据结论，判据与 `internal/game/detect.go` 保持同一套。

#### 宏（macro）：把隐藏状态的多步序列收进档案

「展开技能盘 → 点技能卡 → 等本回合结算」是一个**带隐藏状态的多步序列**，
要求小模型一次给全每一步并不现实（它一次只输出一个动作）。

做法：打包成档案里的**命名宏**，老师只需一次 `PRESS cast_huoyanjian`，
回路按 `steps[]` 确定性展开，**整段只落一条示范样本**：

```jsonc
{ "name": "cast_huoyanjian", "aliases": ["放火焰箭"], "state": "battle",
  "steps": [
    { "pos": [0.908, 0.900], "wait_ms": 1600, "note": "点技能钮展开左侧技能卡" },
    { "pos": [0.215, 0.745], "wait_ms": 4200, "note": "点「火焰箭」卡并等本回合结算完成" }
  ] }
```

配套约束（都在 `profile.go` / `detect.go` 里钉死）：

- **宏不参与 `Resolve`**：`resolvePress` 遇到宏名直接拒绝。若被展开成单点，就退化成
  「点一下技能钮」——正是小模型的坑。
- **`hidden` 项不进老师动作空间，但宏/脚本仍可调用**：技能钮与技能卡标 `hidden`，
  老师看不到它们，只能通过宏使用。
- **按钮与宏带界面态标签**（`world` / `battle`）：`ProtocolOptionsForState` 在战斗态
  只列战斗项并**关掉 `MOVE`**；`PressNamesForState` 供复读兜底**按态轮换**，绝不跨态。
- `main.go` 启动时会打印宏清单与「界面态可否自动判定」，一眼看出档案是否生效。

#### ⚠️ 设备息屏：`screencap` 全黑、`input tap` 被静默吞掉

平板 `screen_off_timeout=60000`（60 秒）且 `stay_on_while_plugged_in=0`，于是**长时间停顿**
（等老师推理、等回合结算）会息屏。息屏后：

- `adb ... screencap` 只能拍到**全黑帧**；
- `adb shell input tap` 被系统**静默吞掉**（不报错、界面毫无反应）。

排查时极易误判成「游戏吞了输入」或「MIUI 截图 toast 干扰」。
**设备侧一键修正**：

```bash
adb shell settings put global stay_on_while_plugged_in 7   # 充电时保持常亮
```

**回路侧**也加了保护（`cmd/helper/demo.go`）：黑帧均值 `blackFrameMean=12.0`，
发现黑帧就发一次 `KEY wakeup` 并等 2 秒重取；仍然黑则跳过本步（不落示范样本），
同时重置卡死计数，避免把「黑屏」当成「卡死」而触发脱困。

#### 真机实测结论（洛克王国：世界 / 3200x2136 平板）

- **摇杆是固定热区**：手势必须从圈内起手。「起手就落在圈外、原地按住」实测完全
  不接管（Δ2~3.6），而「从中心划到边缘」稳定有效（同一手势连做三次 Δ 均为 20 上下）。
  因此 `Joystick` 的实现（中心 → 目标点的一次 swipe）是对的，不必改成原地长按。
- **画面变化量 Δ 的分档**（灰度、降采样 160px、逐像素平均绝对差）：
  正常走动 11~39，被岩石/坡面顶住 1.3~2.7，界面静止 0.0。
  卡死判据取跨 5 步窗口 + 阈值 6.0，两侧余量都很足。
- **点任务追踪不会触发自动寻路**：实测点右侧「前往 XXX N 米」只有一次转视角动画，
  角色并不持续移动（`tools/watch.py` 连看 5 帧验证）。它只能用来读方向与距离，
  长距离移动得走「大地图 → 魔力之源 → 传送」。
- **大地图关闭按钮 ✕ 的热区明显小于图标**：同屏 A/B 实测
  `(0.9270,0.0450)`＝设备 `(2966,96)` **一次点掉**，而 `(0.9245,0.0405)`＝设备 `(2958,87)`
  只差 8~9px 却**点不动**。标定按钮时要用放大网格取**热区中心**，不能只对准图形。
- **地图上的魔力之源锚点坐标依赖视野**（视野随角色位置变化），会失效。
  所以 `escape` 脚本是二线手段（每 4 次脱困才跑一次），
  并自带「关详情面板 → 关大地图」两步收尾，保证失败时不会把角色丢在地图界面里。

### 9.6 Phase 2.5：教学视频抽帧与判读（`cmd/video`）

§9.4 的在线示范有个绕不开的短板：**老师只能靠自己瞎猜**——实测动作分布熵极低，
几乎永远输出「摇杆推某方向」。更快的路子是**向已经玩明白的人类录像学**：
抽帧 → 去重 → 切成动作段 → 老师逐段判读，产出可读的策略清单。

```bash
# 只抽帧切段（不烧算力，先看关键帧质量）
go run ./cmd/video -in 教学视频.mp4 -out .workbuddy/videos/p01

# 抽帧 + 老师判读（需先 bash tools/serve_ollama.sh）
go run ./cmd/video -in 教学视频.mp4 -out .workbuddy/videos/p01 \
  -annotate -game nrc -goal "学会移动、捕捉精灵、推进新手流程"

# 先试水 8 段，确认提示词效果再跑全量
go run ./cmd/video -in 教学视频.mp4 -annotate -annotate-limit 8 -game nrc
```

**流水线：**

```
mp4 ──ffmpeg 定频抽帧──> 原始帧 ──dHash 去重──> 关键帧 ──距离突变切段──> 动作段
                                                                  └─每段取 3 帧送审──> 老师判读
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `-in` / `-out` | — | 输入视频；输出目录（默认 `.workbuddy/videos/<时间戳>`） |
| `-rate` / `-width` / `-q` | `2` / `640` / `3` | 抽帧频率；输出宽度（0 = 原分辨率）；JPEG 质量 |
| `-dedup` | `10` | 去重阈值（dHash 汉明距离），负数 = 不去重 |
| `-seg` / `-min-seg` | `26` / `8` | 切段阈值；段最小帧数（用于合并碎片段） |
| `-start` / `-end` | — | 只处理片段，如 `-start 10m -end 20m` |
| `-annotate` / `-annotate-limit` | 关 / `0` | 开启判读；最多判读多少段（试水用） |
| `-game` / `-goal` | — | 游戏档案（提供按钮名与界面先验）；游戏目标 |
| `-keep-raw` / `-quiet` | 关 / 关 | 保留未去重的原始帧；不显示 ffmpeg 进度 |

**产出：**

| 文件 | 内容 |
|---|---|
| `meta.json` | 源信息、参数、统计、关键帧清单（含每帧 dHash 与时间戳） |
| `clips.jsonl` | 每段一行：时间范围、代表帧、老师判读结果 |
| `frames/` | 去重后的关键帧，保留完整时序（第二阶段的输入） |
| `report.md` | 人读汇总：局面 / 操作 / 策略 |

**关键设计：**

- **不用 ffmpeg 的场景检测**（`select='gt(scene,X)'`）。录屏压缩后 scene 分数抖动大；
  更重要的是它的语义是「变化开启」而不是「去重」，一段静止的讲解画面会被整段漏掉——
  而操作教学里「停在某界面不动」往往正是重点。主路径改为「定频抽帧 + Go 侧 dHash 去重」：
  结果可复现、可单测，去重率本身还能当质量指标。
- **去重与切段解耦成两个独立阈值**：去重管「保留多少细节」（关键帧是第二阶段蒸馏的输入，
  不能太稀），切段管「划分粒度」（决定送审成本与判读跨度）。
- **用 dHash 而不是画面均值**：均值只看整体亮度，「镜头从左转到右」这种等亮度的剧烈变化
  会被判为没变。dHash 还天然免疫整体亮度漂移（单测：整图提亮 12 级，哈希一位不变）。
- **判读必须关思考**（`think=false`，且必须放请求顶层，见 §9.1 的坑），单段 2.0~3.1s。

**阈值标定（《洛克王国：世界》38 分钟新手录屏实测）：**

游戏画面是持续运动的（草地、云、UI 骨骼动画、镜头跟随），相邻帧 dHash 距离天然就有 8~20，
且**距离分布是连续单峰、没有天然分界点**。这意味着纯视觉手段切不出「玩家在做什么」的
语义边界，只能按「一屏操作的天然时长」来标定粒度：

| 参数 | 初值 | 标定值 | 依据 |
|---|---|---|---|
| `-dedup` | 6 | **10** | 关键帧 2848 → 2292，去重率 38.9% → 50.8% |
| `-seg` | 14 | **26** | 546 段 / 3.5 秒一段 → 120 段 / 18.3 秒一段 |
| `-min-seg` | 4 | **8** | 合并快速运动产生的碎片段 |

3.5 秒一段时老师根本看不出「一件事」，18 秒才够。**默认值只对运动画面成立**，
静止画面为主的演示类视频应显著调低。

**实测（1280x720 AV1 录屏，38.8 分钟）：**

| 项 | 实测值 |
|---|---|
| 抽帧 + 去重 + 切段 | 4658 帧 → 2292 关键帧（去重 50.8%）→ 120 段 |
| 单段判读（`qwen3.5:9b`，think=false） | **2.0~3.1 秒** |
| 全量判读 120 段 | 约 5 分钟，**成功 120/120** |

判读产出的样例（原样摘录，可见确实是从画面读出来的）：

- `00:17:03` 精灵整理阶段：**通过拖拽方式将新获得的精灵放入图鉴网格中进行收纳**
- `00:18:29` 移动技巧：**利用飞行或跳跃技能可以快速跨越障碍和地形，提升探索效率**
- `00:35:04` 过场处理：**在剧情节点前移动到指定位置触发事件，遇到可跳过的过场动画时选择跳过以节省时间**
- 27 段如实标注「本段无操作可学」（过场动画 / 加载 / 纯界面停留）

**⚠️ 诚实边界（别当成已解决）：**

- **视频里没有动作 ground truth**。录像只有画面、没有「手指按在哪」，老师推断出的
  「操作」是**弱标签**——数据里用 `weak_label: true` 标出，报告里也显式标注，
  **绝不能当训练真值**。本阶段真正可靠的产出是**局面**与**策略**。
- 想要真标签只有一条路：录制时打开 Android 开发者选项的「显示点按操作反馈」，
  让触点圆点直接画进画面，那才可以机械提取。
- **视觉段 ≠ 语义段**：dHash 只能给出「画面结构稳定的一段时间」，切不出「玩家在做同一件事」，
  段碎或段长是这类方法的固有问题。
- **hints 会被当成答案**。档案里写了「点任务追踪文字可以自动寻路」，实测 8 段里 6 段的
  「策略」都在照搬这句，连纯过场动画段也不例外。已在提示词里加约束（结论必须来自画面差异，
  并允许模型如实回答「本段无操作可学」），改后同类问题消失，单段耗时还从 3.6s 降到 2.4s。
- **已实测确认：视频判读不能当动作训练集**（2026-09-13）。用 `tools/video_to_dataset.py`
  把 1780 段判读按关键词映射成训练格式（映射率 79.7%，1419 有效样本），训了两版学生模型：
  `val_acc` 分别恒定 **63.49% / 52.36%**（恰好等于最多数类占比），40–50 个 epoch 纹丝不动——
  典型的 mode collapse：模型学会「无论看到什么都输出同一类」，毫无决策能力。
  **对照组更有说服力：真机示范只用 60 个样本就有 66.67%，视频 1419 样本反而更低。**
  根因是四条叠加：① 标签是**推断**的弱标签；② 段长 19.4 秒 ≫ 训练样本的单帧粒度；
  ③ 35.5% 的段是复合行为（移动+点击混在一起）；④ `tap` 占 51.9%、`up=256` 而 `down=6`
  严重不均衡。**铁律：标签质量 > 数据数量。**
  正确用法见 `outputs/game-sensei-视频训练可行性实测.md`：视频 → 流程知识（hints）、
  界面状态分类、视觉预训练；**动作克隆一律走真机示范**（`-demo`）。
  另记一个跨模块坑：`trainer/train.py` 的 `map_action()` 认的是**原始轨迹 kind**
  （`move`/`key`/`joy`），不是目标类别（`up`/`press`），按直觉输出会静默丢样本
  （实测 1472 只剩 841）。
- 若要把这版弱标签数据先训成**管线基线**、后续用真机示范 `--init` 加训，见 §11.14。

## 11. 去 CGO 化方案（Windows 专属）

项目仅运行在 Windows，因此可彻底去掉 CGO 依赖：`go build` 秒级编译、单 exe 发布、无 C 工具链。原方案中 `robotgo`（键鼠）与 `onnxruntime_go`（推理）是仅有的两处 CGO 依赖，替代如下。

### 11.1 截屏与键鼠：纯 Go syscall（必做）

- **截屏**：用标准库 `syscall` 直接调 Windows API，不引入 robotgo。
  - 整机/窗口抓屏：`PrintWindow` / `BitBlt`（gdi32）——简单通用。
  - 游戏实时抓屏首选 **DXGI Desktop Duplication**（d3d11），纯 Go 经 `syscall.NewLazyDLL("d3d11.dll")` 调用，比 GDI 更快、不吃游戏性能。
- **键鼠**：`syscall.NewLazyDLL("user32.dll").NewProc("SendInput")` 模拟键鼠，跨进程通用，无需 robotgo。
- 收益：核心程序彻底零 CGO，去掉 robotgo 的 C 依赖与编译负担。

### 11.2 学生推理：三种去 CGO 选项

| 选项 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A 纯 Go 自写前向 | 自己用 Go 实现小 CNN/LSTM/MLP 前向（整型运算） | 零依赖、零 CGO、编译最快 | 只能跑自定义网络结构，不能加载任意 ONNX |
| B 挂 onnxruntime.dll | 运行时 `syscall.NewLazyDLL("onnxruntime.dll")` 调其 C ABI | 保留 ONNX 生态、能加载训练好的量化模型、核心仍零 CGO | 需自写一层纯 Go 的 onnxruntime C API 绑定（中等工作量） |
| C 独立推理子进程 | `cmd/inferd` 单独编译（可用 CGO 或 Python），核心经命名管道/IPC 收发「帧→动作」 | 核心纯 Go、推理组件热替换、崩溃隔离 | 多一个进程、需 IPC 协议 |

### 11.2.1 ✅ 已落地：A 方案（纯 Go 前向，2026-09-12）

实际选了 **A**：学生网络很小（3 层 CNN + 双头），48×64 输入下纯 Go 前向 <1ms，
不需要为它引入 dll 分发。链路：

```
老师示范(-demo)                    训练(CPU)                    学生实时操作
trajectory.jsonl + frames/  →  trainer/train.py  →  models/*.weights.json  →  helper -student
(internal/dataset 落盘)        torch BC 训练         纯 JSON 权重文件           internal/student 纯 Go 前向
```

- **网络结构**（Python 与 Go 两侧严格一致，tools/parity 校验误差 <1e-5）：
  `conv1(1→8,3x3)+relu+pool2 → conv2(8→16,3x3)+relu+pool2 → conv3(16→24,3x3)+relu
  → GAP → fc(24→64)+relu → cls_head(64→8) / coord_head(64→2)+sigmoid`
- **输出头**（跨游戏通用，不随游戏变）：8 类 = up/down/left/right/tap/press/wait/none
  + tap 归一化坐标回归。「学的是看画面选动作」这个能力本身，具体点哪/往哪走由动作空间和档案吸收。
- **权重文件** `models/*.weights.json`：JSON 格式（float32 数组），version=1；
  Go 侧 `internal/student.Load` 按字段名加载并做长度校验。
- **训练**：`C:/Users/ay/.workbuddy/binaries/python/envs/default/Scripts/python.exe
  trainer/train.py --data <demo目录> --out models/<名字>.weights.json`（依赖 torch+numpy+pillow）。
  类别加权（tap/press 权重高）防「永远不动」退化；解析失败的示范步自动剔除。
- **一致性校验**：`go run ./tools/parity`（合成数据冒烟：训练→导出→Go 前向，比对 torch 基准）。
- **接入实时回路**：`go run ./cmd/helper -game <档案> -live -student models/<名字>.weights.json`。

### 11.3 推荐组合

- **截屏 / 键鼠**：纯 Go syscall（必做，去 robotgo）。
- **推理**：✅ 已落地 **A（纯 Go 自写前向）**（§11.2.1）；学生网络变复杂（如要跑视觉
  Transformer 或加载现成量化 ONNX）时再启用 B（LazyDLL 挂 onnxruntime.dll）。
- **老师**：本来就是 `net/http` 调 Ollama，无 CGO 问题。
- **子进程 C** 作为进阶选项：当学生网络变复杂、想用 Python 训练链直接服务时，把推理拆出去。

### 11.4 发布形态

- 纯 Go 核心 → 单 `helper.exe`，`CGO_ENABLED=0 go build`。
- 学生权重 `models/*.weights.json` 是纯数据文件，随包放置即可（热载同 onnx 方案）。
- `robotgo` 从依赖中移除，`go.mod` 不再需要 CGO 工具链。

### 11.5 ⚠️ 实测坑：锁屏/系统 UI 前台会让 GDI 会话失效（2026-09-12）

锁屏（LockApp，类名 `Windows.UI.Core.CoreWindow`）在前台时：

1. `SetForegroundWindow` 对任何普通窗口都失败（前台锁 + 锁屏在独立桌面）；
2. `SendInput` 的点击会**落在锁屏上**，触发锁屏过渡——过渡期间本进程的
   GDI 句柄批量失效，`BitBlt` 连续报 `The handle is invalid`（重试也失败，
   等锁屏稳定后自动恢复——是会话级状态破坏，不是句柄泄漏）。

防御（已实装）：helper 启动时 `gamewin.ForegroundIsSystemUI()` 检查，
前台是锁屏/系统 UI 直接拒绝启动；demo 循环抓屏失败自动重试 2 次（应对偶发抖动）。

### 11.6 窗口感知域：把截屏/点击/送审收敛到游戏窗口（2026-09-12）

窗口化游戏（微信小游戏 427x782）嵌在 1920x1080 桌面里，全屏感知双重劣化：
老师 1024 宽送审帧里游戏只占 28%（实测被描述成「手表表盘」），学生 160px
灰度观测里游戏只剩 45px 噪声。

解法（`-game` 档案模式自动启用，无需新参数）：

- 启动置顶游戏窗口后 `gamewin.ClientRectByTitle` 取**客户区**矩形
  （排除标题栏/边框），注入 `pcBackend.SetWindowRegion`；
- `capture.GrabRegion/GrabColorRegion` 只抓窗口子矩形；
- `input.Actuator.Offset` + 窗口尺寸注入：归一化坐标 = 窗口域，
  `pixel()` 换算后加窗口原点得屏幕绝对坐标；
- 档案按钮 `pos` 从此全部按**窗口归一化**填写（与感知域一致）。
  ⚠️ 旧档案按全屏标定的坐标需重新标定。

### 11.7 ⚠️ 实测坑：日志浮窗与 GDI 抓屏互斥挂死（2026-09-12）

浮窗开启时第一次「Hide→BitBlt→Show」整进程挂死（最小探针复现；
卡点在 user32/GDI 交互，未深究）。**`-overlay` 默认已改 false**，

的元凶就是它——当时误判为 Ollama/网络问题。

### 11.8 ⚠️ 实测坑：9B 老师的「复读机」与强制轮换兜底（2026-09-12）

解忧梦幻岛实测：PrevAction 喂回 + 提示词禁令都压不住 qwen3.5:9b
重复同一坐标（20+ 步连点，甚至误点 VIP 弹出 30 元付费弹窗）。

兜底（已实装 `cmd/helper/demo.go`）：连续重复 ≥3 步时跳过老师决策，

用状态多样性弥补动作多样性。**小模型提示词禁令不可信，程序级兜底才可靠。**

> 「≥3 步就换按钮」（走远本就要连续同向），且卡住时改为**换方向**而非换按钮。

### 11.10 ⚠️ 实测坑：单向死撞——单帧 VLM 分不清「在走」和「顶墙」（2026-09-13）

反横跳（§11.8 的加强版）落地后 `pet_run12` 复测：横跳窗口 **0/44**（此前 9/30），
但暴露了它的**镜像失败模式**——单向死撞。

现象（`pet_run12`）：老师 43 步里连打 `move:up_right/1500ms`、**最长连走 41 步**，
单步画面变化量多次掉到 1~3（只剩角色呼吸/粒子），角色在地图上原地不动。
两个既有兜底都没解开：

- **卡死判据**（窗口 Δ，`stuckDiffEps=6.0`、窗口 5 步）看的是**跨窗口**变化，
  要求「整段时间世界都没动」。顶着墙持续走时角色/粒子动画仍在变，窗口 Δ
  压不到阈值以下 → 脱困几乎不触发（`pet_run12` 全程只触发 2 次，且都在 Δ<3 的极端时刻）。
- **复读兜底**（移动放宽到 ≥8 步）只会按 `step%n` 轮换**世界按钮**（`mount`/`star`/`wolf`），
  在顶墙场景里那是空操作甚至误触——既没解开卡点还白送一步。

根因：**单帧 VLM 无法区分「在往前走」和「顶着墙走」**——两种情况画面里都有角色动画，
相邻两帧的变化量天生就小。判据必须**把相邻两步的 Δ 喂给老师**，让它自己察觉「这一步没挪窝」。

修复（已实装）：

1. `Demonstrator.LastDiff`（上一步单步 Δ）+ `MoveStallStreak`（连续同向小 Δ 步数，
   阈值 `moveStallDiffEps=4.0`）。连续 ≥2 步时，MOVE 分支提示词改口
   **「禁止再沿原方向走」**并附上实测 Δ；正常时也给一句 Δ 供参考（提示词不再只说「继续走」）。
2. 复读兜底**分流**：`prevKind==MOVE && Profile.CanMove()` 时，在 `escapeDirs`
   里轮换出一个**与当前方向不同**的方向长推（`moveDirOf` 解析当前方向，避免「换向」换到同一个）；
   非移动动作仍走原 PRESS 轮换。`Profile.CanMove()` 与 `ProtocolOptionsForState` 的
   `HasMove` 同源，保证「能给 MOVE」和「能换方向」不打架。

两级卡死判据的分工（都保留，缺一不可）：

| 判据 | 口径 | 阈值 | 治什么 |
|---|---|---|---|
| `stuckStreak` | 跨窗口 Δ（当前帧 vs N 步前锚点） | `6.0` / 窗口 5 步 | 整段时间世界没动（息屏、加载、角色被钉住） |
| `moveStallStreak` | 相邻两步 Δ | `4.0` | 这一步几乎没挪窝（顶着墙持续走） |

后者专治前者的盲区：**「世界在动」不等于「我在动」**。

### 11.11 ✅ 真机复验：Δ 闸门与提示词反馈各自生效（2026-09-13，pet_run14）

三场同目标采集（`-demo-steps 60`，`qwen3.5:9b`，无线 ADB）横向对比：

| 指标 | pet_run12（反横跳） | pet_run13（停滞反馈） | pet_run14（+Δ 闸门） |
|---|---|---|---|
| 老师动作数 | 49 | 50 | 60 |
| 小 Δ（<4）步数 | 25 | 10 | 11 |
| 最长同向连走 | **41** | 40 | 20 |
| 横跳窗口 | 0/44 | 0/45 | 5/55 |
| 复读兜底·换方向 | 0 | 5 | **1** |
| 复读兜底·误点世界按钮 | **6** | 1 | **0** |
| 🧱 撞墙告警 | 0 | 1 | 1 |

**闸门漏放行（强制换向时 Δ≥4.0）**：pet_run13 为 **4/5 次**（Δ 13.3 / 5.4 / 19.1 / 6.4，
都在正常赶路），pet_run14 为 **0/1 次**——闸门按设计只在「确实没挪窝」时介入。
校验脚本：`.workbuddy/codex/verify_gate.py`（新旧日志格式都兼容；它直接断言每条
强制换向日志内嵌的 Δ 是否 < `moveStallDiffEps`）。

两条关键证据（`pet_run14` 原始日志）：

- **闸门放行正常赶路**：step 2~14 老师连打 `move:down_right/1200ms` 共 **13 步**，

  **step23 老师自己把方向从 `down_right` 换成 `up_left`**（无人强制），Δ 立刻回到 15.4。
  这验证了「把回路实测 Δ 喂给老师」这条路的有效性。

**新增观察（与本轮无关，待单独处理）**：`pet_run14` 后段（step 47~60）在战斗态反复进出，
老师交替 `cast_hetu` ↔ `battle_catch`，横跳窗口 5/55、🔁 告警 2 次。属「战斗内策略打转」
（技能/投球/聚能之间的取舍），不是移动治理的回归，需另找判据。

### 11.12 ✅ 战斗内死锁的三层成因与修复（2026-09-13，pet_run15 + 真机手动标定）

§11.11 结尾留的「战斗内策略打转」查清了：**不是提示词措辞问题，是三个缺陷叠在一起**。

#### ① 能量机制此前是错的：一次聚能 +5，不是 +1（真机实测）

拿 `cmd/shot` 在真机战斗里逐次操作 + 截图，把 ★ 机制标定清楚了：

| 操作 | 观测 | 结论 |
|---|---|---|
| 战斗开始 | 左下角 ★0/10 | ★N/10 是**我方能量**；技能卡面 ★N 是消耗（赫突★3/火焰箭★2/超导★3/热砂★2） |
| 点一次「聚能」 | ★0 → **★5** | 一次 **+5**（原档案写 +1，是猜的） |
| 再点一次 | ★5 → **★10**（封顶） | 上限 10 |
| ★10 时点「赫突」卡 | 能量 10 → **7**，Δ 明显变大，回合结算 | **有能量技能就放得出去** —— 确认「Δ<4 = 能量不足」判据成立 |
| 每次点聚能 | 敌方立刻反击，我方掉 63 血 | 聚能**消耗一个回合**，不能连点 |

修复：`gather_energy` 宏由「连点 2 次」收敛为**单步一次**（`profiles/nrc.json`），
档案 hint 同步改写为实测数值。原来的两条（+1、连点两次）都会白送一回合给敌方。

#### ② 战斗态检测闪断，把动作空间整体抖散（治本的一条）

`pet_run15` 里 92 帧**翻转 28 次**（`pet_run14` 60 帧翻 5 次）。离线复跑 `IsBattle`
逐帧判定，结果与日志的 ⚔️ 标记完全一致 —— 检测器忠实反映画面，不是判据 bug。

真相在画面里：点 `battle_catch` 进入**投球瞄准态**后，游戏把底部五钮收起、右下换成
世界三钮，**但敌方精灵仍在场、血条不变，战斗并没有结束**。于是：

```text
进战斗 → 点 battle_catch（进瞄准态）→ 检测判「世界」→ 提示词给出 MOVE
       → 老师推摇杆（无效）→ 下一帧又检出战斗 → 又给战斗项 → ...
```

每翻转一次，老师的**整套动作空间**都换一套（战斗态隐藏 MOVE、只列战斗项；世界态反之），
模型只能跟着横跳。**这是「战斗段动作横跳」的上游成因，比提示词措辞更根本。**

修复（`cmd/helper/demo.go`）：新增 `battleStateStep` 滞回状态机 —— 检出即进战斗态，
但必须**连续 `battleHoldFrames=3` 帧都没检出**才切回世界态。取 3 的理由：瞄准态在采集
节奏（约 1 步/1.2~2s）下通常持续 1~2 帧，3 帧能盖住它；而战斗真结束时会多按 2 步战斗
按钮，代价只是白耗 2 步。已补 `TestBattleStateStep` 钉住语义（含 run15 step18~22 的真实形状）。

#### ③ 抓宠闭环仍是断的：`battle_catch` 只进瞄准态，不投球

这是**本轮最重要的结论，也是任务闭环的断点**：

- `battle_catch` 只把界面切到投球瞄准态（左侧弹咕噜球轮盘 + 一条黄色抛物线），**它本身不投球**。
- 真正投球要**沿抛物线从弧末端朝敌方精灵快速拨动（fling）**，是个 SWIPE。
- 而战斗态的动作空间按态收窄后**只剩 PRESS/KEY/WAIT，没有 SWIPE**
  （见 `ProtocolOptionsForState`，`AllowFreePointer=false`）。

所以老师永远走不到「投球出手」那一步：它反复点 `battle_catch`（只进瞄准态），
能量不足时又反复点技能 → 两招之间来回空按。**要闭环，得给战斗态补一个可投球的宏。**

好消息：`game.MacroStep` **本身已支持拖拽**（`pos` + `to` + `drag_ms`），
不需要改 Go 代码就能表达「按下拖到某处」；档案里也有现成先例（`escape` 脚本用
`to` 把大地图拖到底）。所以投球宏是**纯档案工作**，就差在真机战斗里标定起止坐标。

#### pet_run15 vs pet_run14（同目标 60→100 步）

| 指标 | pet_run14 | pet_run15 |
|---|---|---|
| `gather_energy` 使用次数 | **0** | **9** |
| 战斗内动作种类 | 2（cast_hetu / battle_catch） | 4（+gather_energy / none） |
| 全局横跳窗口 | 5（打转段 2） | **2（打转段 2）** |
| 战斗内无效动作（Δ<4）占比 | 42% | 55% |
| 战斗段落数 | 3 | 15 |

「Δ<4 → 去聚能」这条**已被老师学会**（9 次），横跳密度减半；无效动作占比反而升高，
是因为按①②修好前的聚能只给 +1、且战斗态闪断，老师拿到的是自相矛盾的信息。
校验脚本：`.workbuddy/codex/verify_battle.py`（按 ⚔️ 标记切战斗段，逐段列动作序列）。

#### 结论分级

- **已验证**：★ 机制数值（+5/上限 10/技能消耗★N/聚能占回合）——真机逐次操作 + 截图。
- **已验证**：滞回状态机的逻辑 —— 单测 + 离线重放 run14/15 帧。
- **已实现未真机验证**：滞回在真机上对横跳的抑制效果。
- **未完成**：投球宏（缺真机战斗内标定）；能量不足时「压血→捕捉」的完整闭环。
- **已知限制**：战斗态暂无 SWIPE，投球只能做成宏（坐标固定），抛物线会随敌方位置变。

### 11.13 ⚠️ 上一节有三处判断被推翻 + 给纯文本模型补一双「眼睛」（2026-09-13）

接着 §11.12 继续做投球标定时，先卡在「找不到一场战斗」，查下去发现**上一轮的结论有一半
是建立在错误的态势判断上的**。这一节按「先纠正、再补工具」的顺序记。

#### 一、所谓「角色被地形卡住」是误判：它其实在战斗里推摇杆

上一轮收尾时的结论是「角色被岩壁困住，脱困脚本坐标失效」。本轮用新写的确定性探索器
`cmd/hunt`（见第四节）实跑 60 步，Δ 曲线把真相直接摊开了：

```text
步 1~28   Δ = 11.4 / 11.0 / 11.5 / 19.4 / 15.8 … 55.1     ← 角色确实在走
步 29     Δ = 1.7                                          ← 骤降，此后再没起来
步 29~60  Δ = 1.5 ~ 2.0（全程）
步 34/49  执行档案脱困脚本 5 步（大地图传送）→ Δ 仍是 1.5（一点没动）
```

Δ≈1.5~2.0 正是「只有环境动画」的基线（量纲见下表）。**推摇杆没反应不是因为撞墙，
而是因为已经进了战斗——战斗里根本没有摇杆，给 MOVE 什么都不会发生**（档案 hint 里
早就写了这条，只是当时没人把它和「Δ 卡在 1.5」联系起来）。

#### 二、`IsBattle` 会漏判真实战斗（本轮最该记住的坑）

决定性证据是一条命令：在「卡住」的画面里按一次**聚能**钮（坐标 `0.085,0.885`）。

```text
shot -press gather_energy -delta   →   Δ=25.6
```

世界态下这个坐标是空的，不可能有 25.6。**它生效 ⇒ 当时就在战斗里。**

那为什么 `IsBattle` 一路判 `world`？看底栏像素证据（`cmd/see` 的掩膜图）：

```text
x≈0.08 有白色圆钮（= 聚能，仅战斗态存在）
x≈0.63 / 0.71 / 0.78 / 0.85 / 0.92 有五个等距白圆钮（= 逃跑/背包/捕捉/更换/技能）
```

判据依赖「检测带内**亮且低饱和**的列簇 + 落到标定位置」。同一场战斗里，
瞄准态那一帧亮度正常（整幅 luma≈161）→ 判 `true`；而另一帧整幅更亮（luma≈163，
但背景是大片高亮天空/水面，底栏圆钮被照亮、饱和度也被带高）→ 亮簇数掉到 2、命中 0
→ 判 `false`。

**结论：判据对「整体亮度 / 背景色」不够鲁棒，会把真实战斗漏成世界态。** 危害是连锁的：
漏判 → 提示词给出 MOVE → 老师推摇杆（必无效）→ 白耗一整步并污染示范数据。
§11.12② 的滞回只解决了「闪断」，解决不了「持续漏判」——**这两件事要分开治**。

> 待办：给 `BattleDetect` 补一条不依赖亮度的备用判据（例如「底部固定位置是否存在
> 圆形轮廓」或「聚能钮配色」），并在 `cmd/see` 里做成可视化的判定依据。

#### 三、投球不是 fling，是**两次点击**（推翻 §11.12③ 的核心假设）

`dvg.cn`《洛克王国世界》捕捉任务图文攻略原文：

> 3、然后进入战斗，可以看到下面有捕捉
> 4、**点击，再点击左上的咕噜球，最后点击想捕捉的精灵**，就可以完成任务了

即：`battle_catch` 进瞄准态 → **点左上的咕噜球** → **点目标精灵**。没有划动。

真机实测也把「沿抛物线 fling」这条彻底证伪了。协议：进瞄准态后，在屏幕中心做滑动手势，
**只扫时长这一维**（路径固定 `0.52,0.44 → 0.58,0.46`）：

| 时长 | 10ms | 30ms | 60ms | 100ms | 150ms | 300ms | 600ms |
|---|---|---|---|---|---|---|---|
| Δ | 26.1 | 26.2 | 26.5 | 25.9 | 25.5 | 25.5 | 21.6 |

**全时长给出同一个 Δ≈25，而且可以无限重复。** 投球是**一次性**动作（投完瞄准态就该退出），
「每次都能再现」说明它只是**连续的位置拖动**（调准星/转视角）。佐证两条：

- 同一位置的**纯点击** `tap 0.55,0.45` → Δ=1.6（等于待命基线，什么都没发生）；
- 每次尝试后按 `cancel_aim` 仍给 Δ≈33~39（瞄准态**始终没退**，球没投出去）。

所以 §11.12③ 的「战斗态没有 SWIPE 所以断链」这个论证前提本身是错的：
**投球不需要 SWIPE，战斗态的动作空间本来就不用放开。** 缺的只是一组「点球 → 点精灵」的坐标。

#### 四、本轮新增的工具（都不依赖大模型，可复用）

这一节的排查能推进，靠的是三件新工具。它们的存在理由都是同一个：
**老师是纯文本模型，读不了图**，所以「看清屏幕」这件事必须由代码来做，不能靠人肉。

| 工具 | 作用 | 关键用法 |
|---|---|---|
| `cmd/see` | 把一帧画面翻译成**纯文本报告**：亮度图（`.:-=+*#%@`）、色相图（`ROYGCBPM·`）、面板图（近白占比）、颜色掩膜图（yellow/orange/red/white/cyan/green，带质心与包围盒）、A/B 变化图；每张图都带**归一化坐标标尺** | `see -in f.png -mask yellow` / `see -in a.png -vs b.png` / `see -crop 0.0,0.83,1.0,0.97` |
| `cmd/hunt` | 确定性探索器：按档案推摇杆找野生精灵，一进战斗态就落图退出。把「找一场战斗」从「跑完整回路撞运气」变成一条命令 | `hunt -game nrc -steps 300 -escape` |
| `cmd/shot`（扩展） | 标定器：`-press 名字`（按命名按钮，宏会整条跑完）、`-seq "x,y:wait;x,y:wait"`（多步连击，用于「点A再点B」）、`-delta`（报动作前后 Δ）、`-ab`（存动作前帧做对照）、`-check`/`-game`（判界面态） | `shot -press cast_hetu -delta -ab -o _t.png` |

配套改动：`frameDiff` / `meanGray` 收敛到 `internal/vision`（`FrameDiff` / `MeanGrayFrame`），
helper、hunt、shot、诊断脚本**共用同一份判据**——之前这段逻辑被独立写过四遍，代价是
「各处 `Δ<4` 说的不是同一件事」，复盘时无法对齐。

#### 五、Δ 的量纲（标定时的读数参照）

`vision.FrameDiff` = 逐像素平均绝对差（0~255），对 3200×2136 帧下采样到 320 宽后实测：

| Δ | 含义 | 洛克的典型场景 |
|---|---|---|
| 0.0 | 逐字节相同 | — |
| **1~3** | 只有环境动画/呼吸动作 | 角色没动、或输入没送达；**战斗待命态的稳定基线 = 1.6** |
| 4~8 | 边界带 | 小步位移、或只有远景在动 |
| 10~60 | 角色确实在移动 | 大世界赶路（实测 11~56） |
| >60 | 整屏变化 | 开地图/转场/技能特效 |

判据设计上有个反复踩到的坑值得写下来：**「Δ 大」不等于「动作按我说的生效了」**。
本轮 25 左右的 Δ 一度被误读成「投球成功」，实际只是相机被拖动。要区分，
必须找一个**只对目标动作敏感**的二值判据（本轮用的是「投球成功后瞄准态应当消失 →
再按 `cancel_aim` 的 Δ 应该很小」），而不是只看 Δ 的量级。

#### 结论分级

- **已推翻（上一轮结论）**：「角色被地形卡住」——实为战斗内推摇杆；「投球要 fling（SWIPE）」——实为两次点击。
- **已验证**：`IsBattle` 存在**持续漏判**（聚能钮 Δ=25.6 为直接证据）；底栏 5 等距圆钮 + x≈0.08 聚能钮可作像素指纹。
- **已验证**：瞄准态下中心区拖动的 Δ 对时长不敏感（10~600ms 全 ≈25）且可无限重复 ⇒ 是调准星不是投球。
- **已实现未真机验证**：`cmd/see` / `cmd/hunt` / `shot -seq` 三件工具本身；`internal/vision.FrameDiff` 收敛。
- **未完成**：咕噜球与目标精灵两个坐标的标定（扫描脚本 `throw_sweep.py` 已就绪）；`IsBattle` 的亮度鲁棒性修复。
- **新增线索（来自攻略，非本机实测）**：战斗抓宠成功率与血量/异常状态/球种的关系、大世界可直接抓、
  稀有精灵的限时/天气/场景刷新条件 —— 已整理进 `profiles/nrc.json` 的 hints。

> ⚠️ `--epochs` 别照抄小值：几十条样本时 **30 epoch 严重欠训**（实测 val_acc=0.00%，

- `--init <weights.json>`：从已有权重**热启动**。任一不一致（格式 / 版本 / `hidden` /
  类别顺序 / 字段长度）都**直接报错退出**——静默退回随机权重是最坏结果：
  看着像「加训」，实际是重训，而且不会有人发现。
- `--freeze-backbone`：冻结三层卷积、只训 `fc` 与两个头。真机样本常只有几十条，
  全量微调会把预训练视觉特征冲掉（灾难性遗忘）；冻结骨干只让「决策头」适配新数据更稳。
- **血缘可追溯**：产物 `meta` 记 `parent` / `parent_val_acc` / `parent_samples`，
  外加 `epochs` / `lr` / `batch` / `seed` / `git_commit`，满足 DEVELOPMENT_PLAN §7 的要求。

**`val_acc` 的边界**：校验集小或类别极不均衡时它会被众数类主导——**只能判断「有没有在学」，
不能当能力指标**。见 §9.6 的 mode collapse 实测。训练器现已把可解释性内建：每次训练先打印
**类别普查**（原始 kind → 学生类、每类样本数）、**空类清单**、**分层切分**、**多数类基线**

### 11.15 ✅ nrc 首次真机加训：链路闭环 + 三条实测结论（2026-09-13）

先修掉两个**会静默污染示范数据**的 bug，再采集干净数据加训——否则训出来的学生会
模仿错误行为，且**没有报错、看不出来**：

1. **`KindName` 漏 `ActionPress`**（`internal/dataset/demo.go`）：战斗里按技能/聚能
   走的是 `ActionPress`，原实现没这个分支，落进 `default` 记成 `kind=none`。
   后果：老师正确的「聚能/放技能」被记成「发呆」，学生学到的是**反面样本**。
   已补 `ActionPress → "press"`，并加**反向白名单断言**（`TestKindName` 遍历所有
   可录动作，任何一个落 `none` 就报错），防止以后加动作类型时再静默丢。
   `trainer/train.py` 的 `map_action` 同步认 `press`（kind 由 Go 侧决定，两边必须一起改）。
2. **`IsBattle` 对整幅亮度不鲁棒**（`internal/game/detect.go`）：原判据是检测带内
   「亮且低饱和」像素的**全局列投影**；背景一亮，列峰被抬高，15% 列阈值就把真圆钮淹没
   → 角色在战斗里推摇杆却被判成大世界，动作空间被抖散（§11.13 二的延续）。
   新增互补判据 `battleByLocalContrast`：只看每个标定位置的**局部对比度**
   （内盘平均亮度 − 外环平均亮度 ≥ 18，默认半径 0.011/0.026），与整幅亮度无关。
   `IsBattle = battleByColumns || battleByLocalContrast`。新增参数在 `battle_detect`
   缺失时**逐个零值兜底**（档案没写也不会退化成「恒判战斗」）。

**诊断证据（8 组对照，`.workbuddy/codex/diag_train.py`，全部可复现）**：

| 配方 | train_acc | val_acc | 验证集预测分布 |
|---|---|---|---|
| A 基线 `video_v1` **不训练**直评真机 | — | **0.00%** | 8 个样本**全预测 `tap`** |
| B `--init` 不冻结 30ep | 11.76% | 12.50% | tap5 / press3 |
| C 从零 30ep | 39.22% | 37.50% | 全 press |
| D `--init`+冻结 30ep（**原跑法**） | 1.96% | 0.00% | 全 `tap` |
| D2 `--init`+冻结 **200ep**（**现采用**） | 49.02% | **50.00%** | press7 / down1 |
| E `--init` 不冻结 200ep | 41.18% | 37.50% | 全 press |
| G 从零 400ep | 60.78% | 37.50% | press6 / down2 |

结论（按可信度排序）：

- **A 是最关键的一条**：`video_v1` 在视频域自称 52.36%，拿到真机帧上直评是 **0%，
  且恒输出 `tap`**。这说明**视频域骨干对真机帧没有迁移价值**（跨域差得太远）。
  因此「`--init video_v1`」在本项目里的真实含义只是**借一个 fc 初始化 + 固定入口**，
  **不是**「站在巨人肩膀上」。要用视频数据，得先解决域对齐（同分辨率/同 UI 布局）。
- **30 epoch 严重欠训**：D（30ep）1.96% → D2（200ep）49.02%，同一配方只差迭代次数。
  小样本冻结骨干收敛慢，别按大模型直觉给 epochs。
- ~~**方向类在单帧观测下本质不可分**~~ → **⚠️ 此结论证据不足，已在 §11.16 推翻**：
  当时看到「所有配方都没把 `up` 学起来，全挤在 `press`/`down`」，据此推断方向信息
  不在单帧里。但 §11.16 查明那 12 个「`up`」训练样本本身就是**错标产物**——
  `map_action` 用子串匹配把 `up_right`(11) 与 `up_left`(1) 一起塞进了 `up`，
  即**两条方向相反的示范被贴上同一个标签**。模型学不会它，是标签矛盾的必然结果，
  不能据此推断「单帧不可分」。该问题需用 12 类头 + 方向覆盖更全的数据重做（§11.16）。
- **8 个验证样本的粒度是 12.5%**：`val_acc` 只能当**趋势**看，不能当能力指标；
  真正的验收标准是「上真机跑一段看行为」。

**采集质量核对**（第二轮示范，59 条落样）：
`move 35 / press 23 / tap 1`，**`none` 完全清零**——第一轮同样的采集是
`none 25 / move 35`（PRESS 全被记成 `none`），对比即是修复生效的直接证据。
示范日志还实测到判据切换正确：`[13/60] ⚔️进入回合战斗态` → 用
`cast_hetu`/`gather_energy` → `[38/60] ⚔️回到大世界探索态` → 继续 `move`。

**本轮新增工具**：
- `cmd/battledbg`：判据诊断器，量测每个标定位置的局部对比度、打印命中数，
  用来在真机上一眼看出「为什么这帧判成 world」。
- `.workbuddy/codex/diag_train.py`（本地脚手架，不入库）：把加训失败拆成
  A/B/C/D/E/F/G 可分别证伪的实验，输出 train_acc / val_acc / **预测分布**（查 mode collapse）。

### 11.16 学生动作空间对齐 L1 的 8 向 + 训练器可解释性加固（2026-09-13）

§11.15 收尾时留了一句「方向类在单帧观测下本质不可分」。**这一节推翻它**：
那个结论的证据不成立，真实原因是**标签错了**。

#### 一、根因：8 向的设计，4 向的实现，子串匹配的标签

三处对不上，且全都不报错：

| 层 | 声称 | 实际 |
|---|---|---|
| `internal/agent`（L1 动作空间） | 8 向 `AllDirs` | 8 向 ✅ |
| `internal/student`（学生头） | 注释写「方向 8 选 1」 | **4 向**（up/down/left/right）❌ |
| `trainer/train.py` 的 `map_action` | —— | 4 向**子串匹配** ❌ |

`map_action` 原实现：

```python
for d in ("up", "down", "left", "right"):
    if d in raw: return d          # raw = "ACTION MOVE dir=up_right dur=1200"
```

`up_right` 会被 `"up"` **先命中**——所以 `up_right` 与 `up_left` 一起被塞进 `up`。
这不是「标签略粗」，而是**把方向相反的示范贴上同一个标签**。

真机示范的实际方向分布（nrc 第二轮 35 条移动）打脸了「4 向够用」的假设：

```
up_right 11 / down_right 23 / up_left 1     ← 全是斜向，没有一条正向前后左右
```

即：**采集到的方向示范 100% 是斜向**，而学生头一个都表达不了。
§11.15 里那 12 个「up」训练样本正是 `up_right(11)+up_left(1)` 被错标合并的产物——
模型学不会一个自相矛盾的标签，是必然，**不能据此推断「单帧里没有方向信息」**。

#### 二、修法：12 类头 + 加载期拒绝 + 训练期普查

1. **学生头扩到 12 类**（`trainer/train.py` 的 `CLS` 与 `internal/student.Classes` 逐项对齐）：
   `up/down/left/right/up_left/up_right/down_left/down_right + tap/press/wait/none`。
   方向类集合与 `agent.AllDirs` 一致，`internal/student/classes_test.go` 用测试钉住
   「L1 的每个方向都能被学生表达」。
2. **标签解析去掉子串匹配**：新增 `parse_dir()`，按 token 归一化（大小写、`-`/空格/`/`），
   认不出就**丢弃**而不是猜。`dir_of()` 同步支持 8 向，并给斜向加了「小分量 ≥ 大分量 40%」
   的门槛——推杆抖动不该把「前」判成「右前」。
3. **加载期拒绝不一致的权重**（`internal/student.Load`）：类别数/集合/顺序任一不符即报错，
   并把**缺失的类名点名**。旧 4 向权重会得到：

   ```
   权重只声明了 8/12 个类别，缺少 [up_left up_right down_left down_right]
   —— 这类权重（多为 4 向旧格式）无法表达 L1 的斜向移动，请用当前 trainer 重新训练
   ```

   刻意选择「响亮失败」而非静默降级：4 向头结构上表达不了斜向，放它过去只会让
   「方向永远学不会」的现象继续存在而无人察觉。
4. **训练器内建可解释性**（每次训练都打印，不再需要事后写诊断脚本）：
   - **类别普查**：原始 `kind` → 学生类、每类样本数、被丢弃的条数；
   - **空类检查**：`CLS` 里任何一类 0 样本 → **默认拒绝训练**（`--allow-missing-classes`
     可强行跑通，空类清单会如实写进 `meta.missing_classes`）；
   - **分层切分**：按类别内比例切 val（每类至少留 1 条在训练集），替掉原来的随机切分
     ——原实现还有 `max(4, ...)` 硬留 4 条 val，59 样本时等于吃掉 7% 训练数据；
   - **多数类基线 + 各类召回 + 验证集预测分布**：`val_acc` 旁边直接摆出「众数类占比」，
     让 mode collapse 一眼可见。

#### 三、真机复采暴露的第三个静默缺陷：逃跑有二次确认弹窗

用脚本化的八向循环去刷方向数据（不依赖老师选方向），第一次跑就卡住了：
40 步里 **25 步在战斗里空蹭**（Δ≈2），全部卡在同一个地方。抓图看到真相：

> 点逃跑钮后弹出「**是否要退出本次战斗？** 否 / 是」——**不点「是」就退不出去**。

于是形成死循环：战斗卡住 → 内部自愈点 `battle_flee` → 停在弹窗 → Δ 依旧很小 →
再判卡住 → 再点逃钮…… 每一步都「执行成功」，日志看起来很正常。

修法：

- 档案新增宏 **`flee_battle`**（`点逃跑钮 → 点确认「是」`，坐标 0.664,0.906 → 0.563,0.761），
  把「有二次确认」这个事实固化在档案里，换游戏只改档案；
- `cmd/helper` 的**战斗卡死自愈改为执行该宏**（原实现只单点逃跑钮，正是卡死的原因）；
  档案没定义该宏时退回单点，保留旧行为；
- `macro_test.go` 新增 `TestFleeMacro_含二次确认`：守卫「第二步必须与逃跑钮不同位置」，
  防止以后有人把它简化回单点。

> 这条与 §11.13 的 `gather_energy` 是同一类问题：**游戏的真实交互步数往往多于
> 「看起来的一个按钮」**。凡是「按了却没用」的按钮，先怀疑是不是漏了确认/展开/结算。

#### 四、结果（同一批 59 条数据，12 类头）

```
nrc_real_v1.weights.json   59 样本 / 300 epoch
  val_acc = 58.33%    多数类基线 = 41.67%   （旧 4 向头：37.50%）
  验证集预测分布: press 10 / up_right 1 / down_right 1
  各类召回: press 1.00 | up_right 0.50 | down_right 0.20
```

两个可验证的进步：

- **预测里第一次出现了斜向类**（`up_right`/`down_right`）。旧 4 向头的预测分布是
  `tap`/`press`/`down` 三选一，永远不可能输出斜向。
- `val_acc` 首次**高于多数类基线**（58.33% > 41.67%），而 §11.15 的 37.50% 是低于基线的。

**但它仍然不是可用模型**：12 类里 7 类是空的（`up/down/left/right/down_left/wait/none`），
`press` 占验证集预测的 10/12。`meta.missing_classes` 里如实写着这个清单。
原因很清楚——这批数据本来就只有 5 类样本，方向覆盖严重不足。

#### 五、方向数据采集的阻塞（如实记录）

要让方向类真正学起来，需要**每个方向都有足够样本**的数据。脚本化八向循环是正路，
但当前所在区域**野生精灵极密**，三五步就触发遭遇战，实测连续三次尝试都被打断
（一次 25 步卡在弹窗、一次采样全挤在 `up_left`、一次恢复后立刻再进战斗）。

下一步需要二者之一：

1. 把角色移到**安全区**（城镇等无野怪区域）再刷方向；或
2. 在 helper 里加一个**纯脚本采集模式**：指定八向序列 → 自动执行 → 每步落样，
   循环时用现有的卡死自愈+逃跑宏自动处理遭遇。

在拿到方向覆盖均衡的数据之前，**方向类的能力结论一律不下**（既不能说「学不会」，
也不能说「学会了」）。

### 11.17 ✅ 脱困传送改用「颜色运行时定位」+ 一次「以为在走路、其实在拖地图」的事故复盘（2026-09-13）

**事故**：角色被困在野生精灵密集区反复被拖进战斗，按档案 `escape` 传送——
连续三轮都没把角色挪走，而日志看起来「一切正常」。

#### 一、为什么三轮都白跑：三个静默缺陷叠在一起

| # | 现象 | 根因 | 证据 |
|---|---|---|---|
| 1 | 步骤 2「点蓝色盾牌」点空 | 盾牌图标的屏幕位置取决于**当前地图的平移/缩放**，坐标是运行时状态不是常量 | 两次采样同一批盾牌 **x 完全一致、y 整体差 ~0.097**（地图被纵向拖过）；点下去 Δ 只有 15，而面板弹出应是 50+ |
| 2 | 点空之后「看起来有反应」 | 在大地图**空白处**点一下 = 放标记，弹出「标记(点击修改名称)」面板 | 抓帧让本地 VLM 读面板标题，读到「标记(点击修改名称)」，而我最初以为是「传送」；那把「黄色按钮」其实是**标记面板的「标记」按钮** |
| 3 | 8×10 秒的摇杆长推**没有让角色移动一步** | 大地图开着时，同样的手势是**拖地图**；Δ 一样有 20 上下 | 静默判据失效 ——「画面在变」≠「角色在动」 |

第 3 条是最贵的一条：它把「角色没动」伪装成「在移动」，Δ=20 看起来完全正常。
最后是靠**对照组**揭穿的：**静止 10 秒 Δ=0.0**（这个游戏画面静止时完全不刷新），
所以 Δ 本是干净的移动信号——但前提是**不在大地图上**。

#### 二、修法：改成「运行时测」而不是「写死坐标」

新增 `tools/teleport.py`（配套 `tools/escape_now.py`）：

```
开地图 → 颜色找蓝色盾牌图标 → 点开 → 点面板底部黄色「传送」→ 验证转场
```

关键判据（都是实测标定，写进 `tools/find_icons.py` 的 `is_anchor` 并被 `teleport.py` 复用）：

- **蓝色盾牌图标**：`B 主导 + |R-G| ≤ 18`。
  这条 `|R-G|` 是**跨地图**能不能用的分界：图标是正蓝（R≈G，实测 rgb≈(72,78,163)），
  而雪地/夜晚地图的地形本身偏青蓝（rgb≈(72,96,149)，**G 比 R 高 23**），
  青色河水更明显（rgb≈(115,183,201)）。只卡「B 主导」时雪地地图会给出 26 个候选、
  最大「图标」面积 10 万像素 —— 拿这个去点就是满地图乱点。
  配合面积上限 600（图标实测 50~400）后，候选回到个位数。
- **面板底部黄色上下文按钮**：同一个位置在标记面板下写「标记」、在庇护所/魔力之源
  面板下写「传送」。所以「点黄色按钮」本身不足以证明点对了，必须**先确认弹出的是
  详情面板**（Δ≥8 且底部出现该按钮），否则就是在放标记。
- **世界态/地图态判据**：米黄占比（大地图 40%~69%，3D 世界 <10%）。
  这是第 3 条事故的守卫——**每段移动前先确认不在大地图上**。
- **传送成功判据**：Δ 突增到 150+、米黄从 ~69% 掉到 <5%、亮度先掉到 ~35 再回升
  （关地图 → 加载 → 新场景）。

另外标定出两条容易踩的交互事实：

- **返回键 / ESC 被游戏吞掉**（实测 Δ=0.0，连按 4 次画面一模一样）。
  关大地图只能点右上 ✕ (0.927,0.045)，**且面板盖住时点它也无效**（Δ 只有 13.9；
  面板关掉后再点，Δ=53.2 一次关掉）。
- 传送落地**不代表安全**：落点是雪原庇护所，落地 0 怪，几分钟后仍刷新出主动攻击的
  野生精灵（啾啾鸟）并进入战斗。脱困 ≠ 免疫遇敌。

## 12. 确定性执行计划（`-plan`）：把「学会的流程」固化，不再让大模型一直盯着

### 12.1 为什么需要它

老师 VLM 单步决策 1~2s，且**每次调用都要花钱**。用它探索未知界面是合适的，
但用它**重复已经学会的流程**既慢又贵。

正确的学习闭环是三段：

```
老师探索（贵、一次性）  →  把流程写进档案 plan（免费）  →  确定性执行器反复跑（零模型）
```

`internal/plan` 就是那个「确定性执行器」：**零训练、零推理、零 API 花费**。

与既有能力的分工：

| 能力 | 谁决定下一步 | 成本 | 适用 |
|---|---|---|---|
| `-demo`（老师示范） | 老师 VLM 逐步决策 | 高（秒级/次） | 探索未知界面、采示范数据 |
| `-student`（量化学生） | 学生 CNN 看画面出动作 | 低（<1ms） | 已训练场景，判「做什么」 |
| **`-plan`（本方案）** | **档案里写死的步骤序列** | **零** | 流程固定的操作（进关、清弹窗、走对话、点结算）|
| 档案宏 `macros` | 仍需要模型决定按它 | 零（执行时） | 一次 PRESS 展开成多步 |

**分界线：下一步做什么如果是确定的，就不该问模型。** 把确定性从推理里拿出来
写进档案，就是省钱的本质。

### 12.2 用法

```bash
# 先把流程写进档案的 plan 段（见 12.3），然后：
go run ./cmd/helper -target android -adb <adb.exe> -serial <设备> -game <档案> -plan -live

# dry-run（默认）：照常解析并按画面反馈推进，但不发送真实输入，用来验证判据是否合理
go run ./cmd/helper -target android -adb <adb.exe> -serial <设备> -game <档案> -plan
```

档案没配 `plan` 段时会明确报错并提示怎么加，不会静默什么都不做。

### 12.3 档案格式

```json
"plan": {
  "name": "清弹窗并进下一关",
  "loop": false,
  "steps": [
    {
      "name": "点继续",
      "action": "ACTION TAP x=0.5 y=0.9",
      "until": { "type": "change", "region": [0.0, 0.1, 1.0, 0.72], "diff": 3 },
      "timeout_ms": 4000
    },
    {
      "name": "连点直到出现装扮界面",
      "action": "ACTION TAP x=0.5 y=0.9",
      "max_repeat": 25,
      "until": {
        "type": "ratio",
        "region": [0.0, 0.76, 1.0, 1.0],
        "color": [233, 42, 127],
        "tolerance": 40,
        "min_ratio": 0.02
      }
    }
  ]
}
```

`action` 语法与老师输出完全一致（`ACTION TAP` / `ACTION PRESS name=..` /
`ACTION KEY code=..` / `ACTION WAIT`），由 `agent.ParseAction` 解析——
**同一个动作词汇表**，档案作者不用学第二套语法。

字段说明：

| 字段 | 说明 |
|---|---|
| `repeat` | 固定连做几次（默认 1） |
| `max_repeat` | **循环模式**：反复执行，每轮判定 until，满足即停，最多 N 轮 |
| `gap_ms` | 重复间隔；无 until 时兼作动作后的固定等待 |
| `until.type` | `change`（默认，画面变了就继续）/ `stable`（画面稳住）/ `ratio`（区域内出现目标色）/ `time`（只等固定毫秒） |
| `until.region` | 只比较这块归一化区域（`[x0,y0,x1,y1]`）。**强烈建议收窄**，见 12.4 |
| `until.diff` | 灰度平均绝对差阈值，默认 4 |
| `until.color` | `ratio` 的目标色 `[R,G,B]`，`tolerance` 默认 40 容差，`min_ratio` 默认 0.05 |
| `until.min_ratio` | `ratio` 正向：目标色占比 **≥** 该值才满足（「某 UI 出现了」） |
| `until.max_ratio` | `ratio` 反向：目标色占比 **≤** 该值才满足（「某 UI 消失了」）。与 `min_ratio` 互斥 |
| `timeout_ms` | 等待超时，默认 3000。**循环模式（max_repeat）下不生效**，由轮数上限控制 |
| `strict` | 超时/跑满轮数是否算失败，**默认 false（宽松跳过）** |
| `when` | **前置条件**：进入本步前判一次，满足才执行本步，不满足整步跳过（幂等化）。只允许 `ratio` |
| `on_timeout` | **超时补偿**：等待超时后依次执行的动作（`;` 分隔多个），再按同一条件等一轮 |
| `comp_retries` | 超时补偿的**轮数上限**（默认 1）。每轮执行 `on_timeout` 后按同一条件重等，全都没等到才走 `strict`/宽松。需配合 `on_timeout`，范围 1..20 |

**`when`：前置条件（2026-09-13 新增）**

plan 是**顺序执行**的，没有「现在在哪一屏」的概念。所以「清残留弹窗」这类步骤在
没有弹窗时**是有害的**：实测在主界面按 `popup_close` 的坐标会直接跳进 MY CLOSET，
把后面所有步骤一起带偏（判据从 7.9% 掉到 0.5%，整份计划全超时）。

`when` 让每步能声明「只在某状态下才做」：

```json
{
  "name": "清残留弹窗（幂等：主界面已干净就跳过）",
  "action": "ACTION PRESS name=popup_close",
  "max_repeat": 6,
  "when":  { "type": "ratio", "region": [0.05,0.235,0.155,0.295],
             "color": [139,1,64], "tolerance": 30, "max_ratio": 0.04 },
  "until": { "type": "ratio", "region": [0.05,0.235,0.155,0.295],
             "color": [139,1,64], "tolerance": 30, "min_ratio": 0.04 }
}
```

语义是**前置条件**（precondition），不是「跳过条件」：

- 进关步骤 `when=「主题页票券条可见」` → 只有还在主题页才点卡片；
- 退出步骤 `when=「结算页 Exit 可见」` → 只有真在结算页才点 Exit；
- 反面情形（幂等跳过）用**否定式**表达，如 `when=「ADS 徽章不可见」`（主界面已干净就跳过）。

> ⚠️ 语义写反是最容易犯的错：早期把 `when` 定成「满足则跳过」，于是退出步骤写成
> `when=「Exit 可见」`就变成了「在结算页就跳过」，实测在非结算页也照样点了一次 Exit。

只允许 `ratio`：前置条件必须依据**绝对特征**（某 UI 在不在）；`change`/`stable` 是
相对量，没有基准帧无从判定，加载时静态校验就报错。

**`on_timeout`：超时补偿（2026-09-13 新增）**

手游的推进经常被**不可控的插屏/激励广告**截断。补一个「等不到就补一手」的兜底，
再按同一条件等一轮：

```json
{
  "name": "点 Change 等结算页",
  "action": "ACTION PRESS name=change",
  "until": { "type": "ratio", "region": [0.36,0.888,0.64,0.935],
             "color": [110,93,236], "tolerance": 20, "min_ratio": 0.6 },
  "timeout_ms": 20000,
  "on_timeout": "ACTION KEY code=back",
  "comp_retries": 4
}
```

`on_timeout` 支持 `;` 分隔的**多个动作**（按序执行）。但 ⚠️ **补偿动作要选无副作用的**：
实测在激励视频**播放中**点屏幕（哪怕点右上角关闭键的坐标）会命中「跳转应用商店」热点，
把游戏带去 Google Play，而且这类广告 Activity 挂在游戏包名下、前台检查拦不住。
所以 Sparkle 的补偿只写返回键（`ACTION KEY code=back`）——它在广告播放层/应用详情页
可关、评审页等于跳过评审，都朝目标前进。

`comp_retries`（默认 1）让补偿可以**多轮**：激励视频的卡法不止一种（播放层、结束页、
应用商店页），单补一次处理不了全部；用安全的返回键周期性补偿则必然收敛，最多几轮
就能等到结算页。真机上广告正常播完，补偿根本不触发。

与 `when` 的分工：`when` 是**事前**守卫（该不该做这一步），`on_timeout` 是
**事后**兜底（做了但没等到结果时补一手）。补偿动作同样走安全检查与重试。

**`max_ratio`：判「某 UI 消失了」**（2026-09-13 新增）

多数推进是「等某 UI 出现」，但有些场景只能靠「某 UI 消失」判断：

- 评审页的进度条消失 = 本局评审结束，可以进结算；
- 加载转圈消失 = 场景切换完成。

这些「离开某状态」的信号用「出现了什么」表达不了。实测反例：Sparkle 结算页
**没有专属颜色**——紫色按钮在结算页占 46%、在 SALE 弹窗的价格按钮上占 54%，
两者根本分不开。判「绿条没了」反而是唯一稳的判据。

```json
{ "type": "ratio", "region": [0.0, 0.78, 1.0, 0.86],
  "color": [77, 224, 114], "tolerance": 40, "max_ratio": 0.005 }
```

**动作尽量用 `PRESS name=<按钮名>`，不要直接写坐标**

`ACTION TAP x=.. y=..` 与 `buttons[].pos` 是**两份坐标**，改一处必然漂移
（2026-09-13 实测踩到：把 `start.pos` 改成 `[0.5,0.784]` 却忘了同步 plan 里的
`ACTION TAP x=0.784`，结果点到卡片区、流程走偏）。

用 `ACTION PRESS name=start` 让坐标只存一份，后端 `Apply` 会经档案解析：

```json
{ "name": "点 Start 进本关", "action": "ACTION PRESS name=start" }
```

### 12.4 ⚠️ 实测数据与坑

**提速效果（实测 2026-09-13/14，MuMu 模拟器 + Sparkle）**

| 场景 | 耗时 |
|---|---|
| 死等固定时长（新手写法） | 4.07s |
| **改为等画面变化** | **973ms** |
| **整份 13 步计划端到端（一局，零模型）** | **110~125s** |
| 整份 6 步计划端到端（早期版本，模拟器广告卡死、4 轮返回键补偿） | ~110s |

> ⚠️ 慢的那几行**不是缺陷**：模拟器无真实广告源、激励视频常卡住，要靠返回键补偿推进；
> 真机广告自行播完、补偿不触发，单局会显著更短。指标统计见 `-plan` 输出的
> 「性能」行（端到端/抓帧/动作下发/安全检查/跳过/重试/失败）。
>
> 📌 **瓶颈在抓帧，不在动作**：13 步跑完 1m50s~2m00s 里，**抓帧占 72~100 次共 92~98s
> （约 1.3s/帧）**，动作下发只有 1.5~1.9s。安卓后端 `exec-out screencap` 是本项目当前的
> 性能天花板；要提速应优先解决抓帧（降分辨率/换 `screencap` 通道），而不是优化动作。

**坑一：`change` 会被插播广告骗过**

实测点「换发型」后 973ms 就判定「画面变化 → 成功」，截图一看是 **Google 广告插播**
（全屏视频），发型根本没变。

> `change` 只能证明「画面动了」，不能证明「我想让它发生的事发生了」。

对策：关键步骤改 `ratio`，或把 `region` 收窄到**只有预期变化会发生的那块区域**
（如只看人物头部，广告全屏也无法触发）。

**坑二：循环的停止条件必须判「出现什么」，不能判「变了没有」**

`change` 在循环里会退化——每轮动作本身就改变了画面，基准帧被自己破坏，
于是第一轮就「满足」退出。所以 `max_repeat` 模式**只允许 `ratio`**，
这在档案加载时静态校验（`plan.Validate`）就报错，不会跑到一半才发现。

**坑三：手游的固定干扰项**

| 干扰 | 处理 |
|---|---|
| 冷启动平台登录（Google Play Games 选账号等） | 固定坐标点「继续」；每次冷启动必现，计划第一步就该清掉 |
| 插屏广告（全屏视频） | 用**无副作用**的返回键补偿推进（`on_timeout` + `comp_retries`）——**别点广告区域**，可能有跳转热点（见坑四） |
| 活动弹窗 / 评级请求 / 竞品试玩 | 关掉，别点「去评分」 |
| 应用切后台 | `am start` 拉回即可，**别用重启**（重启会再触发登录弹窗） |

**坑四：激励广告的关闭必须选「无副作用」的动作，且要允许多轮**

Sparkle 点 Change 触发激励视频后的实测（2026-09-13）：

| 态 | 画面 | 可用动作 |
|---|---|---|
| 播放层 | 全屏视频 | 返回键可关；**点屏幕任意处是「跳转应用商店」热点** |
| 应用详情页 | Google Play 安装页（左上角 X） | 返回键可关 |
| 结束页 | 「Reward granted」+ 右上角 X | 返回键**无效**，只能点 X |
| 评审页 | 底部绿/红进度条（约 13s） | 返回键 = **跳过评审直接进结算** |

三个要点：

1. **补偿只用无副作用的返回键，并且要能多轮**。早期版本用 `back; 点广告X` 两步，
   实测在广告**播放中**点右上角 X 会命中跳转热点，把游戏带去 Google Play——
   而该广告 Activity 挂在**游戏包名下**，`IsForeground(pkg)` 的前台检查**拦不住**。
   改用纯返回键 + `comp_retries` 多轮后，广告/详情页/评审页三种卡法都能收敛到结算页。
2. **补偿动作之间必须留间隔**：若写多动作序列，第一层关掉后第二层**要几百毫秒才渲染**——
   紧接着的点击会落在还没出现的按钮上、点空。引擎固定留 `900ms`（`plan.compGap`）。
3. **真机上补偿根本不触发**：广告正常播完自动回游戏，只有模拟器（无真实广告源）才卡住。

```json
{
  "timeout_ms": 20000,
  "on_timeout": "ACTION KEY code=back",
  "comp_retries": 4
}
```

> ⚠️ **返回键不能当通用「退出」用**。实测：广告播放层/应用详情页=关掉它们回到游戏、
> 评审页=跳过评审进结算、**主界面=无副作用**（仍停在主界面）、
> **结算页=重开一局**（等价 replay）。所以「退出回主界面」只能走紫色 Exit 按钮，
> 绝不能靠连按 back。返回键的安全用法只有「广告/评审」这类必须往前的场景。

> 📌 **本轮端到端实测（2026-09-14，模拟器）**：13 步 / 15 个动作 / 零模型调用，
> 从主界面走完整局并回到主界面。step4 因模拟器广告卡死触发返回键补偿（1m26s），
> 最终仍收敛到结算页——**补偿机制按设计生效**。

> ⚠️ **注意反例：有一类广告/模态页对返回键完全无响应**（实测连按 3 次 BACK，画面
> 逐字节不变）。此时返回键补偿会空转到耗尽，唯一可靠的恢复是
> `am force-stop` + 重新拉起（冷启动约 30s 回到主界面）。所以跑批脚本的
> 「起点校验」不能只靠 BACK/Exit，必须有冷启动兜底。

**坑五：界面判据必须选「该界面独有」的元素，并且要拿整批帧离线验证分离度**

同一份计划里连踩三次，都是「凭一帧印象定阈值」造成的：

| 候选判据 | 实测 | 结论 |
|---|---|---|
| 底部服装卡「白」 | 盘面 48.9%，但**进关入场过渡帧整屏发白**也会判到 100% | ❌ 不可用 |
| 底部 Change 按钮区域（色 `[220,221,232]`） | 盘面 86%，**主界面同位置 96%** | ❌ 零区分度 |
| **盘面中部绿色计分条** | 盘面 **39.0~44.1%**，其余界面最高 **0.87%**（44 倍分离） | ✅ 采用 |

坑的具体后果：`卡片白` 判据在 run12 里 **223ms 就判到 100.0%**（实为白色过渡帧），
于是「等盘面」步提前通过，接着 **item2 被误判为「已结算」而整步跳过**、Change 也被跳过，
整局走向完全不同。

> 方法论：候选判据要在一批历史帧上**批量跑一遍**，看「目标界面最小值」与
> 「其它界面最大值」的比值（分离度）。本项目用 `.workbuddy/sparkle/ui.py` 统一算，
> 一次能扫几十帧。凭单帧印象定的阈值，几乎一定会被过渡帧或近似界面打穿。

**坑六：胜负判定不能用「输赢两侧都出现」的元素** —— 见 §12.6。

**宽松优于严格**：单步超时默认不致命，因为手游插播太频繁，硬失败会让计划
一步都走不完。确实不能容忍的步骤再单独标 `strict`。**但「必须捕获失败」的校验步
恰恰相反**：胜负判定步要 `strict: true`，超时即让计划失败、退出码非 0（见 §12.6）。

### 12.6 ⚠️ 胜负判定：为什么「结算页紫色按钮」判不出来

`-plan` 要能回答「这局赢了没有」。**Sparkle 的结算页有一个致命陷阱：赢和输的页面
长得几乎一样**，紫色按钮的占比实测如下（同区域 `[0.36,0.888,0.64,0.935]`、同色
`[110,93,236]`、容差 20）：

| 画面 | 紫色按钮占比 | 用它判胜负的结果 |
|---|---|---|
| WINNER 结算页 | **93.71%** | — |
| LOSE 结算页 | **93.73%** | ❌ 与 WINNER 差 0.02 个百分点 |

**两帧差 0.02% —— 旧任务书据此把败局判成 PASS。** 根因：紫色 `Exit` 按钮在
WINNER / LOSE 两页都存在且位置重合；所谓「WINNER 真 Exit」其实是 **LOSE 页的 Exit**。

**能区分胜负的是结算页顶部大字**（WINNER 紫蓝色、LOSE 银白色）：

```json
{ "type": "ratio", "region": [0.10, 0.08, 0.90, 0.175],
  "color": [255, 235, 255], "tolerance": 18, "min_ratio": 0.06 }
```

在全部 81 张历史帧上的分布：

| 帧类别 | 顶部大字占比 |
|---|---|
| WINNER 结算页 | **11.21 ~ 14.12%** |
| LOSE 结算页 | **2.21 ~ 2.24%** |
| 主界面 / 主题页 / 关卡盘面 | 0.07 ~ 4.58% |
| 广告播放帧 | 最高 18.16% ⚠️ |

阈值取 **6%**：高于 LOSE 上限（2.24%）2.7 倍、低于 WINNER 下限（11.21%）1.9 倍。

> ⚠️ **该判据只在结算页上有意义**：广告帧可达 18.16%，单独用会被广告误判为胜。
> 工程上靠**步骤顺序**保证——胜负判定步排在「等结算页出现」步之后，此时画面必然
> 是结算页。离线复算脚本同理会先按紫色按钮确认是结算页，再判大字
> （`.workbuddy/sparkle/verify_winner.py`、`ui.py`）。

**判定动作用 `ACTION WAIT` + `strict: true`**：

```json
{ "action": "ACTION WAIT",
  "until": { "type": "ratio", "region": [0.10,0.08,0.90,0.175],
             "color": [255,235,255], "tolerance": 18, "min_ratio": 0.06 },
  "timeout_ms": 8000, "strict": true }
```

`strict: true` 让「等不到紫蓝大字」直接变成**计划失败、退出码非 0**——于是
**胜率可以直接从进程退出码统计**，不需要人工看图。两条边界必须记住：

1. **只等不动**：`ACTION WAIT` 不会在结算页误点任何按钮；
2. **`strict` 不能滥用**：只给「必须捕获失败」的校验步加。循环步（`max_repeat`）
   绝不能加——手游上「循环跑满」是常态，加了会把正常局面判成失败。

**实测证据（同游戏、同一结算页结构、两次独立运行）**：

| run | 旧判据（紫按钮 ≥80%） | 新判据（顶部大字 ≥6%） | 真实结果 |
|---|---|---|---|
| run6 | 93.7% → **PASS（错）** | — | 实际是败局 |
| run7 | 93.73% → PASS（错） | 2.24% → **判负** ✓ | 败局（退出码 1） |
| run12 | 93.7% → PASS（错） | 2.2% → **判负** ✓ | 败局（退出码 1） |
| run20 | 93.74% → PASS（错） | 2.24% → **判负** ✓ | 败局（退出码 1） |

> 「判据能捕获败局」这条验收，靠的是 run7/12/20 **退出码非 0 + 终态帧独立复核**
> 两条证据同时成立，而不是只看计划自己打印的结论。

### 12.7 关卡盘面的「装备」与胜率

早期版本的计划从不点服装卡、直接提交，胜率恒为 0——**这是「不能只看流程跑通、
要看真实结果」的一个实例**。实测机制：

- 角色进关时**只穿内衣**（裸装）；
- 关卡盘面底部有 **3 张服装卡**（x 中心 `0.272 / 0.5 / 0.728`，y 中心 `0.862`，
  卡片行 `y∈[0.815,0.910]`），**点它 = 给角色穿上该服装**；
- 点完 1~2 张卡后**盘面会自行消失、直接进评审页**，此时 `Change` 步会被 `when`
  守卫跳过，必须另有一个「等结算页出现」的步骤把评审/广告等过渡态等过去
  （见档案里第 10 步）。

> ⚠️ **游戏本身仍有随机性**：既有「点了卡却 LOSE」也有「没点卡反而 WINNER」的
> 记录。所以胜率必须**跑批统计**（`batch.sh`，起点不在主界面记 `SKIP_START` 不计入），
> 不能用单局结果下结论。

跑批结果见 §12.8。

### 12.8 跑批实测：真实胜率与「赢不了」的根因（2026-09-14）

**结论先行**：`-plan` 把一局的**流程**跑到零失误没问题，但**打赢不是执行问题**。
两轮共 **20 局真机跑批 → 6 胜 14 负（合并胜率 30%）**，且**败局的装备步与 Change 步
全部执行过**（动作失败 0 次）。⇒ 判据②（连续 ≥10 次 WINNER ≥80%）**未达成**，
根因在**决策/内容层**；且**两轮胜率 40% ↔ 20% 的剧烈波动本身就是证据**——
胜负主要由「随机出的主题 vs 固定点的服装卡是否匹配」决定，执行层无法左右。

**第一轮 10 轮跑批（run21–run30，脚本 `.workbuddy/sparkle/batch.sh 10 21`）**

| 项 | 结果 |
|---|---|
| 计入轮数 / `SKIP_START` | 10 / 0 |
| **WINNER** | **4**（run24 / 26 / 28 / 29）|
| **LOSE** | **6**（run21 / 22 / 23 / 25 / 27 / 30）|
| **胜率** | **40.0%** |
| 终态回到主界面 | **1/10**（仅 run29）|

6 局败局都是「第 12 步（胜负判定，顶部大字 ≥6%）条件超时」——结算页大字实测 2.2%，
是 LOSE 页（§12.6 判据成立），退出码全部为 1。

**第二轮 10 轮跑批（run31–run40，脚本 `.workbuddy/sparkle/batch.sh 10 31`，
用于验证坑七/坑八的修复）**

| 项 | 结果 |
|---|---|
| 计入轮数 / `SKIP_START` | 10 / 0 |
| **WINNER** | **2**（run35 / 39）|
| **LOSE** | **8**（run31–34 / 36–38 / 40）|
| **胜率** | **20.0%** |
| 终态回到主界面 | **2/10**（run35 / 39，均为胜局）|
| **合并（两轮 20 局）** | **WINNER 6 / LOSE 14 → 胜率 30.0%** |

第二轮验证了两处修复：**坑七**（统计口径）——`batch.sh` 现在按**步名**读判胜步结论，
8 局 LOSE 全部记账正确、2 局 WINNER 不再被误记为「未判定」；**坑八**（SALE 弹窗）——
2 局胜局都**干净回到主界面**（`[终态校验] 已回到主界面 ✓`），兜底步生效。

> **运维观察**：LOSE 局 `strict` 判胜步失败后计划终止，设备**停在 LOSE 结算页不回主界面**
> （这是「因输而失败」的预期终态）。⇒ 跑批脚本每轮起点都要先**恢复**：先试轻量点 Exit，
> 不行再 `am force-stop` 冷启动（约 30s）。这使单轮实际耗时 ≈2 分钟。若要让 LOSE 局也
> 自动回主界面，需在 plan 引擎支持 `on_failure` 终态步后再加，当前由跑批脚本兜住。

#### ⚠️ 坑七：统计口径也会说谎——「胜局」在日志里长什么样

第一版 `batch.sh` 用 `grep -F '占比>=6.0%'` 从日志里捞判胜行，结果**4 次胜局全被记成
「未判定」，胜率被算成 0%**。根因：plan 日志里一步**成功**时只打印

```text
step <步名>: none —— 条件满足（1.483s）
```

**判据描述（`区域出现 RGB(...) 占比>=6.0%`）只出现在「等待中 / 条件超时」行**，
成功行根本不含它。⇒ 判胜负必须**按步名**匹配（步名在成功行与超时行里都出现），
且步名从档案现读——`.workbuddy/sparkle/verdict_key.py` 取档案里唯一的 `strict` WAIT 步名。
修正后离线复算 run21–run30 得 WIN=4 / LOSE=6，与逐帧人工核对一致。

> **方法论**：这和 §12.4 的「跑完≠成功」是同一类错误的两个面——那次错在**判定顺序**
> （`strict` 默认 false + 末步 `when` 被跳过 → 假成功），这次错在**结果行的措辞**。
> 任何「从日志/输出里提取结论」的脚本，都要先拿**已知正反例回放**验证一遍再用。

#### ⚠️ 坑八：胜局点 Exit 后被 SALE 弹窗挡住

4 局胜里只有 1 局（run29）干净回到主界面，其余 3 局停在**全屏 SALE 内购弹窗**上
（深色角色立绘 + 紫色「3800」钻石按钮，实测该紫色按钮正落在结算页 Exit 判据区内，
被读成「紫Exit=25%」）。ADS 红标被遮住 ⇒ 「已回主界面」判据不成立 ⇒ **终态不达标**。
兜底：档案新增**末步**「胜局回主界面兜底」——ADS 不可见时连点右上 ×（最多 6 轮）。

#### ⚠️ 更正：「换装 = 必胜」不成立

§12.7 早期记录过人工探针的「不换装必输、换装必赢（5/5）」。**跑批推翻了它**：
6 局败局的执行轨迹里**装备①②③与 Change 全部执行、动作失败 0 次**，照样 LOSE。
⇒ 换装只是**必要不充分**条件；本作胜负含**内容/随机成分**（要选到与主题匹配的造型——
关卡盘面顶部有 `Level N / 地名`、装扮界面有 `Style Tips` 主题风格），
**确定性 plan 保证不了「选对」**。

#### 判据②的结论与建议

| 判据 | 现状 | 证据 |
|---|---|---|
| ① 端到端含终态校验跑通 ≥1 次 | ✅ | run29 / 35 / 39：胜局 + 独立抓帧确认回到主界面 |
| ② 连续 ≥10 次 WINNER ≥80% | ❌ | 两轮实测 40% / 20%（合并 30%）；失败全部止于第 12 步大字判据 |
| ③ 抓帧失败必须重试 | ✅ | batch 起点抓帧失败重试；plan 内 P0 安全检查 / 动作重试 |
| ④ README 补章节 | ✅ | 本节 |
| ⑤ 判据能捕获败局 | ✅ | 14 局 LOSE 退出码均为 1，终态帧独立复核为 LOSE 页 |

**判据②与游戏类型不匹配**：Sparkle 是**换装评分对战**，「赢」由**装扮内容**决定，
属框架的**决策·策略层**；`-plan` 属**执行层**，只能保证「同样的选择每次执行到位」。
把「打赢」写成 `-plan` 线的收尾判据，等于让执行层背决策层的 KPI。

⇒ **建议**：Sparkle 的 `-plan` 线以 **①③④⑤** 收尾，**②改判为「胜负判定正确 ∧ 败局可捕获
∧ 终态正确」**（现状合并 30% 胜率作为**基线**如实记录，不粉饰）；若要「稳定打赢」，
需在**决策层**另做（读 `Level / 主题 / Style Tips` → 选卡），不在本线范围。
**下一款 `-plan` 游戏选型**：优先选**胜负由操作决定**的游戏（节奏 / 反应 / 固定解法类），
否则同样会在判据②上卡住。

> **跑批证据**：逐轮明细（run21–run40 的胜负 / 退出码 / 终态 + 判据分离度复算）见
> `outputs/game-sensei-sparkle跑批报告.md`；脚本与抓帧留证在 `.workbuddy/sparkle/`。

### 12.9 远程 ADB（217 上的安卓模拟器）：接入方式与单局耗时构成（2026-09-14）

把模拟器装到远程机器上跑，可以减少本机占用。接入方式与实测数据如下。

**接入（一次 connect 即可，不需要额外的端口转发）**

```bash
adb connect 192.168.50.217:16384        # MuMu 系默认 adb 端口；7555 也监听同一实例
adb -s 192.168.50.217:16384 shell wm size
go run ./cmd/helper -target android -game sparkle \
  -serial 192.168.50.217:16384 -adb "<adb 路径>" -plan -live
```

- 设备身份：指纹 `Samsung/a52xq/a52xq:15/V417IR/972`（**V417IR 是 MuMu 内部版本号**，
  机型伪装成三星 SM-A5260）、Android 15、**900×1600 / density 240** —— 与 Sparkle 现场一致。
- `16384` 与 `7555` 是**同一个模拟器实例**的两个监听端口（`adb devices` 里会列出两条）。
- ⚠️ **每个 shell 会话都要先 `adb connect`**：Git Bash 里 adb daemon 会随 shell 退出被回收，
  新会话的 `adb devices` 是空列表（TCP 设备不持久化），helper 会报「未发现设备」。

**抓帧方式的实测差距（900×1600，同一时刻同一画面）**

| 方式 | 单帧耗时 | 说明 |
|---|---|---|
| `adb exec-out screencap -p`（**helper 实际使用**） | **517~548 ms** | 二进制直出，不做换行转换 |
| `adb shell screencap -p` + `adb pull` | **1330~1425 ms** | 多一次落盘 + 二次传输，**慢 2.5 倍** |

⇒ 排查性能时**不要**用 `shell + pull` 取样，会得到偏慢 2.5 倍的错误结论。

**单局耗时构成（同一档案版本内可比的一对）**

| 局 | 端到端 | 抓帧次数 | 抓帧耗时 | 占比 | 第 10 步（等结算页） | 第 13 步（点 Exit） | 结果 |
|---|---|---|---|---|---|---|---|
| run41（旧档案） | **117 s** | 115 | 93.4 s | 80% | 86 s | 2.4 s | WINNER |
| run46（新档案） | **87 s** | 72 | 57.9 s | 67% | 40.2 s | **0.57 s** | WINNER |

> ⚠️ **本表的结论已被 §12.10 推翻，保留作过程记录**：两局的「WINNER」都是**假成功**
> ——跑完后设备停在结算页、并未回到主界面。第 10 步并非「白等」，而是需要等 30~100 s
> 的评审阶段；把它缩短只是**更早失败**，反而让胜负判定落到评审页上造成误判。
> 单局耗时对比的正确口径见 §12.10。

- **端到端 −26%，抓帧次数 −37%**。动作下发全程只占 1~2%（1.4~2.6 s），
  安全检查 16~25 次，动作重试 / 失败均为 0。
- **瓶颈 100% 在抓帧**，不在动作、更不在模型（`-plan` 全程零模型调用）。
  抓帧成本 = 设备端 `screencap` + PNG 编码（模拟器 CPU）+ TCP 传输 + Go 侧 PNG 解码。

**本轮修掉的三处耗时硬伤**

1. **第 10 步 `timeout_ms` 25 s → 5 s**：实测同一画面下紫色判据连续 86 s 恒为 0.0%，
   每轮 25 s 纯属白等。⚠️ **「缩短 = 提速」的推论已被 §12.10 推翻**：该阶段是评审动画在
   循环、自然耗时 30~100 s 且 **BACK 无法跳过**；缩到 14.4 s 预算只是「更早失败」，
   会让胜负判定落到评审页上造成**假 WINNER**。现档已改为**单次等 100 s + 不配任何动作**，
   「结算页有没有出现」的硬门禁交给下一步 `strict` 的 No,thanks 步。
2. **第 13 步判据改「结算页紫色 Exit **消失**」（`max_ratio 0.1`），不再等「ADS 红标出现」**：
   胜局点 Exit 后随机弹的全屏 SALE 弹窗**恰好盖住 ADS 红标**，用 ADS 判据时该步连续 4 轮
   判 0.0%、空等 **48.9 s**（run42/43 复现两次）；改用「Exit 消失」后与弹窗无关，
   **1~2 s 即命中**，弹窗交给下一步清理。
3. **第 3 步 `max_repeat` 3 → 1**：实测点 3 轮画面毫无变化（变体①点卡只「选中」、
   票券条恒在 62.6%），白等约 8 s，进关实际由下一步的紫色 Start 完成。

**三个新坑（本轮实测，都已写进档案/本条）**

1. ⚠️ **改 `internal/game/profiles/*.json` 必须重新编译**：档案走 `go:embed` 打进二进制，
   只改 JSON 不 `go build`，跑的还是**旧档案**（本轮 run42/43 因此白跑了两次，
   日志里仍是旧的 25 s 超时与 ADS 判据）。要免编译调试，可在工作目录放
   `profiles/<名>.json` 覆盖内置（`profiles/` 目前只有 `jieyou.json` / `nrc.json`）。
2. ⚠️ **主界面上的模态弹窗会「暗化」ADS 红标**，使 `[0.05,0.235,0.155,0.295]` 的
   ADS 判据实测 0.0%（如「5 星评分」弹窗，红标 `(139,1,64)` → 约 `(97,1,45)`，
   色差 ≈46 > tol 30）。后果：**起点检测与清弹窗步一起失灵**。该弹窗的 × 在
   `[0.828,0.328]`，与 SALE 弹窗的 ×（`[0.85,0.185]`）**不是同一个位置**，
   故新增按钮 `popup_close_alt`，并在第 1 步用 `on_timeout` 两个动作交替点
   （`ACTION PRESS name=popup_close_alt; ACTION PRESS name=popup_close`）。
   注意 `step.action` 只支持**单动作**，多动作序列仅 `on_timeout` 支持（`;` 或换行分隔）。
3. ⚠️ **该模拟器有真实 AdMob 广告**（实测前台会停在
   `com.yoyaworld.sparkle/com.google.android.gms.ads.AdActivity`），不是此前假设的
   「无广告源」。因此清理阶段**必须用返回键**（广告页/主界面均无副作用）；
   点 `popup_close` 的坐标在广告页可能命中「跳转应用商店」热点。第 14 步已改为
   返回键循环（执行时已离开结算页，不会触发「结算页 BACK = 重开一局」）。

**单局操作要点（跑多局时）**：每局起点须为**干净主界面**（判据：ADS 红标 ≥4%；
用 `.workbuddy/sparkle/` 下的取色脚本核对）。若停在结算页/广告页，先按返回键，
必要时 `am force-stop` + 冷启动（≈20 s）。**游戏状态残留会破坏 plan 的起点假设**：
实测在异常状态下点 Start 会**直接进评审页**（跳过换装盘面），此时装备步全部
`前置条件不满足`、绿条判据 0.0%，整局空转。

### 12.10 ⚠️ 推翻 §12.9：所谓「单局提速 26%」是**假成功**；点服装卡后真正发生了什么（2026-09-14 晚）

§12.9 把 run41(117 s) → run46(87 s) 当作提速证据，并据此把第 10 步的 timeout 一压再压
（25 s → 5 s → 1.2 s）。**这个方向是错的**。本轮用「判据离线复算 + 屏幕实时采样」把那段
黑箱打开，结论如下。

#### 一、怎么发现的：两个「看起来对」的结果对不上

| 局 | 端到端 | 退出码 | 独立终态校验（ADS 红标 ≥4% = 已回主界面）| 结论 |
|---|---|---|---|---|
| run46（旧档 5 s） | 87 s | 0 | **不在主界面**（停在结算页）| ❌ 假成功 |
| run47（timeout 1.2 s） | 74 s | 0 | **不在主界面**（紫 64% 结算页）| ❌ 假成功 |
| run48（本轮新档） | 134 s | 0 | 不在主界面（漂成"新一局"）| ❌ 步 14 有 bug |
| run49（本轮新档） | 115 s | **1** | 不在主界面 | ✅ **LOSE 被正确捕获** |

「退出码 0 + 设备停在结算页」= plan 宣称跑完、其实没跑完 ⇒ **之前统计的成功率里混着假 WINNER**。
这也是「20 局合并胜率 30%」必须重测的原因。

#### 二、屏幕实时采样看到的四条硬事实

方法：`diag_step10.py` 用与 `internal/plan/plan.go` 的 `colorRatio` **等价**的逐通道
Chebyshev 判据逐帧采样；`repro_step10.py` 负责「恢复到主界面 → 驱动进关 → 点服装卡 →
逐帧记录」。

1. **点 1~2 张服装卡后，游戏会自行跳过 `Change` 进「评审阶段」**（中部绿计分条在
   30%→0%→44% 之间循环，约 10.5 s 一轮）。该阶段**自然耗时 30~100 s**：零输入连采 96 s，
   紫色结算按钮**全程 0%**，之后才落到结算页 ⇒ **第 10 步不是"白等"**。
2. **返回键在评审阶段毫无作用**：6 次 BACK 打在评审页上，画面照旧循环、紫色恒 0%
   （与档案 hints 里「评审页按 BACK = 跳过评审」的旧说法**相反**）。
3. **返回键在结算页会「重开一局」**，所以"等不到就猛按 BACK"有**反作用**：BACK 一旦落在
   刚出现的结算页上，就把刚等到的结果打掉（run48 终态漂成新一局：紫 8.2% / 票券条 8.6%）。
4. **点 Exit 后是真实 AdMob 插屏广告**（前台 `com.google.android.gms.ads.AdActivity`，
   实测 ≥10 s）；**广告起来后按 1 次 BACK 即回主界面**（ADS 红标 7.9%）。

#### 三、为什么"缩 timeout"会造出**假 WINNER**

判据离线复算（`verify_winner.py` / `judge_all.py`，900×1600）：

| 画面 | 「顶部大字」判据 | 「紫按钮」判据 |
|---|---|---|
| 结算页 WINNER | 12~15% | 64%（领奖浮层）/ 93.7%（真 Exit）|
| 结算页 LOSE | **2.2%** | 93.7% |
| **评审页（循环期）** | **0 → 8.3%（会漂）** | 0~10% |
| 主界面 | 3.1% | 0% |

胜负阈值是 6%，而**评审页顶部白字会漂到 8.3%，越过 6%** ⇒ 只要胜负判定步在评审页上执行
就会**误判 WINNER**。第 10 步一旦被缩到 14.4 s 预算就必然超时（真实需要 30~100 s），
把胜负判定推到评审页上 —— 这正是 run46/47 假 WINNER 的来路。

#### 五、修正后的实测口径（12 步新档，三局连跑）

| 局 | 端到端 | 退出码 | 独立终态抓帧 | 判定 |
|---|---|---|---|---|
| 1 | **97 s** | 0 | 紫 93.7% / 大字 **13.6%** | ✅ WINNER |
| 2 | **83 s** | **1** | 紫 93.7% / 大字 **2.2%** | ✅ **LOSE 被捕获** |
| 3 | **114 s** | **1** | 紫 93.8% / 大字 **2.3%** | ✅ **LOSE 被捕获** |

- **终态全部 = 结算页真 Exit 态**（紫 ≥0.8，即档案设计的终点），可独立复核；
  大字判据 13.6% vs 2.2/2.3% 分离清晰 —— 这一批判定**可信**（对比 §一 的两个假 WINNER）。
- **单局真实 83~114 s**（旧口径 87 s 是"提前放弃 + 判在评审页上"换来的假数值）。
- **提速方向不在缩短等待**（过渡动画时长是游戏定的、按不动），而在**抓帧**：
  0.52 s/帧 × 70~90 帧仍占一半以上；要再快只能减少抓帧次数或换更快的取帧通道。
- **成功率**：本批 3 局 1 胜 2 负；旧「20 局 30%」含假 WINNER，须用本档重测才有意义。
