## 一、类型：换装 / 造型评分类（Fashion dress-up & style battle）

**代表游戏**：Sparkle（详见 ima 知识库 `Sparkle-新手教程流程与界面实测笔记`、
`Sparkle-关卡体系与任务经济实测笔记`、`Sparkle-剧情主线与评分机制实测笔记`）

### 1.1 核心循环

```
选主题  →  按主题从候选部件中挑一件  →  提交  →  评委/进度条反馈  →  结算
   ↑                                                                    │
   └────────────────── 下一轮 / 下一关 ←───────────────────────────────┘
```

### 1.2 三条类型特征（跨游戏稳定）

1. **无自由移动**
   没有摇杆、没有方向键，屏幕不存在「角色位置」这一状态量。
   → **动作空间塌缩为纯点击**，不需要 MOVE / SWIPE / JOYSTICK。

2. **决策本质是「按主题排序候选」**
   给一个主题（场景/风格/场合），给 2~3 个候选，挑匹配度最高的那个。
   隐藏变量是「**部件 × 主题的匹配度**」，这是该类型的唯一核心决策。

3. **反馈分强弱两层**

   | 层级 | 载体 | 特性 | 用途 |
   |---|---|---|---|
   | 弱信号 | 评委文字评语 | 模糊、正向/中性词、无分数 | 语义理解、氛围判断 |
   | 强信号 | 进度条 / 分数 / 星级 | 连续、可量化、即时 | **作为 reward** |

   → **做 reward 一律优先用强信号**，不要试图把评语文本量化。
   → **进度条的颜色常直接编码极性**（实测：绿 = 领先，橙/橙红 = 落后），
   可先做二值化（绿=+1 / 橙=-1）再谈连续量；颜色比长度更稳、更好识别。

4. **奖励随关卡递增 + 新手局加成**
   实测同一游戏内单局收益逐关上升，且**新手首局给得特别多**。
   → 采集样本时别用第一局推算稳态收益。

### 1.3 物品的属性结构

部件通常是**二维属性**，不是一维：

```
部件 = 款式（shape/style） × 颜色（color/palette）
```

同款可换色，且颜色往往也参与主题匹配。
→ 感知层要为「款式」与「颜色」分别建表示，不能只当作一张图。

### 1.4 对抗性选秀（draft）—— 不要当成单人评分

这类游戏很容易被误判为「单人评分」：给几个候选，挑最好的，加分。
**实际多数是零和对抗**：

```
给 N 个候选  →  我选 1 个（归我）  →  对手拿走剩余里最好的那个
```

实测形态：3 个候选，我选走青蕾丝裙后，对手**立刻穿上**剩下的黑哥特裙
（未选中的选项不会保留）。

**策略含义（决策层必须体现）**：

- 目标不是「选一个高分的」，而是**「抢走对手最想要的那件」**
- 选错时对手直接起飞 → **进度条会立刻掉**，这是最灵敏的负反馈
- 因此 reward 是**相对量**（我 vs 对手），不是绝对分

→ 决策模型要拿**对手状态**做输入，不能只看自己。

### 1.5 多级评分（星级）—— 「满足需求」只是必要条件

除了「赢/输」二值结算，这类游戏还有**多级评分结算**（实测 1~3 星 + 评语标题）。
决策时**最容易踩的坑**是把界面上的「需求勾选」当成高分保证：

**实测控制变量实验（同一关，只改发型）**：

| 组 | 发型 | 服装/鞋 | 需求勾选 | 星级 |
|---|---|---|---|---|
| A | 披肩长发 | 金色礼服 + 金高跟 | ✅ 已打勾 | **1 星（So-So）** |
| B | 正式盘发 | 金色礼服 + 金高跟 | ✅ 已打勾 | **3 星（Unbelievable）** |

**结论（跨游戏通用）**：

- 界面上的「需求/Tips 勾选」是**必要非充分条件**——它只表示「至少有一个部件命中该标签」，
  **不代表整体协调**。两组都打勾，星级却差 2 星。
- 星级由**全部部件的整体匹配度**决定，单个部件权重不等（实测**发型/轮廓**权重很高）。
- → 自动化策略：**先把勾选拿满（约束满足），再优化星级（整体协调）**，两者是两层目标，
  不要用「勾选已满足」就停止优化。
- 信号层级：星级（离散、确定）= reward 主信号；勾选（二值）= 约束检查；评语文本 = 归因解释。

### 1.6 一款游戏可能有多条并行主线，奖励结构不同

**不要假设一款游戏只有一条主线**。实测同一款换装游戏有两条独立主线：

| 主线 | 形态 | 结算结构 | 奖励 |
|---|---|---|---|
| 对战/竞技线 | 选主题 → 对指定对手 | **赢/输二值** | 固定货币 |
| 剧情/任务线 | 逐格推进 → 换装 | **1~3 星多级** | 分级奖励 |

**自动化含义**：

- 两条线**可能共用同一套操作 UI**（如共用换装工坊），但**结算反馈结构完全不同**。
- 必须先判「**当前在哪条线**」，否则会拿二值逻辑去套星级界面（或反之）。
- 剧情线常用「**角色头像在地图上逐格移动**」作为唯一进度指示，
  头像旁的**关卡号牌** = 当前可玩关卡；通关后头像前移一格。

### 1.7 通用适配要点

- **档案只配 TAP**。给点击类游戏配 move，会让老师模型无限重复 MOVE
  （动作熵极低——在点击类游戏里 MOVE 是无效动作，模型却会抓着不放）。
- **感知重点**：
  1. 当前界面态（几个稳定态可枚举）
  2. 候选件数量与各自热区
  3. 顶部进度条长度（reward 来源）
- **每步先判弹窗，再判主流程**。这类游戏弹窗密度高，漏判必卡死。

## 二、跨类型的通用操作模式

以下模式在多个类型的游戏中反复出现，属**通用能力层**，可直接复用。

### 2.1 弹窗处理（高优先级）

休闲/移动游戏的弹窗密度远高于 PC 单机。实测在一局新手流程内可连续遇到
4 种不同弹窗：服务条款、插屏广告、评分请求、新主题推广。

**处置原则**：

1. **每步动作前先做弹窗检测**，命中弹窗时优先关弹窗，不推进主流程。
2. **不要为每种弹窗写死坐标**。它们的关闭按钮位置各不同（实测 y 跨度 0.20~0.35，
   x 跨度 0.83~0.96），但**形态高度一致：右上角一个圆形 ×**。
   → 应识别「圆形 × 图标」这一视觉模式，而非枚举坐标。
3. **插屏广告是特例**：它由广告 SDK 全屏接管，关闭按钮位置由 SDK 决定
   （实测在 (0.958, 0.023)），通常比游戏内弹窗更靠角。建议单独建一个
   「广告关闭」识别器。
4. ★**广告必须先等播放完才关得掉**。实测：点右上角 × → 等 7 秒 → 截图**仍是广告**
   （画面在播动画）；再等 6 秒后点 × 才成功。
   **同一支广告还会重复出现**（实测同一支插屏出现 2 次）。
   → 自动化对策：**关闭广告必须重试**——点 × 后截图复检，若仍判为广告页，
   等 3~5 秒再点一次，**最多重试 3 次**。绝不点一次就认定关掉了。
5. **弹窗形态**：实测 6 种——服务条款、插屏广告、评分请求（5 星）、新主题推广、
   **Google Play 应用安装广告**（全屏、底部「安装」、右上角 ×，关闭行为同第 4 条）、
   **竞品游戏试玩广告**（同类产品导量，关闭按钮为 `Skip video` 或右上角跳过图标）。
6. **弹窗关不掉的兜底顺序**：先试右上角带状搜索区 → 再试点击空白区 →
   若是模态面板则用**返回键** → 最后考虑把游戏**拉回前台**。
   - **返回键**：有退出游戏的风险，别第一时间用；但对**模态面板**（如历史记录/设置页）
     往往**是唯一可靠**的关闭方式（实测点空白、点原按钮都无效）。
   - **拉回前台（对付试玩类广告的杀手锏）**：
     `adb shell am start -n <包名>/<主 Activity>`（Unity 游戏主 Activity 名可在
     `dumpsys window` 的 `mCurrentFocus` 里读到）。
     → 广告 activity 若**永不自动结束**（实测试玩广告卡住不退出），
     直接把游戏主 Activity 拉回前台，**不丢游戏内进度**。

### 2.2 点击类游戏的档案收敛

| 若游戏… | 档案应… |
|---|---|
| 无自由移动 | **不配 keys / move** |
| 纯点击交互 | 只保留 TAP（+ 必要时 PRESS） |
| 有拖拽/缩放 | 才开 SWIPE / ZOOM |

> 反面教材：给纯点击类游戏配上移动键，会直接导致老师动作分布退化。

### 2.3 货币与刷取节奏识别

进入一款新游戏后，**先测「单局收益 / 关键商品价格」**，即可量化刷取成本。

- 记录：单局固定收益、主要商品价格
- 推导：需要多少局才买得起 → 判断是否存在体力/次数限制
- 用途：规划采集样本量（要跑多少局才能覆盖足够的界面状态）
- **「能否无限刷」的实测判据**：连续跑 4~5 局，观察是否出现
  体力条递减、冷却倒计时、或「次数不足」提示。
  若钻石只增不减且无障碍 → 判定**无限制**，可连续采集（对训练样本是利好）。

### 2.4 数值/资源面板的固定读法

移动游戏普遍在三处放资源：
- **左上**：玩家身份（头像、昵称、等级）
- **右上**：硬通货余额（货币、体力）
- **右侧竖排**：功能入口（邮件、商店、相机、地图、通知）

→ 新游戏进场先扫这三处，能快速建立 UI 骨架认知，比逐屏试探快得多。

### 2.5 界面态枚举法（新游戏上手流程）

对新游戏建立认知时，按这个顺序推进最省样本：

1. **走完新手教程**（系统会强制把主要界面过一遍，天然覆盖核心循环）
2. **每步截图存档**，标记状态转移边
3. **回到主界面，逐个点开功能入口**（各截一图）
4. **对高密度区域用网格标定工具读精确坐标**（而不是目测或猜）
5. **跑第二局**，验证状态机是否有未覆盖的分支（如失败结算）

### 2.6 任务 / 订单系统（高频，必有）

休闲/换装/经营类几乎都有「任务列表」，形态高度统一：

```
[角色头像]  任务名                        🔍
           [标签1] [标签2]                 ← 完成条件 = 满足这些标签
           🎁 : 💎 20          [ Accept ]  ← 奖励 + 接取按钮
```

**通用结构特征**：

| 特征 | 说明 | 自动化含义 |
|---|---|---|
| **标签式完成条件** | 要求「穿/带/建出具备某标签的东西」，1~2 个标签 | 需把「标签」纳入物品表示 |
| **刷新倒计时** | 顶部常驻 `Refresh Countdown HH:MM:SS`（实测周期 5~6 小时）| 可预测下一批任务时间 |
| **完成后即消失** | 接取并完成 → 该条从列表移除 | 任务是**消耗性**的，一周期内有限 |
| **奖励分层** | 标签越稀有/越具体，奖励越高（实测 20 → 50 → 120）| 优先做高奖励任务 |
| **底部常留一条锁** | 显示 `Buy VIP to unlock` | 免费玩家槽位被打折（付费点）|

→ 自动化该模块的价值很高：**奖励确定、条件明确、可重复**，比自由探索更容易做出稳定收益。

### 2.7 结算页的「看广告翻倍轮盘」

多数休闲游戏在结算页放一个**倍率轮盘 + 看广告按钮**：

```
       💎 base            ← 基础奖励
  ╭─2x─┬─3x─┬─4x─╮
  │    │    │    │        ← 彩扇标注倍率（实测 2x/3x/4x/5x）
  ╰─5x─┴────┴────╯
    [ ▶ 💎 N ]            ← 按钮上直接写「看了实得多少」
     No,thanks            ← 放弃，只拿基础
```

**识别要点（通用）**：

- 该界面的**基础值**就是关卡固定收益；按钮上的数字 = 加成后的实得
- 这是**免费玩家获取硬通货的主要途径**，也解释了「为什么广告这么多」
- 自动化取舍：看广告耗时且依赖 SDK 可用；**采集样本时建议直接 `No,thanks`**，
  保证节奏稳定（实测模拟器上广告 SDK 常初始化失败，会卡住）

### 2.8 关卡选择器（横向轮播）

常见形态：**一排场景卡横向滑动，居中那张被高亮，打的就是居中那张**。

- 卡片正面 = 场景概念图；卡片上有编号或标签
- **★记住上次浏览位置**：下次进入停在离开时那张，不回起点
  → 自动化需**显式把目标卡滑到居中**（可能要滑多次），不能假设从第一张开始
- ⚠️ **别把卡片上的数字当成关卡号**：实测它可能与进入后顶部的 `Level N`
  不一致（主题名对得上、数字对不上）。**以进入后的界面为准，卡片数字仅作参考**。

### 2.9 找失败条件的探测法

想确定「失败长什么样」，不要随机乱试，用**对照实验**：

1. 正常打一局（选最匹配的）→ 记录结算形态
2. 故意选**明显不匹配**的选项 → 看进度条是否变负、结算是否变 LOSE
3. 若单次选错仍赢 → 说明失败需要**连续多轮选错**，或低难度有保底

> 实测：即使选了明显不搭的部件（进度条掉到橙红），最终**仍然 WINNER**。
> 结论要写成「未观察到 LOSE」而非「不存在 LOSE」——**样本不足不下结论**。

### 2.10 复玩 / 重试入口 = 天然的对照实验平台

结算页常带一个**重试按钮**（`again` / `Retry` / `再来一次`），这是研究机制的最佳工具：

- **省掉重复流程**：重试进入后会多出**跳过剧情/对白按钮**（首通通常不允许跳过）。
  实测：首通必须看完全部对白，**重试时才出现右上角跳过键**，一键直达换装环节。
  → 做多组对照实验时，用「重试 + 跳过」能省掉大量重复等待。
- **变量可控**：重试回到**同一关、同一初始条件**，天然满足控制变量的前提。
- ⚠️ 先确认**重试是否消耗资源**（体力/次数/货币），再决定是否大量复玩。

### 2.11 控制变量法测机制权重（研究游戏的标准手法）

要搞清「哪个因素影响结果」，**一次只改一个变量**：

1. 固定关卡与其余所有部件，只改**一个部件**（实测只改发型）
2. 两组各打一次，记录**强信号**（星级/进度条/分数）
3. 差异即该变量的权重证据

> 实测：只把「披肩长发」换成「正式盘发」，星级从 1 星直接跳到 3 星
> → 证明**发型对该主题的权重很高**。
> 反过来，若两组结果相同 → 该变量在此主题下**无关**，可安全忽略。

**注意**：结论只对**该主题/该关卡**成立；换主题要重测（风格匹配是**条件相关**的）。

### 2.12 付费道具是「一次性买断」，不是租用

判断付费道具的经济模型（影响长线策略）：

- 点付费道具 → 弹确认框（`花 N 货币购买？` Cancel/Confirm）→ Confirm 后：
  - **货币真实扣除**（实测 730 → 580，正好 -150）
  - 道具**立即装备并永久解锁**（再次点击不再弹购买框）
- Cancel 则**无任何变化**。
- → 属**买断制**：货币花掉换永久使用权。自动化的经济策略可以「值得的道具买断后长期复用」。

### 2.13 剧情/对白的推进与跳过

视觉小说式剧情（立绘 + 名字标签 + 对白框）的通用交互：

- **推进**：点右下角**向下箭头**（实测 @ ~0.94, 0.86）或点击对白框
- **跳过**：右上角 **`▶|` 跳过按钮**（**仅重试/复看时出现**，首通不可跳）
- **可交互物件**：剧情中会出现**高亮物件**（如礼物盒），需点击才推进
  → 这类"剧情里的小交互"容易漏判，自动化时要检测「非标准对白框」的可点元素

### 2.14 自由移动类：单帧观测分不清「在走」与「顶墙」——把画面变化量喂回策略

**这是有自由移动（摇杆）的游戏最容易被忽略的一类死锁**，与「策略打转」是两种病，用药不同。

- **现象**：决策模型（尤其小 VLM）只看一帧时，**无法区分「正在前进」和「顶着墙/障碍走」**——
  两种情况下画面里都有角色动画、粒子特效在动。模型会因此长期重复同一方向
  （实测出现过**连续 41 步同向**、单步画面变化量掉到 1~3 而无人察觉）。
- **为什么通用兜底救不了**：动作多样性类兜底（「重复 N 步就换个按钮/换个动作」）在此**完全无效**，
  换按钮在顶墙场景里是空操作甚至误触。**移动卡住的唯一出路是换方向。**
- **通用解法（三件套）**：
  1. **把可测的 Δ 回传进提示**：回路本就能算**相邻两帧的画面变化量 Δ**，把它连同
     「连续同向小 Δ 的步数」一起写进决策提示；连续 ≥2 步时为一句显式禁令
     （「禁止再沿原方向走」）。单帧模型看不到的东西，回路替它测。
  2. **兜底按动作种类分流**：移动复读 → **换方向**（挑一个与当前方向不同的方向长推），
     非移动复读 → 才换按钮。两者混用会把「走远」（本就要连续同向）误判成卡死。
  3. **换向再加一道 Δ 闸门**：只有在**确实没挪窝**（Δ < 阈值）时才强制换向。
     否则会把正常赶路打断，把一次直行拆成一路乱拐（实测：8 步固定门限下，
     4/5 次强制换向发生在 Δ 13~19 的正常赶路中）。
- **两级卡死判据要分清**（缺一不可）：

  | 判据 | 口径 | 治什么 | 盲区 |
  |---|---|---|---|
  | 跨窗口 Δ | 当前帧 vs N 步前锚点 | 整段时间世界没动（息屏、加载、角色被钉住） | **「世界在动」不等于「我在动」**——顶墙时角色/粒子仍在动画，压不到阈值 |
  | 相邻两步 Δ | 这一步几乎没挪窝 | 顶着墙持续走 | 单步 Δ 天生小（小步长正常走动也只有 1~2），必须**连续多步**才判定 |

> 实测数据与实现细节见 `README.md` §11.10 / §11.11（判定阈值、日志锚点、校验脚本）。

### 2.15 示范数据采集与学生加训：三类「不报错但白干」的坑

来自 nrc 首次真机加训（2026-09-13，详见 ImA「游戏」库《洛克王国-战斗判据修正与首次真机加训实测》与仓库 §11.15）。
共同特征是**全程没有任何报错**，只能靠采集后核对、或对照实验才能发现。

**坑一：记录层的动作类型漏映射 → 案例标签被静默改写。**
真实示范里「按技能/聚能」走的是一个独立动作类型（如 PRESS），若记录层没有为它建映射，
它会落进 `default` 被记成「无操作」——于是**老师正确的操作被记成「发呆」，
学生学到的是反面样本**。对策：给映射函数加**反向白名单断言**，遍历所有可录动作类型，
任何一个落 `default` 就报错；采集结束**必看类别分布**再训练。

**坑二：界面判据用「全局统计」对整体亮度不鲁棒。**
用「亮像素的列/行投影 + 阈值」判界面态，在背景一变亮时列峰被整体抬高，
阈值把真正的目标淹没 → 判据漏判，动作空间被抖散，而日志上看像「游戏没反应」。
对策：优先用**局部对比度**（目标区域内亮度 − 周边环亮度）这类与整幅亮度无关的量，
并把位置约束保留（只有落在标定位置的才算命中）。新参数要有**零值兜底**，
否则档案缺字段会让判据退化成「恒真」。

**坑三：把「热启动 + 冻结骨干」当成万能加训配方。**
三条实测结论（8 组对照实验）：
1. **跨域热启动没有迁移价值**：在 A 域（如视频抽帧的弱标签）训出的骨干，拿到 B 域
   （真机截图）上直评可能直接是 0%，且恒输出一个类。`--init` 此时只是「借一个 fc 初始化」，
   不是站在巨人肩膀上。**先做「基线不训练、直接在目标域上评估」这一步**，
   再决定要不要热启动。
2. **epoch 别照抄小值**：几十条样本、冻结骨干只训决策头时，30 epoch 可能严重欠训
   （实测 0.00%），同配方拉到 200 epoch 才到 50%。
3. **单帧静态观测学不会方向**：`上/下/左/右` 的区别在**帧间**不在帧内，
   单帧灰度图上这些类本质不可分（实测所有配方都学不起其中一个方向类）。
   这是**架构上限**，调超参无解——要学方向必须换观测（帧差 / 帧对 / 短时序）。

**关于 `val_acc` 的门槛**：验证集只有几条样本时，一个样本就是 10%~25%，
`val_acc` 只能当**趋势**看，不能当能力指标。真正的验收标准是**上真机跑一段看行为**。

## 四、自动化执行层：把「学会的流程」固化下来（跨类型通用）

> 这一节不是游戏知识，而是**工程方法**：怎么让程序学会玩，而不是让大模型一直盯着玩。
> 起因（2026-09-13）：老师 VLM 单步决策 1~2s、每次都要花钱，让它「重复已学会的流程」
> 既慢又贵。正确闭环是 **老师探索（贵，一次性）→ 固化进档案（免费）→ 确定性执行器跑**。

### 4.1 用「画面反馈」代替「死等时长」——提速 5~10 倍

新手写自动化最自然的做法是每步 `sleep 2s`，20 步就是 40s 纯浪费。

改为「**等画面变化就推进**」后，实测同一动作从 4.07s 降到 **973ms**。

| 判据 | 含义 | 适用 |
|---|---|---|
| `change` | 画面相对**动作前**发生变化 | 点完等界面切换（最常用） |
| `stable` | 画面连续两帧不再变化 | 等动画播完 / 等加载结束 |
| `ratio` | 指定区域内**目标颜色**占比达阈值 | 等特定 UI 出现（最可靠，见 4.3） |
| `time` | 只等固定毫秒 | 确实无可观测变化时的兜底 |

**为什么 change 需要「动作前」的基准帧**：动作可能瞬间改变画面，动作后再抓基准
会把变化本身当成基准，导致永远等不到差异。

**阈值经验**：灰度平均绝对差用 **4**（0~255 量级）。太小会被压缩噪声误触，太大则迟钝。

### 4.2 「连点直到出现某界面」需要专门的循环原语

对话推进的条数**不固定**（剧情长短、是否插播广告），写死次数必然要么点不够、
要么白点十几次。必须支持「反复执行 → 每轮立即判定 → 满足即停 → 最多 N 轮」。

**关键约束：循环的停止条件必须判「出现什么」，不能判「变了没有」。**
`change` 在循环里会退化——每轮动作本身就改变了画面，基准帧被自己破坏，
于是第一轮就"满足"退出。所以循环只能用 `ratio`（绝对特征）。
这条要在**档案加载时静态校验**报错，不能跑到一半才发现。

### 4.3 ⚠️ change 判据会被插播广告骗过（实测踩坑）

实测：点「换发型」后 973ms 就检测到「画面变化」并判定成功，截图一看——
是 **Google 广告插播**（全屏视频），不是发型变了。

**教训**：`change` 只能证明「画面动了」，不能证明「我想让它发生的事发生了」。
手游随时会插播广告/活动弹窗，`change` 的成功率会被污染。

**对策**：关键步骤改用 `ratio`（判目标 UI 出现），或把 `region` 收窄到
**只有预期变化会发生的那块区域**（如只看人物头部，不看全屏），让广告全屏也无法触发。

### 4.4 手游自动化的「固定干扰项」清单

按处理方式分类，写档案时逐条准备：

| 干扰 | 表现 | 处理 |
|---|---|---|
| **启动期平台登录** | Google Play Games「选择玩家资料」等 | 固定坐标点「继续/取消」；**每次冷启动必现**，固化计划第一步就该清掉 |
| **插屏广告** | 全屏视频/静态图，带 X 或倒计时 | 等可关闭 → 关闭 → 重试；可能连环弹 |
| **活动弹窗** | 多个位置不固定（绚彩生活/新主题推广…） | 宽松跳过（超时不算失败），靠后续步骤拉回 |
| **评级请求/竞品试玩** | 应用内评分框、"试试这个游戏" | 直接关掉，别点「去评分」 |
| **后台掉帧** | 应用切后台后 `am start` 拉回即可 | 不要用重启，重启会再触发登录弹窗 |

**宽松优于严格**：单步超时默认**不致命**（记日志继续），因为手游的插播太频繁，
硬失败会让整个计划一步都走不完。确实不能容忍失败的步骤再单独标 strict。

### 4.5 计划里该放什么、不该放什么

- ✅ **放**：流程固定的操作（进关、清弹窗、走完对话、点结算）
- ❌ **不放**：需要判断的操作（选哪件衣服、打哪个敌人）——那交给学生模型或规则
- 分界线：**「下一步做什么」如果是确定的，就不该问模型。**
  这也是省钱的本质——把确定性从推理里拿出来，写进档案。

- [ ] 模拟经营 / 种田放置（点击 + 长时等待，奖励随时间衰减）

- [ ] 解谜（状态空间搜索）

### 4.6 ⚠️ 计划执行的「顺序性」局限（实测暴露）

**现象**：为了让同一逻辑界面（主题选择页）的**两种布局变体**都能走通，
计划里写成"先走路线 A（点 Start），再走路线 B（点卡片）"——
因为计划是**顺序执行**的，当前若是变体 B，路线 A 的那一击不会落空，
而是**落到卡片上直接进关**；紧接着路线 B 又点一次，落在关卡内随意位置。
两次「盲点」把流程推歪，插播广告趁机接管屏幕。

**教训**：`-plan` 是**无条件顺序执行**的，它没有「当前在哪一屏」的概念。
所以：

| 能这么做 | 不能这么做 |
|---|---|
| 每步动作在**多数状态下**都安全（幂等点击、清弹窗、点继续）| 用「A 不行就试 B」的兜底写法——两次都会真的点下去 |
| 用 `max_repeat` + `ratio` **循环到某状态出现** | 把互斥的分支写成顺序执行的相邻两步 |

**正确做法**：让每一步的 `until` 判据把「已经到目标态」也涵盖进去。
例如进关这步，判据应为「**已经进入关卡**（物品卡区出现）**或**已离开主题页」，
而不是"点一次 Start、再点一次卡片"。

**边界总结**：适合 `-plan` 的是**单一路径、步骤可幂等**的流程
（清弹窗、走对话、点结算）。一旦流程存在**多分支且分支动作会互相破坏**，
要么把判据做扎实（每步都能自证是否该执行），要么退回让学生模型决策。
**这不是「计划能替代一切」，而是「确定性流程才值得固化」。**
