> 本文件归集**可跨游戏迁移**的类型层知识与操作模式，是 game-sensei 的通用能力资产。
> 对应 `DEVELOPMENT_PLAN.md` §1.1 的「**游戏类型层（可迁移策略）**」。
>
> **归档规则（用户硬性要求）**：
> - 本文件只放**通用**内容——游戏类型的共同规则、节奏、决策模式、可复用操作。
> - **单一游戏的具体玩法、坐标、攻略、数值，一律存 ima 知识库**
>   （「游戏」KB `7504129723208370` → 文件夹 `game-sensei`），不进本仓库。

## 一、类型：换装 / 造型评分类（Fashion dress-up & style battle）

**代表游戏**：Sparkle（详见 ima 知识库 `Sparkle-新手教程流程与界面实测笔记`、
`Sparkle-关卡体系与任务经济实测笔记`、`Sparkle-剧情主线与评分机制实测笔记`）

### 1.1 核心循环

```
选主题  →  按主题从候选部件中挑一件  →  提交  →  评委/进度条反馈  →  结算
   ↑                                                                    │
   └────────────────── 下一轮 / 下一关 ←───────────────────────────────┘
```

### 1.2 三条类型特征（跨游戏稳定）

1. **无自由移动**
   没有摇杆、没有方向键，屏幕不存在「角色位置」这一状态量。
   → **动作空间塌缩为纯点击**，不需要 MOVE / SWIPE / JOYSTICK。

2. **决策本质是「按主题排序候选」**
   给一个主题（场景/风格/场合），给 2~3 个候选，挑匹配度最高的那个。
   隐藏变量是「**部件 × 主题的匹配度**」，这是该类型的唯一核心决策。

3. **反馈分强弱两层**

   | 层级 | 载体 | 特性 | 用途 |
   |---|---|---|---|
   | 弱信号 | 评委文字评语 | 模糊、正向/中性词、无分数 | 语义理解、氛围判断 |
   | 强信号 | 进度条 / 分数 / 星级 | 连续、可量化、即时 | **作为 reward** |

   → **做 reward 一律优先用强信号**，不要试图把评语文本量化。
   → **进度条的颜色常直接编码极性**（实测：绿 = 领先，橙/橙红 = 落后），
   可先做二值化（绿=+1 / 橙=-1）再谈连续量；颜色比长度更稳、更好识别。

4. **奖励随关卡递增 + 新手局加成**
   实测同一游戏内单局收益逐关上升，且**新手首局给得特别多**。
   → 采集样本时别用第一局推算稳态收益。

### 1.3 物品的属性结构

部件通常是**二维属性**，不是一维：

```
部件 = 款式（shape/style） × 颜色（color/palette）
```

同款可换色，且颜色往往也参与主题匹配。
→ 感知层要为「款式」与「颜色」分别建表示，不能只当作一张图。

### 1.4 对抗性选秀（draft）—— 不要当成单人评分

这类游戏很容易被误判为「单人评分」：给几个候选，挑最好的，加分。
**实际多数是零和对抗**：

```
给 N 个候选  →  我选 1 个（归我）  →  对手拿走剩余里最好的那个
```

实测形态：3 个候选，我选走青蕾丝裙后，对手**立刻穿上**剩下的黑哥特裙
（未选中的选项不会保留）。

**策略含义（决策层必须体现）**：

- 目标不是「选一个高分的」，而是**「抢走对手最想要的那件」**
- 选错时对手直接起飞 → **进度条会立刻掉**，这是最灵敏的负反馈
- 因此 reward 是**相对量**（我 vs 对手），不是绝对分

→ 决策模型要拿**对手状态**做输入，不能只看自己。

### 1.5 多级评分（星级）—— 「满足需求」只是必要条件

除了「赢/输」二值结算，这类游戏还有**多级评分结算**（实测 1~3 星 + 评语标题）。
决策时**最容易踩的坑**是把界面上的「需求勾选」当成高分保证：

**实测控制变量实验（同一关，只改发型）**：

| 组 | 发型 | 服装/鞋 | 需求勾选 | 星级 |
|---|---|---|---|---|
| A | 披肩长发 | 金色礼服 + 金高跟 | ✅ 已打勾 | **1 星（So-So）** |
| B | 正式盘发 | 金色礼服 + 金高跟 | ✅ 已打勾 | **3 星（Unbelievable）** |

**结论（跨游戏通用）**：

- 界面上的「需求/Tips 勾选」是**必要非充分条件**——它只表示「至少有一个部件命中该标签」，
  **不代表整体协调**。两组都打勾，星级却差 2 星。
- 星级由**全部部件的整体匹配度**决定，单个部件权重不等（实测**发型/轮廓**权重很高）。
- → 自动化策略：**先把勾选拿满（约束满足），再优化星级（整体协调）**，两者是两层目标，
  不要用「勾选已满足」就停止优化。
- 信号层级：星级（离散、确定）= reward 主信号；勾选（二值）= 约束检查；评语文本 = 归因解释。

### 1.6 一款游戏可能有多条并行主线，奖励结构不同

**不要假设一款游戏只有一条主线**。实测同一款换装游戏有两条独立主线：

| 主线 | 形态 | 结算结构 | 奖励 |
|---|---|---|---|
| 对战/竞技线 | 选主题 → 对指定对手 | **赢/输二值** | 固定货币 |
| 剧情/任务线 | 逐格推进 → 换装 | **1~3 星多级** | 分级奖励 |

**自动化含义**：

- 两条线**可能共用同一套操作 UI**（如共用换装工坊），但**结算反馈结构完全不同**。
- 必须先判「**当前在哪条线**」，否则会拿二值逻辑去套星级界面（或反之）。
- 剧情线常用「**角色头像在地图上逐格移动**」作为唯一进度指示，
  头像旁的**关卡号牌** = 当前可玩关卡；通关后头像前移一格。

### 1.7 同类型里的「直播 / 实时 PK」变体（第二样本实测）

同一个厂商的换装线可以再长出**「直播」壳**：把「装扮 → 评委打分」换成
**「直播中换装 → 观众人气值实时上涨」**，并叠加 PK 对战。特征：

| 维度 | 换装对战（经典） | 直播变体 |
|---|---|---|
| 主界面形态 | 关卡/主题选择 | **直播房间**（角色居中、弹幕 + 飘心、左侧人气竖条） |
| 反馈信号 | 结算页胜负大字 | **人气值/火焰计数实时跳动** + 角色台词 |
| 进入方式 | 选主题 → Start | 直接开播 → 房内换装 |
| 教学绑定 | 教「选主题 → 提交」 | 教「在直播里换发型、换衣服」 |

**自动化含义**：

- 反馈信号从「离散的结算页」变成**连续变化的人气数值** ⇒ 判据要选
  **数值区域的颜色占比**（如人气条填充比例、火焰计数区域色块），不能沿用结算页判据。
- 直播壳下**换装面板常是覆盖层**，分类 tab + 物品网格叠在直播画面上；
  此时**其余 UI（礼物、色轮、LIVE 标记）常被教学模态拦截**，不要把它们当可用入口。
- ⚠️ 换装类新游的**新手教学是最脆弱的一环**：教学要求逐类换装，
  一旦某分类的资源/列表没就绪，教学模态会卡在那里且吞掉全部输入（详见 §4.7）。

### 1.8 通用适配要点

- **档案只配 TAP**。给点击类游戏配 move，会让老师模型无限重复 MOVE
  （动作熵极低——在点击类游戏里 MOVE 是无效动作，模型却会抓着不放）。
- **感知重点**：
  1. 当前界面态（几个稳定态可枚举）
  2. 候选件数量与各自热区
  3. 顶部进度条长度（reward 来源）
- **每步先判弹窗，再判主流程**。这类游戏弹窗密度高，漏判必卡死。

## 二、跨类型的通用操作模式

以下模式在多个类型的游戏中反复出现，属**跨类型操作模式（类型层）**，可直接复用。

### 2.1 弹窗处理（高优先级）

休闲/移动游戏的弹窗密度远高于 PC 单机。实测在一局新手流程内可连续遇到
4 种不同弹窗：服务条款、插屏广告、评分请求、新主题推广。

**处置原则**：

1. **每步动作前先做弹窗检测**，命中弹窗时优先关弹窗，不推进主流程。
2. **不要为每种弹窗写死坐标**。它们的关闭按钮位置各不同（实测 y 跨度 0.20~0.35，
   x 跨度 0.83~0.96），但**形态高度一致：右上角一个圆形 ×**。
   → 应识别「圆形 × 图标」这一视觉模式，而非枚举坐标。
3. **插屏广告是特例**：它由广告 SDK 全屏接管，关闭按钮位置由 SDK 决定
   （实测在 (0.958, 0.023)），通常比游戏内弹窗更靠角。建议单独建一个
   「广告关闭」识别器。
4. ★**广告必须先等播放完才关得掉**。实测：点右上角 × → 等 7 秒 → 截图**仍是广告**
   （画面在播动画）；再等 6 秒后点 × 才成功。
   **同一支广告还会重复出现**（实测同一支插屏出现 2 次）。
   → 自动化对策：**关闭广告必须重试**——点 × 后截图复检，若仍判为广告页，
   等 3~5 秒再点一次，**最多重试 3 次**。绝不点一次就认定关掉了。
5. **弹窗形态**：实测 6 种——服务条款、插屏广告、评分请求（5 星）、新主题推广、
   **Google Play 应用安装广告**（全屏、底部「安装」、右上角 ×，关闭行为同第 4 条）、
   **竞品游戏试玩广告**（同类产品导量，关闭按钮为 `Skip video` 或右上角跳过图标）。
6. **弹窗关不掉的兜底顺序**：先试右上角带状搜索区 → 再试点击空白区 →
   若是模态面板则用**返回键** → 最后考虑把游戏**拉回前台**。
   - **返回键**：有退出游戏的风险，别第一时间用；但对**模态面板**（如历史记录/设置页）
     往往**是唯一可靠**的关闭方式（实测点空白、点原按钮都无效）。
   - **拉回前台（对付试玩类广告的杀手锏）**：
     `adb shell am start -n <包名>/<主 Activity>`（Unity 游戏主 Activity 名可在
     `dumpsys window` 的 `mCurrentFocus` 里读到）。
     → 广告 activity 若**永不自动结束**（实测试玩广告卡住不退出），
     直接把游戏主 Activity 拉回前台，**不丢游戏内进度**。

### 2.2 点击类游戏的档案收敛

| 若游戏… | 档案应… |
|---|---|
| 无自由移动 | **不配 keys / move** |
| 纯点击交互 | 只保留 TAP（+ 必要时 PRESS） |
| 有拖拽/缩放 | 才开 SWIPE / ZOOM |

> 反面教材：给纯点击类游戏配上移动键，会直接导致老师动作分布退化。

### 2.3 货币与刷取节奏识别

进入一款新游戏后，**先测「单局收益 / 关键商品价格」**，即可量化刷取成本。

- 记录：单局固定收益、主要商品价格
- 推导：需要多少局才买得起 → 判断是否存在体力/次数限制
- 用途：规划采集样本量（要跑多少局才能覆盖足够的界面状态）
- **「能否无限刷」的实测判据**：连续跑 4~5 局，观察是否出现
  体力条递减、冷却倒计时、或「次数不足」提示。
  若钻石只增不减且无障碍 → 判定**无限制**，可连续采集（对训练样本是利好）。

### 2.4 数值/资源面板的固定读法

移动游戏普遍在三处放资源：
- **左上**：玩家身份（头像、昵称、等级）
- **右上**：硬通货余额（货币、体力）
- **右侧竖排**：功能入口（邮件、商店、相机、地图、通知）

→ 新游戏进场先扫这三处，能快速建立 UI 骨架认知，比逐屏试探快得多。

### 2.5 界面态枚举法（新游戏上手流程）

对新游戏建立认知时，按这个顺序推进最省样本：

1. **走完新手教程**（系统会强制把主要界面过一遍，天然覆盖核心循环）
2. **每步截图存档**，标记状态转移边
3. **回到主界面，逐个点开功能入口**（各截一图）
4. **对高密度区域用网格标定工具读精确坐标**（而不是目测或猜）
5. **跑第二局**，验证状态机是否有未覆盖的分支（如失败结算）

### 2.6 任务 / 订单系统（高频，必有）

休闲/换装/经营类几乎都有「任务列表」，形态高度统一：

```
[角色头像]  任务名                        🔍
           [标签1] [标签2]                 ← 完成条件 = 满足这些标签
           🎁 : 💎 20          [ Accept ]  ← 奖励 + 接取按钮
```

**通用结构特征**：

| 特征 | 说明 | 自动化含义 |
|---|---|---|
| **标签式完成条件** | 要求「穿/带/建出具备某标签的东西」，1~2 个标签 | 需把「标签」纳入物品表示 |
| **刷新倒计时** | 顶部常驻 `Refresh Countdown HH:MM:SS`（实测周期 5~6 小时）| 可预测下一批任务时间 |
| **完成后即消失** | 接取并完成 → 该条从列表移除 | 任务是**消耗性**的，一周期内有限 |
| **奖励分层** | 标签越稀有/越具体，奖励越高（实测 20 → 50 → 120）| 优先做高奖励任务 |
| **底部常留一条锁** | 显示 `Buy VIP to unlock` | 免费玩家槽位被打折（付费点）|

→ 自动化该模块的价值很高：**奖励确定、条件明确、可重复**，比自由探索更容易做出稳定收益。

### 2.7 结算页的「看广告翻倍轮盘」

多数休闲游戏在结算页放一个**倍率轮盘 + 看广告按钮**：

```
       💎 base            ← 基础奖励
  ╭─2x─┬─3x─┬─4x─╮
  │    │    │    │        ← 彩扇标注倍率（实测 2x/3x/4x/5x）
  ╰─5x─┴────┴────╯
    [ ▶ 💎 N ]            ← 按钮上直接写「看了实得多少」
     No,thanks            ← 放弃，只拿基础
```

**识别要点（通用）**：

- 该界面的**基础值**就是关卡固定收益；按钮上的数字 = 加成后的实得
- 这是**免费玩家获取硬通货的主要途径**，也解释了「为什么广告这么多」
- 自动化取舍：看广告耗时且依赖 SDK 可用；**采集样本时建议直接 `No,thanks`**，
  保证节奏稳定（实测模拟器上广告 SDK 常初始化失败，会卡住）

### 2.8 关卡选择器（横向轮播）

常见形态：**一排场景卡横向滑动，居中那张被高亮，打的就是居中那张**。

- 卡片正面 = 场景概念图；卡片上有编号或标签
- **★记住上次浏览位置**：下次进入停在离开时那张，不回起点
  → 自动化需**显式把目标卡滑到居中**（可能要滑多次），不能假设从第一张开始
- ⚠️ **别把卡片上的数字当成关卡号**：实测它可能与进入后顶部的 `Level N`
  不一致（主题名对得上、数字对不上）。**以进入后的界面为准，卡片数字仅作参考**。

### 2.9 找失败条件的探测法

想确定「失败长什么样」，不要随机乱试，用**对照实验**：

1. 正常打一局（选最匹配的）→ 记录结算形态
2. 故意选**明显不匹配**的选项 → 看进度条是否变负、结算是否变 LOSE
3. 若单次选错仍赢 → 说明失败需要**连续多轮选错**，或低难度有保底

> 实测：即使选了明显不搭的部件（进度条掉到橙红），最终**仍然 WINNER**。
> 结论要写成「未观察到 LOSE」而非「不存在 LOSE」——**样本不足不下结论**。

### 2.10 复玩 / 重试入口 = 天然的对照实验平台

结算页常带一个**重试按钮**（`again` / `Retry` / `再来一次`），这是研究机制的最佳工具：

- **省掉重复流程**：重试进入后会多出**跳过剧情/对白按钮**（首通通常不允许跳过）。
  实测：首通必须看完全部对白，**重试时才出现右上角跳过键**，一键直达换装环节。
  → 做多组对照实验时，用「重试 + 跳过」能省掉大量重复等待。
- **变量可控**：重试回到**同一关、同一初始条件**，天然满足控制变量的前提。
- ⚠️ 先确认**重试是否消耗资源**（体力/次数/货币），再决定是否大量复玩。

### 2.11 控制变量法测机制权重（研究游戏的标准手法）

要搞清「哪个因素影响结果」，**一次只改一个变量**：

1. 固定关卡与其余所有部件，只改**一个部件**（实测只改发型）
2. 两组各打一次，记录**强信号**（星级/进度条/分数）
3. 差异即该变量的权重证据

> 实测：只把「披肩长发」换成「正式盘发」，星级从 1 星直接跳到 3 星
> → 证明**发型对该主题的权重很高**。
> 反过来，若两组结果相同 → 该变量在此主题下**无关**，可安全忽略。

**注意**：结论只对**该主题/该关卡**成立；换主题要重测（风格匹配是**条件相关**的）。

### 2.12 付费道具是「一次性买断」，不是租用

判断付费道具的经济模型（影响长线策略）：

- 点付费道具 → 弹确认框（`花 N 货币购买？` Cancel/Confirm）→ Confirm 后：
  - **货币真实扣除**（实测 730 → 580，正好 -150）
  - 道具**立即装备并永久解锁**（再次点击不再弹购买框）
- Cancel 则**无任何变化**。
- → 属**买断制**：货币花掉换永久使用权。自动化的经济策略可以「值得的道具买断后长期复用」。

### 2.13 剧情/对白的推进与跳过

视觉小说式剧情（立绘 + 名字标签 + 对白框）的通用交互：

- **推进**：点右下角**向下箭头**（实测 @ ~0.94, 0.86）或点击对白框
- **跳过**：右上角 **`▶|` 跳过按钮**（**仅重试/复看时出现**，首通不可跳）
- **可交互物件**：剧情中会出现**高亮物件**（如礼物盒），需点击才推进
  → 这类"剧情里的小交互"容易漏判，自动化时要检测「非标准对白框」的可点元素

### 2.14 自由移动类：单帧观测分不清「在走」与「顶墙」——把画面变化量喂回策略

**这是有自由移动（摇杆）的游戏最容易被忽略的一类死锁**，与「策略打转」是两种病，用药不同。

- **现象**：决策模型（尤其小 VLM）只看一帧时，**无法区分「正在前进」和「顶着墙/障碍走」**——
  两种情况下画面里都有角色动画、粒子特效在动。模型会因此长期重复同一方向
  （实测出现过**连续 41 步同向**、单步画面变化量掉到 1~3 而无人察觉）。
- **为什么通用兜底救不了**：动作多样性类兜底（「重复 N 步就换个按钮/换个动作」）在此**完全无效**，
  换按钮在顶墙场景里是空操作甚至误触。**移动卡住的唯一出路是换方向。**
- **通用解法（三件套）**：
  1. **把可测的 Δ 回传进提示**：回路本就能算**相邻两帧的画面变化量 Δ**，把它连同
     「连续同向小 Δ 的步数」一起写进决策提示；连续 ≥2 步时为一句显式禁令
     （「禁止再沿原方向走」）。单帧模型看不到的东西，回路替它测。
  2. **兜底按动作种类分流**：移动复读 → **换方向**（挑一个与当前方向不同的方向长推），
     非移动复读 → 才换按钮。两者混用会把「走远」（本就要连续同向）误判成卡死。
  3. **换向再加一道 Δ 闸门**：只有在**确实没挪窝**（Δ < 阈值）时才强制换向。
     否则会把正常赶路打断，把一次直行拆成一路乱拐（实测：8 步固定门限下，
     4/5 次强制换向发生在 Δ 13~19 的正常赶路中）。
- **两级卡死判据要分清**（缺一不可）：

  | 判据 | 口径 | 治什么 | 盲区 |
  |---|---|---|---|
  | 跨窗口 Δ | 当前帧 vs N 步前锚点 | 整段时间世界没动（息屏、加载、角色被钉住） | **「世界在动」不等于「我在动」**——顶墙时角色/粒子仍在动画，压不到阈值 |
  | 相邻两步 Δ | 这一步几乎没挪窝 | 顶着墙持续走 | 单步 Δ 天生小（小步长正常走动也只有 1~2），必须**连续多步**才判定 |

> 实测数据与实现细节见 `README.md` §11.10 / §11.11（判定阈值、日志锚点、校验脚本）。

### 2.15 示范数据采集与学生加训：三类「不报错但白干」的坑

来自 nrc 首次真机加训（2026-09-13，详见 ImA「游戏」库《洛克王国-战斗判据修正与首次真机加训实测》与仓库 §11.15）。
共同特征是**全程没有任何报错**，只能靠采集后核对、或对照实验才能发现。

**坑一：记录层的动作类型漏映射 → 案例标签被静默改写。**
真实示范里「按技能/聚能」走的是一个独立动作类型（如 PRESS），若记录层没有为它建映射，
它会落进 `default` 被记成「无操作」——于是**老师正确的操作被记成「发呆」，
学生学到的是反面样本**。对策：给映射函数加**反向白名单断言**，遍历所有可录动作类型，
任何一个落 `default` 就报错；采集结束**必看类别分布**再训练。

**坑二：界面判据用「全局统计」对整体亮度不鲁棒。**
用「亮像素的列/行投影 + 阈值」判界面态，在背景一变亮时列峰被整体抬高，
阈值把真正的目标淹没 → 判据漏判，动作空间被抖散，而日志上看像「游戏没反应」。
对策：优先用**局部对比度**（目标区域内亮度 − 周边环亮度）这类与整幅亮度无关的量，
并把位置约束保留（只有落在标定位置的才算命中）。新参数要有**零值兜底**，
否则档案缺字段会让判据退化成「恒真」。

**坑三：把「热启动 + 冻结骨干」当成万能加训配方。**
三条实测结论（8 组对照实验）：
1. **跨域热启动没有迁移价值**：在 A 域（如视频抽帧的弱标签）训出的骨干，拿到 B 域
   （真机截图）上直评可能直接是 0%，且恒输出一个类。`--init` 此时只是「借一个 fc 初始化」，
   不是站在巨人肩膀上。**先做「基线不训练、直接在目标域上评估」这一步**，
   再决定要不要热启动。
2. **epoch 别照抄小值**：几十条样本、冻结骨干只训决策头时，30 epoch 可能严重欠训
   （实测 0.00%），同配方拉到 200 epoch 才到 50%。
3. **单帧静态观测学不会方向**：`上/下/左/右` 的区别在**帧间**不在帧内，
   单帧灰度图上这些类本质不可分（实测所有配方都学不起其中一个方向类）。
   这是**架构上限**，调超参无解——要学方向必须换观测（帧差 / 帧对 / 短时序）。

**关于 `val_acc` 的门槛**：验证集只有几条样本时，一个样本就是 10%~25%，
`val_acc` 只能当**趋势**看，不能当能力指标。真正的验收标准是**上真机跑一段看行为**。

## 四、自动化执行层：把「学会的流程」固化下来（跨类型通用）

> 这一节不是游戏知识，而是**工程方法**：怎么让程序学会玩，而不是让大模型一直盯着玩。
> 起因（2026-09-13）：老师 VLM 单步决策 1~2s、每次都要花钱，让它「重复已学会的流程」
> 既慢又贵。正确闭环是 **老师探索（贵，一次性）→ 固化进档案（免费）→ 确定性执行器跑**。

### 4.1 用「画面反馈」代替「死等时长」——提速 5~10 倍

新手写自动化最自然的做法是每步 `sleep 2s`，20 步就是 40s 纯浪费。

改为「**等画面变化就推进**」后，实测同一动作从 4.07s 降到 **973ms**。

| 判据 | 含义 | 适用 |
|---|---|---|
| `change` | 画面相对**动作前**发生变化 | 点完等界面切换（最常用） |
| `stable` | 画面连续两帧不再变化 | 等动画播完 / 等加载结束 |
| `ratio` | 指定区域内**目标颜色**占比达阈值 | 等特定 UI 出现（最可靠，见 4.3） |
| `time` | 只等固定毫秒 | 确实无可观测变化时的兜底 |

**为什么 change 需要「动作前」的基准帧**：动作可能瞬间改变画面，动作后再抓基准
会把变化本身当成基准，导致永远等不到差异。

**阈值经验**：灰度平均绝对差用 **4**（0~255 量级）。太小会被压缩噪声误触，太大则迟钝。

### 4.2 「连点直到出现某界面」需要专门的循环原语

对话推进的条数**不固定**（剧情长短、是否插播广告），写死次数必然要么点不够、
要么白点十几次。必须支持「反复执行 → 每轮立即判定 → 满足即停 → 最多 N 轮」。

**关键约束：循环的停止条件必须判「出现什么」，不能判「变了没有」。**
`change` 在循环里会退化——每轮动作本身就改变了画面，基准帧被自己破坏，
于是第一轮就"满足"退出。所以循环只能用 `ratio`（绝对特征）。
这条要在**档案加载时静态校验**报错，不能跑到一半才发现。

### 4.3 ⚠️ change 判据会被插播广告骗过（实测踩坑）

实测：点「换发型」后 973ms 就检测到「画面变化」并判定成功，截图一看——
是 **Google 广告插播**（全屏视频），不是发型变了。

**教训**：`change` 只能证明「画面动了」，不能证明「我想让它发生的事发生了」。
手游随时会插播广告/活动弹窗，`change` 的成功率会被污染。

**对策**：关键步骤改用 `ratio`（判目标 UI 出现），或把 `region` 收窄到
**只有预期变化会发生的那块区域**（如只看人物头部，不看全屏），让广告全屏也无法触发。

### 4.4 手游自动化的「固定干扰项」清单

按处理方式分类，写档案时逐条准备：

| 干扰 | 表现 | 处理 |
|---|---|---|
| **启动期平台登录** | Google Play Games「选择玩家资料」等 | 固定坐标点「继续/取消」；**每次冷启动必现**，固化计划第一步就该清掉 |
| **插屏广告** | 全屏视频/静态图，带 X 或倒计时 | 等可关闭 → 关闭 → 重试；可能连环弹 |
| **活动弹窗** | 多个位置不固定（绚彩生活/新主题推广…） | 宽松跳过（超时不算失败），靠后续步骤拉回 |
| **评级请求/竞品试玩** | 应用内评分框、"试试这个游戏" | 直接关掉，别点「去评分」 |
| **后台掉帧** | 应用切后台后 `am start` 拉回即可 | 不要用重启，重启会再触发登录弹窗 |

**宽松优于严格**：单步超时默认**不致命**（记日志继续），因为手游的插播太频繁，
硬失败会让整个计划一步都走不完。确实不能容忍失败的步骤再单独标 strict。

### 4.5 计划里该放什么、不该放什么

- ✅ **放**：流程固定的操作（进关、清弹窗、走完对话、点结算）
- ❌ **不放**：需要判断的操作（选哪件衣服、打哪个敌人）——那交给学生模型或规则
- 分界线：**「下一步做什么」如果是确定的，就不该问模型。**
  这也是省钱的本质——把确定性从推理里拿出来，写进档案。

### 4.6 ⚠️ 计划执行的「顺序性」局限（实测暴露）

**现象**：为了让同一逻辑界面（主题选择页）的**两种布局变体**都能走通，
计划里写成"先走路线 A（点 Start），再走路线 B（点卡片）"——
因为计划是**顺序执行**的，当前若是变体 B，路线 A 的那一击不会落空，
而是**落到卡片上直接进关**；紧接着路线 B 又点一次，落在关卡内随意位置。
两次「盲点」把流程推歪，插播广告趁机接管屏幕。

**教训**：`-plan` 是**无条件顺序执行**的，它没有「当前在哪一屏」的概念。
所以：

| 能这么做 | 不能这么做 |
|---|---|
| 每步动作在**多数状态下**都安全（幂等点击、清弹窗、点继续）| 用「A 不行就试 B」的兜底写法——两次都会真的点下去 |
| 用 `max_repeat` + `ratio` **循环到某状态出现** | 把互斥的分支写成顺序执行的相邻两步 |

**正确做法**：让每一步的 `until` 判据把「已经到目标态」也涵盖进去。
例如进关这步，判据应为「**已经进入关卡**（物品卡区出现）**或**已离开主题页」，
而不是"点一次 Start、再点一次卡片"。

**边界总结**：适合 `-plan` 的是**单一路径、步骤可幂等**的流程
（清弹窗、走对话、点结算）。一旦流程存在**多分支且分支动作会互相破坏**，
要么把判据做扎实（每步都能自证是否该执行），要么退回让学生模型决策。
**这不是「计划能替代一切」，而是「确定性流程才值得固化」。**

### 4.7 ⚠️ 教学 / 资源阻塞类「假卡死」的识别与止损（实测方法论）

新手教学阶段是最容易撞上**不可解阻塞**的地方，且症状会被误读成「游戏崩了」「网络断了」。
下面这套判别顺序实测有效、可跨游戏复用。

#### ① 先分清三种「卡」

| 症状 | 判据 | 定性 |
|---|---|---|
| **真崩溃** | 进程消失 / 前台掉回桌面 / logcat 有 `FATAL EXCEPTION` | 崩溃 |
| **逻辑锁死（本例）** | **画面还在动**（帧间 Δ 非 0，动画/数值在跳）但**任何输入无响应**（Δ ≤5） | 模态/状态机死锁，非崩溃 |
| **真的在等** | 画面周期性变化 + **判据在缓慢逼近**（如过渡动画循环） | 只是过渡态，要给足预算 |

> 关键：**「画面在动」与「输入有效」是两件独立的事**。只看画面会漏判锁死。

#### ② 量化「输入是否被吞」——用 Δ（画面变化量）

同一坐标点击后对比前后帧，Δ 呈**双峰分布**，中间几乎没有样本：

| 状态 | Δ | 说明 |
|---|---|---|
| 点击生效（换装 / 切分类 / 关弹窗 / 跳页） | **≈20 ~ 180** | 有实际 UI 变化 |
| 点击被吞 | **≈1 ~ 5** | 噪声级（动画自身的抖动）|

⇒ **别用「感觉没反应」判断**。跑 3~5 个候选坐标、各量一次 Δ，一屏就能定位可用入口。
（`cmd/shot -delta` 已实现；建议后续加 `probe-input` 原语，见 GAP。）

#### ③ 卡死时按顺序排查（都别猜）

1. **网络自身**：`ping` 外网 / `settings get global http_proxy` / `cat /system/etc/hosts`。
   （本例三项全干净 ⇒ 网络本身没问题，别再折腾网络）
2. **云资源是否落地**：`/sdcard/Android/data/<pkg>/files/` 下各缓存目录体积。
   本例典型信号：`AdvertisingShopSnapshots` 2.5M（广告图能下）而
   `TextureFileSystem` 仅 168K、`HTTPCache` 仅 8K（**角色/服装纹理几乎没下**）
   ⇒ **「只通了一个 CDN」**，不是整体断网。
3. **依赖的 SDK 是否初始化成功**：广告/支付/登录 SDK 的证书与网络报错
   （本例 `Trust anchor for certification path not found` ⇒ UnityAds 起不来）。
   若教学里含「看广告解锁」，这一步失败就必然卡住。
4. **异常堆栈要读语义再定性**：`libil2cpp.so 0x0` 的堆栈若首行是
   `Unload unused assets...`，那是**正常内存回收**，不是 native crash。

#### ④ 止损准则（重要）

**同一点位、冷启动复现 ≥3 次即停手**，判定为「阻塞且我方无解」，
记录缺陷后**转回已有产线**，不要继续投入。

理由：新手教学阶段的阻塞**几乎不可能靠执行层绕过**（模态吞输入 ⇒ 任何计划都点不动），
继续投入只会烧掉预算。正确的产出是**一份可复现的缺陷记录**（现象 / 复现步骤 / 判据 /
证据 / 定性 / 待真机确认），而不是硬凑一条走不通的 plan。

### 4.8 ⚠️ plan 线判据的「自身正确性」：一致性 ≠ 正确；否定类结论必须双证据（2026-09-15 实测事故）

前面 4.3 讲的是「判据会被插播广告骗过」（change 判据），这一节是升级版：**判据本身可能是错的，
而所有验证环节都发现不了**——因为验证环节用的是同一条判据。

#### ① 事故形态：一次「双向一致 4/4」里藏着一个假判负

跑批的常规验证是「**plan 自报 == 外部脚本独立复算**」。某轮 4 局跑出 4/4 一致，看着完美；
其中一局的**终态帧其实是一条插屏广告**：广告顶部的**大片黄色**落进了「金色皇冠（判负特征）」的区域，
把占比顶到 **14.5%**（真败局只有 4.4%）⇒ 判负。**plan 与外部脚本读的是同一条判据（同一组
region/color/tolerance），两边算出同一个数、得出同一个错误结论。**

⇒ **铁律：「双向一致」只证明「同一条判据在两边算出同一结果」，不证明判据本身对。**
一致性防的是「解析/口径漂移」；**判据正确性必须单独验证**：
把判据拿到**反例帧**（广告页 / 主界面 / 过渡态 / 同一页面的其他版式）上比分离度。

#### ② 调参常常救不了：小图标特征天然不免疫广告

实测三条路都试过、全失败：

| 做法 | 目标页 | 广告页 | 结论 |
|---|---|---|---|
| 原区域 + 容差 45 | 4.4% | **14.5%** | 广告更高 ✗ |
| 放大区域 + 容差 45 | 12.2% | **29.1%** | 广告更高 ✗ |
| 原区域 + 容差收到 25 | 4.9% | 9.7% | 分不开 ✗ |
| 换成「整页大字」白字箱 | 4.2~4.6% | 0.0% | 但**胜局 8.6~11.2%** ⇒ 分不开正/负 ✗ |

根因：**判据是「小图标/局部特征」，广告是「整块任意创意」**——创意里出现相近颜色，
小图标特征必然被压过去。**只有「整页版式级」的特征才稳。**

#### ③ 结构性修法：把「我在目标页面上」做成闸门的**入口守卫**

若引擎的推进/前置条件**各只能写一条判据**（没有 AND 组合），不要试图"再加一个条件"，
而要**换一条判据在链路上的位置**：

- 把**易被广告命中的特征**从「前置条件（when）」挪到「推进条件（until）」，
  语义从「出现了就动作」变成「**限时内必须消失**」；
- 把**目标页面专有、且广告上为 0% 的特征**（本例：顶部那条彩色进度/血条）放到 `when` 当前置守卫；
- 结果：真·目标页 ⇒ 入口成立 + 特征不消失 ⇒ `strict` 主动失败（**机器可读的否定结论**）；
  正常页 ⇒ 入口成立 + 特征 0% ⇒ 立刻通过；**广告/其他页面 ⇒ 整步跳过**（跳过不报错，也不会误动作）。

**外部复算脚本不受单判据限制，应当收紧成「双证据」**：

```
否定结论 ⟺ 目标特征在场 AND 目标页面特征在场（确实站在那个页面上）
肯定结论 ⟺ 正例专属特征达标
```

#### ④ 两条工程纪律（这次事故同时暴露的）

- **每轮证据必须落盘**：跑批目录里放 `plan.log` + 起点帧 + **独立抓的终态帧** + 结论 JSON。
  事故能查出来，全靠那张终态帧；没有物证的"结论"无法事后追责。
- **汇总统计必须绑「有 schema 的产物」，不要正则猜 stdout**：旧跑批脚本的正则要求关键词紧跟
  某个前缀（实际行里中间还夹着别的字段），结果**单轮结论是对的、汇总表整列是错的**
  （看着像"全军覆没"）。汇总优先读每轮落盘的 JSON，stdout 只作兜底。

#### ⑤ 跑批 × 离线矩阵：两种覆盖互补，缺一不可

- **跑批**覆盖「真机实际走到的那条路径」——但**永远走不到不触发的分支**（守卫步、异常恢复步）。
- **离线「设计验证矩阵」**= 逐步 × 各页面（把每步的 when/until 拿到**已标注的页面帧**上求值，
  看它是「整步跳过 / 执行并通过 / 执行→strict 报错 / 执行→宽松超时」）⇒ 补齐真机不触发的分支，
  还能发现**「判据漏掉了同一页面的另一种版式」**这类跑批永远不会暴露的问题
  （实测：某页结算界面有**带/不带顶部进度条两种版式**，判据只覆盖了其中一种）。

推荐顺序：**先矩阵（便宜、可反复跑、覆盖全）→ 再跑批（贵、验证真实链路）→ 用矩阵结论解释跑批里的异常轮次。**

### 4.9 给新游戏建档前：入口靠实测枚举、坐标靠像素扫描（2026-09-16 实测）

#### ① 入口命名 ≠ 功能，必须逐个真机点过

实测同一款游戏里两个看似同类的入口落点完全不同：`ADS` 进的是**内购页**（一次性买断去广告），
`SHOP` 进的是**「看广告解锁套装」的免费获取页**。右上角一条通知实际是**直播邀请**，不是消息列表。
⇒ **不要用图标外观、位置或名字推断功能**。给新游戏建档时，主界面每个入口至少点一次，
把「入口 → 落点 → 玩法一句话」列成表（这张表就是后续选路线的依据）。

#### ② 坐标一律「像素扫描」，不要视觉估

实测视觉估坐标偏过几十像素（点空）。做法：写个通用小工具，在**给定归一化窗口**内求
**前景质心**——前景判据 `彩度 (max-min) > 40 或 亮度均值 < 110`——输出归一化 `(cx, cy)`，
并同时打印**前景占比**（占比过低说明窗口没圈到东西），落一张带十字标记的核对图人工确认。
窗口给粗一点没关系（±0.05 的容差质心会自己收敛）。工具见 `phone/find_btn.py`。

#### ③ 入口级坐标与档案级坐标可以并存

档案 `buttons[].pos` 里存的坐标（给 plan / 学生用）与复测的质心常差 0.02~0.03 归一化，
**只要都落在按钮内就都可用**，不必强求一致。但**换机型 / 换分辨率必须重标**。

#### ④ 「看广告」是这类养成游戏的核心玩法，至少三种形态

| 形态 | 表现 | 建档要点 |
|---|---|---|
| **解锁型** | 看一次广告解锁一部分内容（实测：每看一次解锁套装 6 件中的 2 件，进度 0/6 → 2/6） | 找「免费获取」入口 |
| **倍数型** | 看广告把收益按倍数放大（实测：点赞收益 X2~X4 可点选，X3→123 / X4→164） | 找「收益结算弹窗」 |
| **免除型** | 一次性内购买断广告（`NO ADS! US$1.99`） | 常与「商店」入口同名易混 |

⇒ 三者入口不同、都别漏。且广告同时是**判据污染源**（粘住不消失、色块撞判据），
见 §4.8；处置原则是「只在确认不在目标页面时才按返回键，绝不在广告区域内点坐标」。

#### ⑤ 覆盖度写成清单，「没反应」与「没功能」分开记

「玩法跑遍」不是收尾判据（收尾看能力证据），但文档里要有那张入口表，并且把
**「注入点击被吞导致没点动」**与**「功能真的不存在」**分开标注——二者对策完全不同：
前者换交互方式（或如实记未覆盖），后者才需要写进限制。

### 4.10 判「点击生效/被吞」的正确姿势：全局 Δ 必然失效于小控件（2026-09-16 定案）

**事故**：YoYa Star 三条功能（他人帖子点赞、收益弹窗倍数条、红按钮）被记为「注入点击被吞」，
第二轮全部破解——**全是坐标估错 + 全局 Δ 失效的误判**，没有一条真是「拒绝注入」。

1. **全局灰度 Δ 对小控件变化必然失效**：1080×2340 画面上「心形由空心变实心 + 数字+1」的全局 Δ 只有 **0.1**，
   而大按钮换页的 Δ 是 20~180。用同一阈值（Δ<5=被吞）判断，小控件永远显示「被吞」。
   ⇒ 判定要么用**以点击点为中心的局部 Δ**（`dot_probe.py`），要么用**区域色占比**（`px.py`：红心区 0%→24.5%，分离度完美）。
2. **目视 540 缩略图估坐标误差可达 0.06~0.14**（=65~150px）。心形真实位置 (0.843,0.653)，
   目视估成 (0.778,0.648)——点在空白卡片上。红按钮真实中心 (0.500,0.738)，目视估成 0.701（偏上 37px）。
   ⇒ **小控件一律 crop 放大量取或像素扫描**（`crop.py`），量完还要复核。
3. **「注入被吞」判定三步排除法**（顺序不可乱）：
   ① `crop.py` 放大点击区，核对坐标是否真落在控件上；
   ② 局部 Δ / 区域色占比判定画面是否真的没变；
   ③ 前两步都排除后才允许下「拒绝注入」结论，且要 tap/swipe/mouse/back 多手法交叉（§4.7）。
4. 判据样式：**「状态小图标」优先用色占比而非几何/Δ**。空心描边图标 → 实心填色（红 0% vs 24.5%），
   这种「有无填充色」的状态是天然的机器可读判据。
5. 工具三件套已沉淀：`phone/dot_probe.py`（全局+局部 Δ 探测）、`phone/px.py`（区域像素统计）、`phone/crop.py`（裁切放大+归一化换算）。

### 4.11 ✅ 换机（换分辨率）后像素判据的整条重标流程（2026-09-17 实测）

**背景**：同一款游戏的界面态判据（band/positions/阈值）是**按分辨率标的**，换设备后必然失效——
面板从 3200×2136（宽高比 1.50）换到 2340×1080（宽高比 2.17）后，战斗态判据直接把战斗画面判成 `world`。
归一化坐标**不跨宽高比通用**：更扁的屏让垂直锚点整体上移（本例按钮 y 0.905 → 0.83，差 0.075）。

**重标流程（顺序不可乱，全程离线复算，不要在设备上试错）**：

1. **先采集一正一反两组帧**：真实目标态帧（战斗）+ 至少 2~3 个反例帧（世界态，最好含易混变体如其它面板态）。
   反例帧的作用是量分离度，没有反例就没法说判据「对」——一致性 ≠ 正确（§4.8）。
2. **用判据原逻辑在 Python 里逐像素复算**（不要凭手感调参）：先按「行投影 / 列投影」把目标控件的位置扫出来，
   再按两条路径各自的匹配规则算 hits。
3. **四帧同时验证分离度**，要求正例两条路径全 PASS、反例全 fail，才允许写进档案。
4. **写进档案后仍要上真机复核一次**（`shot -check`），确认加载路径与离线复算一致。

**两个最容易踩的坑（本轮实测）**：

- ️ **列投影质心会被控件下方的文字标签往下拉。** 检测带若把标签一起框进去，算出的质心 y≈0.848，
  而控件真实圆心在 0.83——差 0.018 就足以让位置匹配失败（容差通常才 0.015）。
  ⇒ **把检测带下界收到标签上沿以内**，让质心回到控件本体（窄带实测质心 0.821~0.835，与 0.83 吻合）。
  通用做法：先跑一次行投影，看命中峰是不是**两段**（控件主体 + 文字标签），是就把带切在缝上。
- ⚠️ **同一组位置参数会被多条判据路径以不同敏感度消费。** 「列投影簇质心」路径偏控件亮像素重心，
  「局部对比度」路径对圆心极敏感（实测圆心 0.845 命中 4/5、0.815 只命中 1/5）。
  ⇒ 标定时**先各测两端，再取折中值**，不要只按一条路径调到位就收工。

**架构侧的坑**：

- ⚠️ **宏名 / 按钮名不能重名**：新加的宏若与档案里既有按钮同名，`go build` 照样通过，
  但**加载时报「宏名 X 与按钮或其它宏重名」**——错误只在运行时暴露，别以为编译过就没事。
  重标坐标前先列一遍档案里现有的命名按钮，往往发现**该有的按钮早就有了**，只是坐标过时。

### 4.12 ✅ 临时态面板：必须连续执行，不能分两次单点（2026-09-17 实测）

**症状**：点「捕捉钮」展开球列表后，再点列表里的球 ⇒ Δ≈2，什么都没发生；而底栏固定按钮怎么点都灵。
**根因**：**面板是临时态、会自动收起**（几秒）。而自动化的「抓帧 → 读图 → 发命令」周期是分钟级，
第二次点下去时面板早关了，点到的其实是关掉后该位置的普通 UI 区域。
**正解**：把「点开面板 → 点条目」压进**一条命令的连续序列**（如 `shot -seq "x1,y1:1200;x2,y2:3500"`），
或写成一条宏整条跑。**判定方法**：如果单点某控件 Δ≈2 但同一坐标在「刚点开面板」的帧上确实有内容，
就优先怀疑「面板已收起」而不是「坐标错」。

> 连带教训：**「控件点不动」要先排除状态问题，再怀疑坐标问题**。
> 本例两次误判（先怀疑坐标 → 反复重读；再怀疑注入失效）都走了弯路，根因是最朴素的「面板已经关了」。

### 4.13 ✅ 「选中后画面静止」≠ 操作完成：警惕「等待目标的瞄准态」（2026-09-17 实测）

**症状**：按流程点了「开面板 → 选道具」两步，画面随即**完全静止**（连拍 6 帧、间隔 2.5 s，帧间差异只有 0.5%）。看起来像卡死/操作无效，但**其实游戏在等你点第三下**。

**根因**：很多游戏的道具使用是 **`（1）开面板 →（2）选道具 →（3）点目标`** 三段式。第（2）步之后进入**瞄准态**：
- 面板**不会关闭**（这点最容易骗人——按 §4.12 的经验，「面板还开着」通常意味着「还没点中」，于是把已经点中的第 2 步判成了失败）；
- 画面可能出现一个"像是已经生效"的视觉形态（本例：球体罩住目标 = 准星，不是命中）；
- 之后**不做第（3）步就永远停着**，等多久都不动。

**判据（怎么区分「瞄准态」与「真卡死」）**：
1. **面板是否还在**：面板仍开 = 还在流程中；面板已收 = 多半已完成或失败。
2. **连拍看是否有微动**：帧间差异 ~0.5% 且仅限光效/粒子 = 引擎还活着（在等输入），不是死画面。
3. **直接补第（3）步**：点目标位置，Δ 若立刻变大（本例 Δ=34.3 切进特写镜头）= 这就是缺的那一步。

**操作铁律**：
- 三段式流程**整条压进一条命令**（`-seq "开面板;选道具;点目标"`），不要中间插抓帧读图（读一次要一两分钟，面板早关了）。
- 交叉验证很有用：本例补上第（3）步后，立刻**印证了档案里一条来源不同（网络图文攻略）的旧先验**——「点击，再点击左上的咕噜球，最后点击想捕捉的精灵」。**当实测与旧先验冲突时，先怀疑自己的流程漏了一步，而不是先推翻先验。**

> 另一条配套教训（非游戏问题）：**adb daemon 会自行退出**，此时 `exec-out screencap` 会产出**截断 PNG**，压缩工具报 `not enough pixel data: invalid format`。
> **别怀疑游戏或坐标**，先 `adb kill-server && adb start-server` 再重试。

### 4.14 ✅ 「长按看详情」与「模态轮盘」两条通用交互 + 攻略可信度分级（2026-09-17 实测）

**一、「长按看详情」是移动端通用模式，出问题先试它**

绝大多数手游的技能 / 道具 / 装备都支持 **长按 → 弹说明面板（名称 / 等级 / 类型 / 效果）**。本例的实战价值：

- 一个技能打出去敌方血量**纹丝不动**，一度被判成「技能失效 / 点了没反应」。**长按看说明后发现它是「状态」类技能（与敌方交换增益减益），本来就不造成伤害。**
- 教训：**「操作已生效，但效果不符合预期」时，先去查这个对象自己的说明，而不是重试操作**。前者一次解决，后者是无底洞。

**二、「模态轮盘」的关闭方式：点外部和返回键都可能无效**

长按触发的**能力 / 道具轮盘**常是模态的，本例实测：

- 点面板外 —— **不关闭**；
- `keyevent 4`（返回键）—— **也不关闭**；
- **只有「长按（或点击）轮盘中的某一项」才会关闭**。

⇒ 通用排查顺序：**先试点项 → 再试长按项 → 最后才判「卡死」**（与 §4.13「先排除状态问题、再怀疑坐标」同源）。

**三、攻略可信度分级（本轮被「毒攻略」坑了两次）**

同一机制，网络攻略与实机冲突时：

- ❌ **凡是给出「硬限制」的（等级上限、次数限制、前置条件），优先怀疑**。本例两处毒攻略：~~普通咕噜球仅限 ≤20 级精灵~~、~~必须先进入战斗才能投球~~ —— 实机**均无此限制**。
- ✅ **高可信攻略长这样**：给出**同一机制的多种触发路径**（「长按 / 或靠近进战斗 / 或用道具」）、带版本号与截图日期、会说明**什么情况下会失败**。
- 🔁 **正解做法**：攻略只当**假设来源**，每条限制都要在游戏里做一次**反例测试**（"我偏拿 46 级精灵配普通球，看它拦不拦"）。

**四、安卓调试的宿主干扰（跨游戏通用，非游戏问题）**

国产 ROM（MIUI 等）会在插拔 / 切换 USB 时弹**系统页抢占前台**（本例 `com.android.settings/.Settings$UsbDetailsActivity`），后果是：

- 游戏被切到后台（还有被系统回收的风险）；
- `adb` 报 `device not found`，抓帧产出截断 PNG。

**恢复三步**：`keyevent 4` 退出系统页 → `monkey -p <包名> -c android.intent.category.LAUNCHER 1` 拉回游戏 → 等 10~15 s 再抓帧。

> 判据：`dumpsys window | grep mCurrentFocus` 里出现**非游戏包名**，就按这条处理，**别怀疑脚本或游戏**。

**五、探测「按住态」UI：后台长按 + 前台抓帧（adb 通用）**

`adb shell input swipe x y x y <ms>` 是**阻塞**的（松手才返回），所以「手指还按在屏幕上」那一刻的界面永远抓不到 —— 极易把**按住才出现的 UI** 误判成**松手后的 UI**。解法是把长按丢到后台：

```bash
( adb -s <serial> shell input swipe 651 1007 651 1007 9000 >/dev/null 2>&1 & )
sleep 4
./shot -o hold.png          # 此刻手指仍按在屏幕上
```

本轮正是靠这一步证明：球按钮**按住第 4 秒时屏幕上只有球轮盘、没有瞄准框**。若省掉它，就会照抄攻略的「长按 → 瞄准框」，把错误结论写进档案。

配套：Android 11+（SDK 30+）可用 `input motionevent DOWN/UP` 做**分段手势**（按住→停→拖→松手各一条命令）；**Android 10 及以下不支持**（`input motionevent` 直接打印 usage），只能靠上面这招近似。

### 4.15 ✅ 「底部选择器 + 右下使用键」手持物范式 + 长按即瞄准、松手即投出（2026-09-17 洛克王国实测）

**一、范式识别**：开放世界手游常见「手持物」设计——底部一排**选择器**（各长按弹轮盘选物品），右下角一个**使用键**（图标随手持物变）。洛克王国实例：底部紫球=咕噜球轮盘（6 球带数量）、底部金星=法杖轮盘（6 杖），右下大按钮=使用当前手持物。**别把右下使用键当成某个固定功能按钮**（本轮先误认成「星星魔法」），要看它的图标随手持物变化。

**二、长按使用键 = 瞄准态；松手 = 投出/施放**。瞄准态三件套：角色举物在手 + 左侧弹出物品栏（选中项高亮）+ **屏幕中央虚线准星 = 落点指示**，左上 ✕ 退出。投球/施法同构。

**三、adb 复现手势（Android 10 无 motionevent 也能做）**：
1. **瞄准不靠拖动**——单条 `input swipe` 从使用键出发的拖动一律被判为**视角操作**（2.2s/2.5s/5s 慢速拖全试过，无效）；
2. 正解：**先转视角把目标对准屏幕中央准星 → 后台长按使用键（`input swipe x y x y 9000 &`）→ sleep 4 抓帧确认举物+准星 → 第 9 秒松手即投出**（投掷动画实测出现）。
3. 「按住中拖动瞄准」是真人手势，adb 单指序列做不到；绕开的本质 = 把「拖动瞄准」退化成「转视角 + 原地长按松手」。

**四、判「游戏卡死」的字节级标准**：连续 ≥3 张**真实新截图**（文件时间戳递增）字节级完全一致 + 所有点击/返回键无效 = 画面冻结（本轮大地图 NPC 面板交互后触发，UE4 游戏）。恢复：`am force-stop <pkg>` + monkey 拉起，进度不丢。温度升高但电量不涨是旁证。

**五、游戏内「追踪」≠ 自动寻路**：地图/NPC 面板的「追踪」按钮只放一个导航标记，**不会自动走路**。凡是攻略写「点击 XX 自动寻路」，先当毒攻略处理（洛克王国已连续三条毒攻略：球等级限制、必须进战斗捕捉、自动寻路）。
