**这条链路是确定性的，不是"偶尔能成"**：十一批正式跑批合计 **152 轮**，
**链路成功率 100%、复位 152/152**，且**没有累积漂移或性能退化**

> 坑④的抓帧兜底旧帧、坑⑤的叠加层误判（成功率照样 100%，实际 2 轮什么都没点成）。

## 跑的是什么

一轮完整闭环（只用**退出路径已实测无损**的动作，不破坏游戏状态）：

```
抓帧 → 全库定位(24 条图标模板) → 点目标图标 → 抓帧验证反应 → 复位回地图
```

判"点击成功"的标准是**帧差达标 + OCR 新增文字**双判据，不是"命令返回 0"。

## 单轮 20.8 秒花在哪（提速后口径）

> 下表分项来自第五批 16 轮（均 21.2s，**PNG 通道口径**）。阶段④换 raw 通道后
> 抓帧由 3.7s → 1.9s/帧，单轮随之降到 **20.8s**（同环境 PNG 组为 26.4s），其余分项未动。

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 抓帧 | 7.1s | 3~4 次/轮 × ~2.0s（含复位过程中的抓帧） |
| 全库定位 | 4.2s | 24 模板单尺度；**与 base 的 OCR 并行** |
| 点击与反应验证 | 3.8s | 含"点后等 1.2s 再抓帧"的稳定窗口 |
| 复位流程 | 8.4s | 内含它自己的抓帧与点击（与上面"抓帧"行**有重叠**） |
| **单轮总** | **21.2s** | 30 轮口径 21.5s |

> 各项之和大于总时间：定位与 OCR 并行（时间重叠）、复位段含抓帧（重复计入）。

⇒ 仍然**几乎全是工具侧取证/识别的固定开销**，游戏侧真正的交互（4 次点击注入）
本身不足 1 秒；表里"点击与验证"主要是**为确认结果而留的稳定等待窗口**。
所以"跑一轮 21 秒"不代表游戏卡，而是取证链条的开销。

**提速四阶段（判据全程未动）**：

| 阶段 | 手段 | 单轮 |
|---|---|---|
| 起点 | — | 55.8s |
| ① 去重复劳动 | 复用定位结果判态 / 帧差判态 / 复位复用点击后那帧 | 32.5s |
| ② 挪开 OCR 与定位 | `ocr -serve` 常驻（冷启动整批只付一次）+ base 的 OCR 与定位**并行** | **21.1s** |
| ③ 抓帧兜底 | 超时 60s / 慢帧丢弃重抓 / 新鲜度校验（**纯保险，不改速度**） | 21.1s |
| ④ 换抓帧通道 | raw 取帧 + 本地编码 PNG（绕开**设备端 PNG 压缩**） | **20.8s** |

> ⚠️ 阶段②的 21.1s 与阶段④的 20.8s **不是同一环境**：午间设备侧 PNG 编码从 2.0s 涨到
> 3.7s，**同一份代码**的单轮随之变成 26.4s。所以阶段④的效果要用**同环境 A/B** 来读
> （26.4s → 20.8s，-21%），**不能把 21.1s 与 20.8s 相减说"只快了 0.3s"**。

**阶段④的瓶颈诊断与对照**（这是本批最有价值的一段量化）：

| 通道 | 耗时 | 数据量 |
|---|---|---|
| `shell echo` | **86 ms** | — |
| `exec-out screencap -p`（PNG） | 3468 / 3724 ms | 2.93 MB |
| `exec-out screencap`（raw） | **1166 / 1278 ms** | **9.64 MB** |
| `shell screencap` 落盘 + `pull` | 4515 + 714 ms | — |

⇒ 链路本身很快（echo 86ms）；raw **多传 3 倍数据反而快 3 倍** ⇒
那 2.3s 全花在**设备 CPU 压 PNG** 上，与传输量无关。

| A/B（连续跑，各 12 轮） | raw | PNG | 差异 |
|---|---|---|---|
| 成功率 / 复位 | 12/12 · 12/12 | 12/12 · 12/12 | 一致 |

| **平均单轮** | **20.8 s** | 26.4 s | **-21%** |

> **定位耗时两组相同**，正是"环境没变、差异来自抓帧通道"的关键对照。

## 四个"给出漂亮假数据"的坑（都已修）

### 坑①：toggle 图标 + 盲点两次 = 帧差 0.00

该图标点一次开面板、再点一次关面板。早期默认**点两次** ⇒ 开了又关 ⇒
逐像素回到原状（帧差 **0.00**），看起来和"点击根本没发出去"一模一样。
判定实验（同一脚本内交替点、每步只点一次）：点地图中部 23.19、点目标 **18.42**、
再点目标**也是 18.42**（与起点同画面）。
⇒ 修法：**点一次 → 抓帧 → 帧差 <3.0 才补点一次**（自适应）。

> 附带更正：排查时我一度把这条假象归因于"沙箱拦截多层 python 调用"，
> 并据此改了 3 处代码 —— **那是错的**，真因只是两次对照实验的点击次数不同。
> 教训：拿"点不动"当结论前先固定点击次数做对照；诊断脚本一次只变一个变量。

### 坑②：自证式判据 —— 复位抓帧覆盖了基准帧

复位"是否已回到地图"用帧差与基准帧比，而复位自己的抓帧**与基准帧共用文件名**
（都不带轮次）⇒ 复位抓帧**覆盖**了基准帧 ⇒ 变成**自己跟自己比 ⇒ 帧差恒 0**
⇒ 永远判"已复位"。更糟：错误状态被下一轮当基准继承，**一路错且不报错**。
⇒ 修法：帧名按轮次隔离 + 同源比较直接返回 `None`（逼调用方走真判据）+ 阈值按语义收紧。

**这个坑只在"异常起点"测试里暴露** —— 正常起点连续跑 10 轮全 100%，
因为起点守卫那段代码**一次都没被执行过**。所以跑批必测两类起点。

### 坑③：自适应补点亲手把成功改写成失败（同一个 toggle 陷阱换了个马甲）

按坑①加了"首点没变化就补点"之后，多图标首版跑批里**皮卡月刊帧差 0.00 判"无反应"**。
它不是点不动，而是它的反应**本来就很小**（它是 toggle 名字标签，点一次只弹一个小标签）：

```
点一次 → 出标签（帧差 2.04）
       → 2.04 < 补点门槛 3.0 ⇒ 判"首点被吞" ⇒ 补点一次
       → 标签被收回 ⇒ 帧差回到 0.00 ⇒ 判"点了没反应"（与"完全没点到"一模一样）
```

⇒ 修法：门槛按**目标类型**给（面板类 8.0 / 标签类 1.5），且标签类**直接关掉补点**
（2.04 vs 1.5 只差 0.5，靠调门槛擦边不稳）。

> 通用教训：**凡"自动重试/自动纠错"的通用保护，作用在边缘目标上时，
> 优先怀疑它是不是在把成功改成失败**，而不是先怀疑链路坏了。

### 坑④：抓帧"兜底"把失败静默变成"拿到旧帧"

16 轮长测里有一轮单轮 64.8s，其中**一次抓帧花了 39.2s**（同轮其他抓帧 2.1s），
而且那帧帧差 **60.64**、与同目标其他轮的 30.98 明显不同 ——
**慢帧通常抓在画面过渡态上，内容不可信**。原实现只把耗时记进统计、不做兜底。

查这个问题的过程中，用离线单测又挖出一个**更隐蔽的真 bug**：抓帧函数在拿不到工具
回传路径时会兜底去读约定文件名 `<tag>.png`，而那是**同名复用**的文件 ——

```
抓帧失败 → 兜底命中"上一轮残留的旧帧" → 当成"本次结果"返回
        ⇒ 后续点击/复位的判据全建在旧画面上，rc=0、不报任何错
```

⇒ 修法三件（判据不变）：子进程超时 60s、单次 >8s 判慢帧**丢弃重抓一次**、
**新鲜度校验**（帧 mtime 必须晚于本次抓帧开始时间）。配套：被丢弃的慢帧挪到
`<tag>.png.slow`（否则下次失败时仍会被兜底捡回来）、被丢弃的耗时单独记账。

> 通用教训：**任何"文件/缓存/上次结果"式兜底，都要能回答"这份数据是不是本次产生的"。**
> 这类 bug 的共同特征：**不报错、指标还好看**，只有**把失败路径单独测一遍**才会露出来。

### 坑⑤：叠加层被误判成底层界面 ⇒ 成功率照样 100%

把起点故意留在**家园信息浮层**（点开家园图标后不回退）跑 12 轮，抓出一个真 bug：

```
轮 1  目标未在屏 ⇒ 未决       ← 起点明明是浮层，却没有任何"起点不在地图界面"的提示
轮 2  皇家招待所 定位 7 条 → 点(177,666) 帧差 17.94 → panel  复位OK(panel/map)
轮 3  目标未在屏 ⇒ 未决
汇总：目标在屏 10/12 · 成功率 100.0%（10/10）· 复位 10/12
```

**根因**：家园浮层是**盖在地图上**的，地图固有词没有消失 ——
判"是不是地图界面"用的两个词**在浮层上同样在屏**：

| 关键词 | 干净地图帧 | 家园浮层帧 |
|---|---|---|
| 卡洛西亚大陆（map 判据） | ✓ ×2 | **✓ ×2** |
| 精灵踪迹（map 判据） | ✓ 11/15 | **✓ 11/14** |
| 舒适度 / 当前居住精灵 / 当前种植植物 | ✗ | **✓** |

⇒ 两个 map 判据词**分不开**这两种界面；而三个浮层特征词在干净地图上**一个都不出现**。
状态判定的顺序里 `marker_edit`、`panel` 都排在 map 之前，**唯独漏了家园浮层**。

**后果是假绿三连**：起点守卫判 map ⇒ 不救；复位探测帧若落在浮层上 ⇒ 也判 map
⇒ **复位假成功**；而目标「家园」图标正被浮层盖住 ⇒ 未在屏 ⇒ 未决。
整套指标里**只有「目标在屏」露马脚，成功率照样 100%**（未决不计入分母）。

⇒ 修法：在 map 判定**之前**插一条叠加层判据（返回新态 `home_panel`），
复位状态机原有的"点一次 ✕"分支自动接管。**离线帧对照 + 真机复跑各 12 轮**验证：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 目标在屏 | 10/12 | **12/12** |
| 未决 | 2 | **0** |
| 复位成功 | 10/12 | **12/12** |
| 轮 1（起点是浮层） | 判 map ⇒ 未决 | **home_panel ⇒ 守卫点 ✕ 救回 ⇒ 成功**（46.2s） |

> 通用教训：**判据顺序必须是"先叠加层、后底层"**。凡是"盖在 A 上的 B"，
> 用 A 的固有特征去认 A，一定会在 B 出现时误判 —— 而且**症状是"一切正常"**。
> 配套心得：**"命中数"不能当界面判据，"锚点齐不齐"可以** ——
> 修复后命中数仍有 11 条 / 20~21 条两档（地图图标动态显隐），但两档都是干净地图、
> **都含两个固定 UI 锚点**；而修复前那个 11 条**没有「家园」**（被浮层盖住）。

## 下一步（按性价比）

1. **稳定性与提速都已有量化基线**：152 轮 100%、30 轮无漂移、四阶段提速到 20.8s/轮。
   继续跑批的价值只在**换条件**：别的区域（换视口/换地图层级）、别的分辨率、
   或**更多"叠加层"界面**（这次证明异常起点最出货——一个起点就抓出一个假绿 bug）。
2. **判据侧还可以更省**：本轮定位固定 3.6s（未动过）。缩小 ROI / 降采样模板匹配
   是下一个提速点，比继续抠抓帧更划算（抓帧已到 1.9s）。
3. **把"反应类型 + 退出路径"写进图标库**：退出策略仍硬编码在 `TARGETS` 表里，
   库里还没有 `reaction`（panel/label/marker/dead）与 `exit`（close/retap）字段。
4. **给状态判据补"反向用例集"**：本轮那条叠加层 bug 是靠人工造起点才暴露的。
   把「干净地图 / 家园浮层 / 区域面板 / 标记态 / 大世界」各存几张帧当**判据回归集**，
   以后改 `detect_state` 先跑一遍，比每次真机造起点便宜得多。
5. 图标库 8 条"单帧出现" + 2 条"未出现"待换帧补验。
