# 开发计划与方向评审 —— 校正记录

> 日期：2026-09-13
> 评审对象：`DEVELOPMENT_PLAN.md`（v 当前基线）、`outputs/game-sensei-学习能力开发计划.md`（v1.0 → v1.1）
> 触发问题：「是不是应该把所有游戏的玩法训到同一个模型上，靠玩游戏和看攻略视频加训，模型就会玩很多游戏？」
> 结论一句话：**大方向正确，但有 4 处需要纠正——其中 1 处是概念分层错误，2 处是计划里缺失的实测约束，1 处是两文档编号冲突。**

---

## 一、方向判断：哪些是对的

| 计划中的主张 | 判断 | 依据 |
|---|---|---|
| 以单游戏短任务闭环起步，不急于多游戏 | ✅ 正确 | 真机示范 60 条即 66.67%，而 1419 条弱标签恒 52.36%；瓶颈是标签质量，不是游戏数量 |
| 三层知识划分（通用 / 类型 / 适配） | ⚠️ 方向对，第 1 层定义错 | 见问题 1 |
| L1 语义动作 + L2 平台动作 + profile 适配 | ✅ 正确 | 换游戏只换 JSON，是唯一已验证的低成本适配路径 |
| 新增游戏的成功标准是「低成本适配并复用既有能力」 | ✅ 正确 | 但要注意「复用」指的是感知层与类型层，不含策略头 |
| 先评测后优化、真实证据优先、版本可回退 | ✅ 正确 | 与实测教训一致 |
| P0–P5（解忧梦幻岛纯点击任务链）不受观测架构限制 | ✅ 正确 | 该任务动作空间不含方向类 |

**关于「所有游戏训到一个模型」：一半对。** 该合的（跨游戏视觉理解）目前**还没被证明可合**；
不能合的（策略头）是**硬约束**。所以「一个模型玩很多游戏」目前是**目标**，不是**路径**。

## 二、发现的问题与已做校正

### 问题 1（最核心）｜`DEVELOPMENT_PLAN.md` §1.1 把「策略」误列为「通用能力」

**原文问题**：第 1 层「通用能力层（核心资产）」把 `角色控制、方向移动、目标追踪、资源管理、
战斗反应、探索、避障、任务执行、失败恢复` 与 `视觉理解、界面识别` 并列，统称「核心资产」。
但前者是**策略**：其输出维度绑定具体游戏的动作语义（同一输出维度在 A 游戏是「向前移动」，
在 B 游戏可能对应「点某个按钮」）。无条件混训会让梯度互相冲突，加速 mode collapse。

**这直接是「把所有游戏训到一个模型」这个直觉的来源**——因为文档把不可迁移的策略层
写成了可累积的核心资产。

**已改为**：
1. **通用感知层**（不含动作语义，唯一可跨游戏累积、可被无标签数据加厚）
2. **决策/策略层**（按游戏可分，不可无条件混训；跨游戏共用一个头必须先有 task id / game embedding）
3. **游戏类型层**（以文档与 hints 承载，**不直接等同于权重共享**）
4. **游戏适配层**

并补了一条通用化原则：**策略头不跨游戏混训**（属未验证假设，不是默认做法）。

### 问题 2｜计划缺少「观测架构上限」这条前置约束

**实测事实**（README §11.15）：`up/down/left/right` 的区别**在帧间、不在帧内**——
从零训到 400 epoch 都没能把 `up` 学起来，方向样本全挤进 `press`/`down`。
这是**架构上限，调超参无效**，必须换观测（帧差 / 帧对 / 短时序）。

**计划缺失导致的风险**：学习计划的 P6（洛克王国移动/导航）依赖方向类动作，
但文档未把「换观测」列为前置条件，容易被当成调参问题反复尝试。

**已补**：学习计划新增 §1.3，并在 P0–P7 路线图下加前置约束说明——
**P0–P5 不受影响**（解忧梦幻岛是纯点击任务，无方向类），**P6 被阻塞**，
进入前必须先完成观测改造并给出「方向类可学」的对照证据。
同时把 §6.3 的训练样本定义从「单帧」改为「观测窗口」，并要求格式预留帧差/帧对。

### 问题 3｜计划缺少「弱标签不得入训练集」的硬门禁

**实测事实**：视频判读的「操作」是推断值，判读报告自身声明不可作真值；
1419 条弱标签训两版学生，val_acc **恒定 52.36% / 63.49%**（等于各自众数类占比）＝ mode collapse。
而真机示范 60 条即 66.67%。

**原计划的缺口**：§15 禁止事项里有「使用无法确认来源的外部坐标或攻略作为真实验证」，
但**没有**禁止把推断出的动作当训练标签——而这才是实际踩过的坑。

**已补**：§6.3 数据质量规则 + §15 禁止事项各加一条，明确弱标签只能进 hints / 状态分类集。

### 问题 4｜两份文档的 P 编号体系冲突

`DEVELOPMENT_PLAN.md` 的 P0–P3 = 工程交付里程碑（P0 安卓闭环 / P1 数据与示范 / P2 训练与治理 / P3 飞轮泛型化）；
学习计划的 P0–P7 = 单游戏学习曲线阶段（P0 评测协议 … P7 泛化工程化）。
两套编号同名不同义，交叉引用时会混。

**已补**：学习计划头部加编号体系说明与对应关系，并明确「引用时必须带文件名」。

### 顺带修正

- `DEVELOPMENT_PLAN.md` §1.2 出现两次（1.2 通用化原则 / 1.2 硬边界）→ 硬边界改为 §1.3，
  新增实测边界为 §1.4。
- `outputs/game-sensei-游戏类型知识库.md` §二 把跨类型操作模式称为「通用能力层」，
  与新分层冲突 → 改为「跨类型操作模式（类型层）」。

## 三、新增的 §1.4 已实测的可迁移性边界（摘要）

写进 `DEVELOPMENT_PLAN.md`，防止后续把待验证假设当基线：

1. **跨域骨干迁移 = 0**。`video_v1`（视频域）在真机帧上直评 **0.00% 且恒输出 `tap`**。
   ⇒ 共享视觉骨干是**待验证假设**，不是既有资产；用视频必须先做域对齐（同分辨率、同 UI 布局）。
2. **单帧观测下方向类不可分**（同上问题 2）。⇒ 架构上限，换观测前不得把方向准确率列为可达成指标。
3. **弱标签会主动污染训练**（同上问题 3）。⇒ 禁止推断动作入训练集。

## 四、需要用户决策的事项（未擅自改动）

### 待决策 1｜是否把「观测改造」提前

当前学习计划把观测改造放在 **P6 之前**（即只阻塞洛克王国方向类任务）。
另一种选择是**提前到 P2 学生考试之后立刻做**，理由是：越早改观测，
后面所有采集数据的格式（单帧 vs 帧对）越统一，避免 P3–P5 采的数据在 P6 时作废。

两种取舍：
- **保持现状（推荐）**：先走完解忧梦幻岛的 R1–R3 纠错闭环，拿到「学会」的第一个真凭实据，再改观测。风险是 P3–P5 采的点击类数据在 P6 需要重采方向类部分。
- **提前改造**：采集格式一次性定型。风险是把焦点从「闭环跑通」挪开，可能再次陷入「改模型不改任务」。

### 待决策 2｜是否要做「共享骨干」的对照实验（P1 级）

现有 `--init` + `--freeze-backbone` 已具备做这个实验的工具，不需要改网络结构：
用 A 游戏权重去初始化训 B 游戏的头，看 B 的独立测试集是否优于从零训练。

但**前提是先解决域对齐**（问题 1 的 §1.4 第 1 条）——同分辨率、同 UI 布局的两款游戏
才构成有效对照。目前手上两款游戏（安卓横屏 2608×1200 / PC 竖屏 427×782）**域差太大，
直接做实验会得到「无迁移价值」的结论，但那只能说明域不对齐，不能说明骨干不可共享**。

⇒ 建议：**等第三款与其中一款同域的游戏接入后再做**，不要现在做。
