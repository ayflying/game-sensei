# 「资料 → 老师」落地清单

> 日期：2026-09-13
> 定位：这是「资料越多越聪明」在本项目**唯一能立刻兑现**的两处之一（另一处是无标签视觉预训练）。
> 目标：让攻略/文档等资料真正提升**老师**的决策质量，且成本为零训练、零 API 追加开销。
> 结论一句话：**机制已经存在（hints → 提示词），但缺分层、缺防护、缺门禁——三个缺口都有代码证据。**

---

## 一、现状：资料到老师的通路是通的，但很粗糙

资料进老师的唯一通路是**档案的 `hints` 字段**：

```text
profile.json 的 hints[]  →  internal/game/resolve.go:223  →  agent.ProtocolOptions.Hints
  →  agent.ActionProtocol() 拼进提示词  →  Ollama 老师
```

另有一条临时通路：`helper -demo-hints "a;b"`（`cmd/helper/main.go:489`），用于现场补先验。

**当前盘点的 hints 规模**（实测读取三个档案）：

| 档案 | 条数 | 总字符 | 战斗相关 | 大世界相关 | 两态都涉及 |
|---|---:|---:|---:|---:|---:|
| `profiles/nrc.json` | 18 | 2291 | **9 条 / 1610 字符** | 7 条 / 496 字符 | 2 条 / 185 字符 |
| `profiles/jieyou.json` | 10 | 753 | 0 | 10 / 753 | 0 |
| `internal/game/profiles/sparkle.json` | 7 | 292 | 0 | 7 / 292 | 0 |

> 分类为**关键词实测**（战斗/技能/捕捉/咕噜球/能量/逃跑/投球/回合/抓宠/出招/聚能/准星/球
> 命中即归战斗；摇杆/移动/传送/地图/坐骑/滑翔/游泳/任务追踪 命中即归大世界）。

`nrc` 是压力最大的样本，也是最有力的证据：

- **战斗类 1610 字符 = 全部 hints 的 70.3%**，但**大世界态完全用不上**；
  反过来大世界的 496 字符（摇杆位置、传送流程、坐骑滑翔）在战斗态也没用。
- 两态都涉及的那 2 条（`idx[5][6]`）恰恰是**界面态判据本身**
  （「两种界面必须先分清…」「战斗态下禁止 MOVE」）——它们**应该**两态都留。
  这说明分层设计是自洽的：把「态特有细节」收进对应态，把「态判据」留为通用。

⇒ **在大世界态，70% 的 hint 字符是无效负担**；9b 老师本就要在 `num_predict ≥ 1500`
的预算里完成思考，这部分先验直接稀释注意力。

## 二、三个缺口（均有代码证据）

### 缺口 1（结构性）｜`hints` 没有界面态分层，但按钮/宏已经有

**证据对比**：

| 项 | 是否支持 `state` | 位置 |
|---|---|---|
| 按钮 | ✅ `State string`（world \| battle） | `internal/game/profile.go:111` |
| 宏 | ✅ `State string` | `internal/game/profile.go:279` |
| 动作协议收窄 | ✅ `PressNamesForState(state)` | `internal/game/profile.go:743` |
| **hints** | ❌ **只有 `[]string`，无态** | `internal/game/profile.go:143` |

`internal/game/resolve.go:223` 是裸的 `Hints: p.Hints`——**无条件全量注入**。

**后果**：大世界态会拿到「战斗态禁止 MOVE」「出招只需一次 PRESS」「咕噜球分档」等
6~9 条完全用不上的先验。9b 老师本就要在 `num_predict ≥ 1500` 的预算里做思考，
一半先验是无效负担，直接稀释注意力。反过来战斗态会拿到摇杆位置与地图传送提示。

**改法**（仿照已有先例，不发明新机制）：为 hints 增加可选态，保持向后兼容——
`hints` 保持「两态通用」，新增 `hints_world` / `hints_battle` 由 `resolve.go` 按当前态合并。
**校验风格跟现有代码一致**：非法态值在加载时立刻报错（同 `normalizeState` 的做法），不静默忽略。

**成本**：中低（有 `State` 解析与校验代码可直接复用）。**风险**：低（纯注入裁剪，不改决策逻辑）。

### 缺口 2（防护不对称）｜视频判读侧已修，决策侧还没修

**证据**：`internal/video/annotate.go:146-157` 对 hints 做了**两段式防护**，注释写明了原因：

> 这条约束是实测逼出来的：档案 hints 里写了「点任务追踪文字可以自动寻路」，
> 结果 8 段里有 6 段的「策略」都在照搬这一句，连纯过场动画那段也不例外——模型把先验当成了答案。

做法是：hints 前加「**仅用于辨认画面元素，不要把这些说法直接当作结论**」+ 结尾再次强调。

**但 `internal/agent/parse.go:460-467` 的 `ActionProtocol` 没有任何防护**：

```go
if len(o.Hints) > 0 {
    b.WriteString("【界面先验】\n")
    for _, h := range o.Hints {
        b.WriteString("- "); b.WriteString(h); b.WriteString("\n")
    }
}
b.WriteString("\n【可用动作】每条一行，只输出一行：\n")   // ← 紧接着就是动作协议
```

值得注意：`ActionProtocol` **已经吸收过同类教训**（`:445-456` 明确写了「占位符里绝不能出现
具体坐标数字」「不要把摇杆四坐标写进协议」），**唯独 hints 这一段没有防护**。

**现存的具体风险点**（实测读取，本意是防误解、但含动作动词，有被照抄的可能）：

- `nrc` hints[2]：「…**点它不会自动寻路**（2026-09-12 用 tools/watch.py 实测…）」
- `jieyou` hints[8]：「左下角任务条…只是进度显示，**点它不是收获**」

这两条都是**否定句**。按 annotate 侧的实测，模型对先验的照抄不区分肯定/否定——
它看到的是「点 + 自动寻路」这个词组。

**改法**：把 annotate 的两段式话术移到 `ActionProtocol`。
**成本**：极低（两行字符串）。**风险**：需重测老师输出质量是否受影响（属提示词改动，必须实测）。

### 缺口 3（无门禁）｜hints 没有容量上限，也没有「加了有没有用」的验证

**证据**：`internal/game/profile.go` 的校验覆盖了字段名（`DisallowUnknownFields`）、
按钮/宏的 `state` 合法性，但**不校验 hints 的条数与单条长度**。

**后果**：
1. **线性膨胀**：按攻略持续追加会无限增长（`nrc` 已达 2291 字符），挤占提示词预算。
2. **无法归因**：加一条 hint 之后老师变好还是变差，现在没有任何机制能测出来。
3. **知识形态错配**：现有 hints 里混着对决策**无用**的内容。典型是
   `nrc` hints[12] 的抓宠成功率数值机制（「麻醉≈×1.5、睡眠≈×2、2~3 次必中」）——
   这是**数值知识**，对「这一帧该按什么」没有帮助，却实打实占着预算。
   同理 hints[13] 的咕噜球分档列表。

## 三、由此得出的「资料转换规则」（比改代码更重要）

攻略原文**不能直接拷进 hints**。按「这一帧该按什么」是否有用来分拣：

| 攻略内容的形态 | 能否进 hints | 理由与去向 |
|---|---|---|
| **画面元素是什么**（摇杆在左下、五个圆钮=战斗态） | ✅ 进 | 这正是 hints 设计的用途：帮模型认画面 |
| **可观测判据**（出招后 Δ<4 就是没生效；★N/10 是能量） | ✅ 进 | 把状态变成模型能验证的判据，价值最高 |
| **怎么做**（点任务追踪→寻路、先清弹窗再走） | ⚠️ 改写成判据才能进 | 直接写会被照抄成动作（annotate.go 实测）；应改写成「什么情况下该做什么」的**条件式**，或直接转成 `macros`/`-plan` |
| **数值与概率**（成功率 ×1.5、球分档） | ❌ 不进 | 对单帧决策无用、纯占预算；进知识库文档 |
| **坐标** | ❌ 不进 hints | 一律放 `buttons[].pos`（一份，防漂移），hints 里出现坐标会被照抄 |
| **单游戏玩法/剧情/关卡** | ❌ 不进仓库 | 按归档分界进 ima 知识库 |

**一句话**：hints 存的是**「怎么认」**，不是**「怎么玩」**。`macros` 与 `-plan` 才是存「怎么玩」的地方。

## 四、建议动作（按成本/风险分三档）

### 档 1｜补 hints 防护话术（立刻可做，成本极低）

`internal/agent/parse.go` 的 `ActionProtocol`：在 `【界面先验】` 后加约束行，动作协议前再收一次
（照抄 `annotate.go:147` 与 `:157` 的两段式）。

**验收**：单测断言协议文本包含防护话术；**真机跑一段**看老师是否还会输出 hints 里描述的字面动作。

### 档 2｜hints 按界面态分层（低成本，有先例可抄）

新增 `hints_world` / `hints_battle`，`resolve.go` 按态合并；非法态值加载即报错。
把 `nrc` 的 9 条战斗先验（1610 字符）迁到 `hints_battle`。

**验收**（注意：当前**没有**现成的协议打印入口）：
`cmd/helper/main.go:105` 只打印 `界面先验: %d 条`（条数，不含内容、也不反映按态收窄）。
`ActionProtocol` 的实际消费点只有 `internal/teacher/demonstrator.go:293`。
因此验收需要**先补一个协议打印入口**——建议加 `-print-protocol` flag（不截屏、不送审，
打印最终协议全文后退出），既能验收本条，也是后续档 1/档 3 的通用验证手段。

验收标准：世界态协议**不含**战斗条目（战斗类字符数应降到 0）、战斗态**不含**摇杆/传送条目；
两态均保留 `idx[5][6]` 这两条界面态判据；真机各跑一段确认老师动作空间未被抖散。

### 档 3｜容量门禁 + A/B 验证流程（需设计）

1. 加载时校验：单条长度上限、总条数上限，**超限报错**（与项目「拼错立刻报错」风格一致）。
2. 新增 hint 的 A/B 流程：同起始画面、同 seed，对比老师动作序列是否变好；无证据不入库。
3. 按 §三 的转换规则，把 `nrc` hints[12]/[13] 这类数值知识迁出到知识库文档。

**验收**：一份 A/B 报告 + 一份 hints 瘦身前后的协议长度对照。

## 五、明确不做

- **不引入向量检索 / RAG**。当前 hints 规模是**几千字符**，全量注入的 token 成本远低于
  引入检索的复杂度与不确定性。**RAG 要等 hints 上万字符规模才值得考虑**——先做分层与门禁，
  把规模问题暴露出来再说。
- **不把攻略原文成段拷进 hints**（理由见 §三，且 annotate.go 的坑已验证照抄风险）。
- **不改 teacher 的异步架构**（`DEVELOPMENT_PLAN` §1.3 硬边界：教师不得阻塞实时回路）。
- **不在没有 A/B 证据的情况下批量追加 hints**（等价于「堆数据＝提升」的错觉，本项目已吃过一次）。
- **不把这套 hints 机制与「让策略头学会新游戏」混为一谈**——资料对策略头是间接作用，
  中间「采真机示范」省不掉。
