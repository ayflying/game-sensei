## 二、玩家时间都花在哪（玩法权重实证）

由 4,118 帧的界面分类统计（按时间序**连续采样**，可近似代表时间占比）：

| 界面类型 | 帧数 | 占比 |
|---|---|---|
| 大世界探索 / 其他 | 1,927 | **46.8%** |
| 任务 / 手册 / 作业面板 | 1,112 | **27.0%** |
| 战斗 | 292 | 7.1% |
| 剧情对话 | 230 | 5.6% |
| 队伍宠物 / 精灵详情 | 222 | 5.4% |
| 商店 | 87 | 2.1% |
| 角色属性 | 68 | 1.7% |
| 家园 | 67 | 1.6% |
| 背包仓库 | 42 | 1.0% |
| 地图 | 33 | 0.8% |
| 捕捉 | 21 | 0.5% |
| 登录加载 / 设置 | 17 | 0.4% |

**结论（对自动化策略的直接指导）**：

1. **这不是一款以战斗为核心的游戏。** 战斗只占 7%，大世界跑图 + 任务面板合计 **73.8%**。传统"找怪→进战斗→打怪升级"的思路在这里权重极低。
2. **任务/手册面板是第二高频界面（27%）**，说明大量时间在**读任务、对进度、开手册**。对 AI 来说，"识别当前课题与进度"比"打赢一场战斗"更有价值。
3. **捕捉界面只有 0.5%** —— 捕捉动作本身极短（在大世界直接投球，无需进战斗），这从数据层面印证了此前"大世界直接丢球、不必进战斗"的结论。

## 六、系统全清单

### 6.1 对战系统

入口：左上角功能栏 `对战系统` (0.117, 0.046)；子页 `星光对决` (0.126, 0.082)。

**星光对决「养成同步」机制**（`P127_f00124` 原文）：

> 参加星光对决精灵的等级、成长次数和成长值会被**重置为精灵盒子中精灵的最高养成水平**
> 仅展示本周捕捉的精灵

⇒ 这是**公平竞技规则**：参赛精灵会被拉平到盒子里的最高水平，且**限定本周捕捉的精灵**才能参赛。含义：想打星光对决必须**本周有新捕捉**，且不必单独培养。

对战界面窗口（`P127_f00123` / `P127_f00137` / `P129_f00083`）：显示 `0/12`、`6/12`、`伍欢呼声xN`（应为队伍欢呼声）、技能条与数值（60/85/130 等）。

**养成机制原文实证**（自动化刷资质/血脉前必读）：

- **「赐福」继承机制**（`P004_f00005`，孵蛋定向养成的核心）：
  > 「被赐福后，**新生的精灵**将**完美继承赐福精灵的性格、特长以及个体资质种类**」
  > 「核心特质可以继承，但**个体资质的具体数值仍然会随机生成**，不会受到赐福精灵影响」

  ⇒ 新生精灵不是纯随机：**赐福可锁定 性格+特长+资质种类，数值仍随机**。想要特定性格/资质种类的精灵，走「赐福→孵蛋」而不是反复野外捕捉。

- **血脉系统**：
  - `P017_f00109`：「能唤醒血脉力量的**远古秘药**，使精灵获得恶系血脉」⇒ **血脉可用道具修改/添加**
  - `P036_f00097`：「『污染』血脉恢复为正常血脉」⇒ 血脉有污染态，可复原
  - `P007_f00004`：「某些**共鸣魔法**可以作用于特定血脉的精灵」⇒ 共鸣魔法×血脉有配合关系
  - `P102_f00007`：「双系甚至多系血脉的后代，其后代还可以学习多重（技能）」⇒ **血脉随繁殖遗传给后代**
- **个体资质**：
  - `P024_f00007` / `P187_f00060`：「可以**修改精灵的个体资质种类**，或激活一条初始值」⇒ 资质种类可用道具改
  - `P045_f00005`：「对**初始个体资质小于 10** 的精灵使用，使该项个体资质的初始值**增加 1**」⇒ 低资质可被道具逐点拉高
- **性格**：`P103_f00017`「确定选择这只精灵的**性格**为胆小吗？」⇒ 性格**可主动选择**（不是捕获即固定）

- **果实澄清**：`P008_f00017`「野外获得的『精灵果实』**不能投喂精灵获得经验**，但有许多妙用」⇒ 投喂经验的果实与野外采集果实是两种东西

## 十二、VLM 画面语义判读（OCR 之外的第二只眼）

**方法**：从 4,118 代表帧分层抽样 240 帧（「其他」类 OCR 盲区占一半名额），本地 `qwen3.5:9b`（think=false）逐帧判读界面类型/画面内容/可点元素/动态状态。成功 236 / 失败 4，平均 **3.3 秒/帧**（模型驻留显存后）。脚本 `.workbuddy/nrc/video_learn/vlm_judge.py` + `vlm_summary.py`，结果 `F:/nrc-roco-video/vlm/`。

### 12.1 纯画面视角的界面分布（与 OCR 版互相印证）

| VLM type | 占比 | 对照 OCR 版 |
|---|---|---|
| 大世界 | 41% | 46.8%（方向一致） |
| 对话剧情 | 17% | OCR 大量剧情帧落在「其他」 ⇒ **剧情实际占比被 OCR 低估** |
| 战斗 | 10% | 7.1% |
| 家园 | 8% | — |

⇒ 两条独立测量路线得出同一结论：**这游戏的主循环是「跑图 + 剧情/任务」，不是战斗**。

### 12.2 动态状态分布（自动化关键参数）

- 静止 47% / 移动 41% / 战斗 8% / 过场 1% / 捕捉 <1%

⇒ **实时操作强度低**：玩家近一半时间站着（读任务、对话、摆 UI），移动占 41%。对自动化意味着：
1. **低帧率抓帧（5FPS）完全够用**，无需提高采样；
2. 帧间画面变化慢 ⇒ `plan` 引擎的 `ratio/change` 判据容忍度可以放宽，误判重试成本低；
3. 战斗占比小 ⇒ 通用自动化不必优先优化战斗性能。

### 12.3 VLM 补充的非文字坐标（OCR 永远抓不到的元素）

### 12.4 OCR 盲区被纠正的地方

交叉表（OCR screen → VLM type）：`其他 → 大世界 61 帧`、`其他 → 对话剧情 20`、`其他 → 战斗 19`、`其他 → 家园 9`。
⇒ OCR 的「其他」类（无文字/文字不合规则）**约 2/3 其实是大世界画面与剧情对话**。后续用 OCR 数据做界面统计时，「其他」类不能当噪声丢弃，应结合 VLM 或上下文再归属。

### 12.5 已知局限

- VLM 输出坐标偶发越界（如 0.92 写成 9.2），汇总脚本已过滤 >1.0 的坐标；
- 4 帧失败（HTTP 500 / JSON 解析失败），不影响整体分布；
- 界面类型是 VLM 主观归类，边界帧（如「背包→对话剧情」交叉 4 帧）存在噪声，取分布趋势而非单帧结论。
