# YoYa Star: On Air 实战：plan 线档案、广告干扰与「判据自身正确性」（原 §12.11~§12.15）

本册承接 `docs/plan-engine.md`（引擎语义）与 `docs/plan-sparkle.md`（第一款游戏的实战）。这里是**第二款游戏**（同厂同域、`com.yoyaworld.dressup.makeup.asmr.cosplay.fashion.style` v1.5）在**本机真机**（小米 MIX 3 / 1080×2340 / Android 10）上的落地记录，档案是 `internal/game/profiles/yoyastar.json`（14 步）。

> 本册的重点不是「又跑通一款」，而是**判据本身也会错**：一次「双向一致 4/4」的漂亮结果里藏着一个假判负。§12.13 是这次事故的完整复盘。

## 12.11 本作结构与「终点必须停在结算页」的由来

确定性主循环（真机实测）：

```
房间主界面 --点 PK CONTEST(0.678,0.845)--> THEME 页 --点 Start(0.500,0.794)-->
matching(约 11~17s) --> 选装卡片(三选一，点即确认) --> PK 演出/评审 --> 结算页(VICTORY / FAIL)
```

四条已实测的硬约束（每一条都直接决定了档案怎么写）：

1. **PK 全程是同一个场景**：两个角色 + 顶部票数条（左粉右蓝渐变）+ 观众评论一直在，**三张选装卡片只是叠加在场景底部**。所以「卡片消失」只能判「离开了选装页」，**绝不能判「到了结算页」**（广告页与 PK 演出页同样没有卡片）。
2. **一局 PK 实测 2 关**（已完成样本 6/6 都是 2 关），综合内容随主题变；但关卡数**不是硬保证**（返回键实测能把卡片重新调出来）。档案用 4 个同构的「选装关」步串起来，每步都带「卡片可见」的 `when` ⇒ 有卡片才点、无卡片整步跳过，1/2/3/4 关都自适应且不会多点。
3. **结算页文案是 VICTORY / FAIL**，不是 WINNER / LOSE。
4. **结算页（已领奖态）拒绝一切注入输入**：Home tap / +POST / 返回键 / mouse source 全被吞（Δ≤4.8），而同页「未领奖」态的 `NO Thanks` 可点（Δ≈90.8）；前台确认是游戏本体、mAwakefulness=Awake、渲染在动 ⇒ **只认真人触摸**。
   ⇒ plan 的终点**刻意停在结算页**，复位交给跑批框架外部冷启动（`am force-stop` + `monkey` ≈25~30s，爱心进度持久化不丢）。这与 Sparkle 的 `restore.py` 是同一个模式。

### 18 步档案结构（`yoyastar.json`，2026-09-16 晚起含 4 个选装前缓冲步）

| # | 步骤 | when（入口守卫） | until（推进判据） | 说明 |
|---|---|---|---|---|
| 1 | 点 PK CONTEST | — | THEME 深色带 ≥0.30 | 8s / strict / 补按 2 轮 |
| 2 | 点 Start | THEME ≥0.30 | 选装卡 ≥0.35 | 45s，等 matching |
| 3 | **选装前缓冲·等 1s** | — | —（`gap_ms=1000` 固定等待） | **2026-09-16 二次修复**：页面刚加载的注入点击会被吞（s30~s34 实据），先等交互就绪再点；WAIT 无副作用、幂等 |
| 4 | 选装·第 1 关 | 选装卡 ≥0.35 | 卡 ≤0.20 | `max_repeat 5 / gap 2s / 16s`，首点约 t=1s，点击序列 ≈1/3/5/7/9s |
| 5 | 清广告·A | 票数条 <0.05 | 票数条 ≥0.15 | `max_repeat 3`，**唯一允许按返回键的步** |
| 6~13 | [缓冲+选装关 2/3/4] 与清广告 B/C/D 交替 | 同上 | 同上 | 同构、幂等 |
| 15 | 等结算页 | — | VICTORY 大字 ≥0.07 | 45s，宽松吸收 PK 演出；**不配 on_timeout** |
| 16 | 败局闸门 | **票数条 ≥0.10**（见 §12.13） | 金冠 ≤0.005 | 1.5s / **strict：主动判负** |
| 17 | 终末守卫 | 选装卡 ≥0.35 | 卡 ≤0.20 | 1.5s / strict：堵「停在选装页」的假胜 |
| 18 | 胜负判定 | — | VICTORY 大字 ≥0.07 | 8s / **strict，且刻意不带 when** |

两条设计决定值得单独记：

- **第 14 步绝不能带 `when`**：带 `when` 的步在条件不成立时会**整步跳过、plan 照样以退出码 0 成功结束**——那会把「根本没走到结算页」记成成功（假成功）。诚实闸门必须无条件执行，靠 `strict` + 超时失败暴露问题。
- **第 13 步是「堵假胜」的最后一道门**：白色主题（Plush Core）的选装页会把判胜区白像素顶到 26.5%（> 阈值 7%，8 个选装帧里 1 个），所以判胜步必须能在任何画面上求值的同时被这道守卫拦下。

## 12.12 判据标定值与分离度（含广告帧）

全部判据都是「区域 + 目标色 + 每通道容差 + 占比阈值」，引擎语义见 `docs/plan-engine.md`。**单位：区域内命中像素占比**。

| 判据 | 区域 | 目标色 | 容差 | 结算 VICTORY | 结算 FAIL | PK/匹配 | 选装页 | 广告 | 主界面 | 阈值 |
|---|---|---|---|---|---|---|---|---|---|---|
| VICTORY 大字 | `[0.14,0.15,0.86,0.20]` | `(255,255,255)` | 4 | **11.6~12.3%** | 2.8% | 4.0% | 0.0% | 0.0~3.7% | 3.6~4.5% | ≥0.07 |
| 金冠（判负） | `[0.84,0.022,0.915,0.065]` | `(255,200,60)` | 45 | 0.0% | **4.4%** | — | — | **14.5%（假象！）** | — | 判「在场」 |
| 选装卡可见 | `[0.15,0.73,0.85,0.80]` | `(238,241,245)` | 10 | 0.0~3.4% | 0.0~3.4% | 0.8~2.3% | **51.1~68.7%** | 0.0~1.6% | 2.3% | ≥0.35 / ≤0.20 |
| 票数条（场景探测） | `[0.20,0.09,0.50,0.115]` | `(255,140,250)` | 50 | 34.4~50.5% | **17.7~33.0%** | 39.4~58.0% | 41.4~53.7% | **0.0%** | 0.7% | <0.05=异常页 / ≥0.10=在结算页 |
| THEME 深色带 | `[0.14,0.10,0.86,0.15]` | `(19,19,19)` | 12 | — | ≤15% | — | — | — | — | ≥0.30 |

几条用血换来的注释：

- **判胜只用「VICTORY 大字」，不要用皇冠**：VICTORY 时皇冠在**左上**（`[0.045,0.022,0.120,0.065]`，实测 4.0%，但只有 4/6 个胜局帧命中，不稳定）；右侧金冠 = 对手赢。
- **不要用「白像素」判选装页**：白色主题的熊会把大字区白像素顶到 26.5%，高于 VICTORY 的 12%，会误判成胜。卡片灰 `(238,241,245)` 与纯白差 17 > 容差 10，天然免疫。
- **票数条是本作最有用的「场景探测」判据**：广告 0.0% / 主界面 0.7% / THEME 0.0%，而所有 PK 相关页面都在 17% 以上 ⇒ `when: 票数条 <0.05` 就是「现在不在 PK 场景、按返回键才安全」的形式化表达。它也是 §12.13 那个修法的支点。

## 12.13 ⚠️ 事故复盘：广告的黄色块让「金冠判据」假判负（2026-09-15）

### 一、现象

4 轮连跑（b01~b04）的结论表**看起来完美**：

```
b01 rc=1 FAIL ; 独立 FAIL ; 一致 ✓      b03 rc=1 FAIL ; 独立 FAIL ; 一致 ✓
b02 rc=0 WIN  ; 独立 WIN  ; 一致 ✓      b04 rc=1 FAIL ; 独立 FAIL ; 一致 ✓
```

胜负 1:3，**双向一致性 4/4**。但 b04 是错的。**它的终态帧根本不是结算页，而是一条插屏广告**（第三方休闲游戏 "Pizza Ready" 的落地页，顶部还挂着 rewarded 广告的 "Reward granted"）。截图存档：`.workbuddy/yoya-star/runs/20260915-221210-b04/end.png`。

### 二、错在哪：判据被广告的色块骗了

金冠判据的区域是顶部右侧 `[0.84,0.022,0.915,0.065]`、目标色亮金 `(255,200,60)` 容差 45。**广告顶部右侧正好是一大片黄色**，于是：

| 帧 | 金冠区域占比 | 票数条 | 真实情形 |
|---|---|---|---|
| b01（FAIL） | 4.4% | 33.0% | 真败局 |
| b03（FAIL） | 4.4% | 17.7% | 真败局 |
| **b04** | **14.5%** | **0.0%** | **插屏广告（黄色块）** |
| v1 / v2 / b02（WIN） | 0.0% | 35.4~49.7% | 真胜局 |

广告的黄色比真 FAIL 的金冠**还多**（14.5% vs 4.4%）。

### 三、为什么「双向一致」没能拦住它

因为 plan 与外部复算脚本**读的是同一条判据**（都从档案 JSON 读同一组 region/color/tolerance）。两边算出的数一样、结论一样，于是「一致性」评分满分。
⇒ **「双向一致」只证明「同一条判据在两边算出同一结果」，不证明判据本身对。** 一致性是防「解析/口径漂移」的，不是防「判据错」的；判据的正确性必须单独与**反例帧**（广告、其他页面）比分离度。

### 四、为什么调参救不了

拿同一批帧做分离度扫描（脚本 `.workbuddy/yoya-star/phone/sep_scan.py`）：

| 候选 | FAIL 帧 | 广告帧 | 结论 |
|---|---|---|---|
| 原区域 `[0.84~0.915, 0.022~0.065]` t45 | 4.4% | **14.5%** | 广告更高 ✗ |
| 放大区域 `[0.855~0.935, 0.030~0.072]` t45 | 12.2% | **29.1%** | 广告更高 ✗ |
| 同上、容差收到 25 | 4.9% | 9.7% | 仍分不开 ✗ |
| 白字「FAIL 字箱」`[0.32~0.68,0.14~0.23]` t4 | 4.2~4.6% | 0.0% | **但胜局 8.6~11.2%、另一张页 9.4% ⇒ 分不开 FAIL/胜** ✗ |

区域、容差、「换用 FAIL 大字」三条路都试过，全都不行。根因：**金冠是一个「小图标」特征，而广告是一整块任意创意**——只要广告创意里有相近颜色，小图标特征就必然被压过去。

### 五、结构性修法：把「在结算页」变成闸门的入口守卫

引擎的 `when` / `until` **各只能有一个判据**（`MinRatio` 与 `MaxRatio` 还互斥），没有 AND 组合。所以不是"加个条件"，而是**换一个判据在链路上的位置**：

```jsonc
// 改前：入口守卫 = 金冠（广告也会命中 ⇒ 假判负）
"when":  { "region": [0.840,0.022,0.915,0.065], "color": [255,200,60], "tolerance": 45, "min_ratio": 0.02 },
"until": { "region": [0.840,0.022,0.915,0.065], "color": [255,200,60], "tolerance": 45, "max_ratio": 0.005 }

// 改后：入口守卫 = 票数条（广告 0.0% ⇒ 整步跳过，金冠判据根本不在广告上求值）
"when":  { "region": [0.200,0.090,0.500,0.115], "color": [255,140,250], "tolerance": 50, "min_ratio": 0.10 },
"until": { "region": [0.840,0.022,0.915,0.065], "color": [255,200,60], "tolerance": 45, "max_ratio": 0.005 }
```

语义变化很关键：**金冠从「入场券」变成「必须在限时内消失」**。

- 真 FAIL 结算页：票数条 17.7~33.0% ⇒ 入口成立；限时 1.5s 内金冠不会消失 ⇒ `strict` 主动失败、退出码 ≠ 0 ⇒ **机器可读的判负** ✓
- 正常胜局结算页：入口成立（34.4~50.5%）；金冠 0.0% ⇒ 立刻通过 ⇒ 继续走第 13/14 步判胜 ✓
- 插屏广告：票数条 **0.0%** ⇒ **整步跳过**（`when` 不成立只跳过、不报错）⇒ 不再假判负 ✓
- 主界面（票数条 0.7%）：同样整步跳过 ✓

### 六、外部复算脚本同步收紧：FAIL 必须双证据

`plan_round.py` 的独立判定改成：

```
FAIL  ⟺  金冠在场  AND  票数条 ≥ 入口门槛（确实在结算/PK 页）
WIN   ⟺  VICTORY 大字 ≥ 0.07
```

对 7 张历史终态帧做离线回归（`plan_round.py --frame`，判据仍全部从档案 JSON 读、脚本不硬编码）：

| 帧 | VICTORY | 票数条 | 金冠 | 修正后判定 | 修正前判定 |
|---|---|---|---|---|---|
| w1 | 0.0% | 0.0% | 0.0% | UNDECIDED（广告） | UNDECIDED |
| v1 / v2 / b02 | 12.1~12.4% | 35.4~49.7% | 0.0% | WIN | WIN |
| b01 / b03 | 2.8% | 17.7~33.0% | 4.4% | FAIL | FAIL |
| **b04** | 0.0% | 0.0% | 14.5% | **UNDECIDED（广告页金冠假象）** | ~~FAIL~~ ✗ |

### 七、残余风险（如实记录）

- 票数条入口门槛 0.10 的样本只有 3 个 FAIL 帧（33.0 / 17.7 / 广告 0.0）。若某局玩家票数极低（左侧粉条极短）导致入口不成立，该局会退化为「未决」而**不是**误判成胜 ⇒ **方向安全**。
- 金冠判据仍会在「PK 演出」页上求值（演出时票数条 ≥0.10）。若演出动画在顶部右侧闪过足够大的金色元素，存在误判负的理论风险；本批未观察到，待更多局数验证。

## 12.14 跑批口径与统计脚本的两个坑

跑批框架：`.workbuddy/yoya-star/phone/plan_round.py`（单轮）与 `batch_plan.py`（N 轮）。两者**共用同一份 `verdict()`**，所以离线回归样本与实际判定同源，不会漂移。

- **每轮的证据必须落盘**：`runs/<时间戳>-<tag>/` 下有 `plan.log`、`start.png`、`end.png`、`result.json`。`end.png` 是**独立抓的终态帧**——它是「这一轮到底发生了什么」的唯一物证（b04 能查出问题全靠它）。
- **⚠️ 汇总字段不要用正则猜 stdout**：上一版 `batch_plan.py` 把「独立判定」的正则写成必须紧跟 `>>>`，而实际行是 `>>> plan 自报 = FAIL ; 独立判定 = FAIL`，于是汇总表整列变成 `?`、退出码还错拿了 Python 自己的 0 ⇒ **单轮结论是对的、汇总表整张是错的**（表面看像「WIN=0 FAIL=0 未决=4」）。现在汇总优先读 `result.json`（有 schema），stdout 仅作兜底。
- **统计口径**：WIN / FAIL / UNDECIDED 三分类；**未决不计入胜率分母**（广告拦截属于环境未决，不是判错）；一致性（plan 自报 vs 独立复算）单独报，且按 §12.13 的教训，一致性**不能当作判据正确性的证据**。

### 环境限制：会「粘住」的插屏广告

结算前后会插播第三方广告（`com.google.android.gms.ads.AdActivity`，挂在本游戏包名下），且**广告不会自动消失**。绝大多数创意按返回键能干净关掉（返回后前台变回 UnityPlayerActivity、票数条回到 39%）。

但有一次（b04 那条 "Pizza Ready" + "Reward granted"）**返回键完全无效**：跑批结束后 11 分钟复查，前台仍是 `AdActivity`，返回键按了 3 轮也没关掉。此时这一局的结局不可知 ⇒ 记「未决」，靠外部 `am force-stop` 复位。
⇒ 处置原则不变：**只在票数条 <0.05（确认不在结算/PK 页）时才按返回键；绝不在广告区域内点坐标**（点广告角落会命中「跳转应用商店」热点，且该 Activity 挂在游戏包名下、前台包名检查拦不住）。

### 汇总（档案定稿后全部 11 轮：v2 + b01~b10）

| 口径 | WIN | FAIL | 未决 | 已判定胜率 | 一致性 |
|---|---|---|---|---|---|
| 全部 11 轮 | 3 | 5 | 3 | **3/8 = 38%** | 11/11（但 b04 的一致是「同错」，见 §12.13） |
| 修正后重算（含把 b04 纠正为未决） | 3 | 4 | 4 | **3/7 = 43%** | 11/11 |

三条要点：

1. **判据②（连续 ≥10 次 WINNER ≥80%）不满足**（实测 33~43%），与 Sparkle 同因：本作胜负由**内容**决定（要选到与主题匹配的造型），属**决策·策略层**——`-plan` 是执行层，只保证「选了什么就执行到位」。⇒ 与 Sparkle 同样**以 ①③④⑤ 收尾**，胜率作**基线**如实记录，不粉饰、不刷局数。
2. **未决全部集中在样本后段（b08/b09/b10 连续三轮）**，形态与 b04 一致：**插屏广告粘住、返回键清不掉**、票数条恒为 0.0%。这 5 轮里广告出现 5 次（b06~b10 全有），**说明广告触发率本身在波动**——这是**环境未决，不是 plan 缺陷**：plan 对此的表现正是设计所要的（**退出码非 0 + 结论记「未决」，绝不误判成胜或负**）。
3. **一致性 6/6 的含金量已在 §12.13 讲清**：它是「两边用同一判据算同一结果」的证据，**不是判据正确性的证据**。本轮真正证明「修法有效」的是 **b04 帧离线回归从 FAIL 纠正为 UNDECIDED**，以及 b08/b09/b10 三局在真机上被诚实记为未决（旧口径下，只要广告创意带近似金色就会假判负）。

### ️ 顺带发现：结算页有**两种版式**，票数条只覆盖其中一种

矩阵里「胜局结算 6 帧」中有 2 帧（`p7` / `o4`）票数条读数只有 **1.4% / 1.8%**，一开始被当成异常帧。用判据数值分类后确认它们**确实是胜局结算页**（VICTORY 白 12.1% / 11.6%），只是**顶部没有票数条**：

| 帧 | VICTORY 白 | 票数条粉 | 选装卡灰 | 判定 |
|---|---|---|---|---|
| `p5` / `r4` / `5_1_res` | 12.0% | **47.9~50.5%** | 0.0~3.4% | 胜局结算（**带票数条**版式） |
| `p7` / `o4` | 11.6~12.1% | **1.4~1.8%** | 0.1~0.5% | 胜局结算（**不带票数条**版式） |
| `o3` / `p6`（广告） | 0.6~3.7% | 0.0% | 0.0~1.6% | 广告 |

两个后果，如实记录：

1. **入口门槛 0.10 会把这版结算页排除在「败局闸门」之外**。方向安全（跳过 ⇒ 不会误判负；败局只会退化成「未决」，而第 14 步仍会因「无 VICTORY」报错），但**这版版式的败局拿不到「机器可读判负」**。没有刻意下调门槛去覆盖它——因为现有 4 个广告帧的票数条都是 **0.0%**，门槛一旦降到 1% 附近，广告的粉色像素就会重新把金冠判据放进来，**正好复现 §12.13 的事故**。⇒ **宁可少判一次负，也不要多判一次错**。
2. **若「清广告」步在这版结算页上求值，`when`（票数条 <0.05）会成立 ⇒ 会按返回键**。步序上不会发生（清广告步全部在第 11 步「等结算页」之前，那时还在 PK 演出/广告阶段），但这是典型的「判据在别的页面也为真」风险，与 `docs/plan-engine.md` 里那条方法论同源。**不要重排步序把清广告步挪到第 11 步之后。**

**方法论沉淀**：跑批（真机路径覆盖）与矩阵（全页面设计覆盖）**互补**，缺一不可；且矩阵能发现「判据漏掉某一版式」这类跑批永远不会暴露的问题（因为跑批只会走到它遇到的那一版）。

### 12.17 训练样本自动采集与学生模型首训（2026-09-16）

**目标**：把「跑批」升级为「边跑边攒训练数据」，打通 采集→训练→Go 加载→Decide 全链路。

**采集（`plan_round.py` 内置，默认开启，`--no-trainset` 关闭）**：
- plan 执行期间后台线程每 2.5s 旁路抓一帧（`exec-out screencap -p` → 540 宽 JPEG），存 `runs/<轮>/stream/`；失败静默跳过，绝不影响跑批。
- 跑完后按判据（从档案读）把帧流打包成 `trainset/<tag>/trajectory.jsonl + frames/`——**格式完全对齐 `trainer/train.py` 的 `load_demos`，训练器零改动**：
  - 选装页帧（卡片灰 ratio≥0.35，按时间断隔 >8s 聚段=按关卡切）→ `kind=tap, nx/ny=档案 pick 按钮坐标`（有坐标监督）；
  - 非选装页帧抽样（≤2× 正样本数）→ `kind=none`（学「不该点」）；
  - 每行附 `label`（本轮 WIN/FAIL/UNDECIDED），train.py 忽略之，留给将来偏好加权。
- 实测 5 轮（s01~s05）：33 样本（tap 11 / none 22），label 覆盖 WIN/FAIL/UNDECIDED。

**首训（`trainer/train.py --data trainset --recursive`）**：
- 新增 `--override-class-weights` 参数：默认 CLASS_WEIGHTS 按「老师示范 none 占大头」设计（tap 1.5/none 0.5），与跑批采集的分布相反 ⇒ v1 塌缩全猜 tap（val_acc 33% < 基线 67%）。v2 用反比权重（tap=2/none=1）后反向塌缩到 none（66.7% = 恰好基线）。
- **坐标头真实收敛**：tap 坐标误差 0.163→0.01，Go 侧 Decide 输出 (0.508,0.768) vs 标签 (0.5,0.782) 误差 ~0.02。
- **分类头无决策力（如实记录）**：33 样本、none 大半是 PK 演出页（与选装页视觉接近），64×48 灰度 3 层 CNN 分不开。**v2 权重=链路验证版，不是能力交付**。提升路径：①STREAM_INTERVAL 降到 1.2s 多抓选装帧 ②样本 100+ 后重训 ③必要时彩色输入（改网络）。

**链路证据**：`go run ./.workbuddy/stucheck models/yoyastar_pick_v2.weights.json <帧...>` 加载+推理全通（val_acc=0.67, hidden=64）。

**v3 重训与策略转向（同日）**：抓帧间隔 2.5s→1.2s 后 6 轮再采（s06~s12，判据全部判定正确），总样本 77（tap 27/none 50）。v3 重训结论：**分类头仍塌缩**（选优 val_acc=66.7%=多数类基线，tap 召回 0；坐标头误差 0.015 持续收敛）——瓶颈不是样本量而是**任务设计**：

1. 「选装页 vs 非选装页」分类价值有限——plan 的像素判据（卡片灰 ≥0.35）已经完美解决场景识别；
2. 用户先验（§笔记十七）：**选装页有倒计时，不选会被随机穿⇒失败**——选装是唯一真决策点，胜负由「选得是否匹配主题」决定；
3. 现有 tap 标签 100% 是 pick_mid（plan 固定行为）⇒ 行为克隆只能学「模仿 plan」，学不到「匹配主题」。

**转向：三分支探索采集**（为离线偏好学习攒数据）：
- 新增变体档案 `profiles/yoyastar_l.json` / `yoyastar_r.json`（把 plan 全部 8 处 `PRESS name=pick_mid` 替换为 pick_left/pick_right，buttons 定义不动；`go build` + 三档案 Load 校验 PASS）；
- `plan_round.py` 按 tag 序号 %3 轮换档案（s12→mid、s13→left、s14→right…），trajectory.jsonl 的 nx/ny 随日志实际按钮名自动跟随（`extract_picks` 既有逻辑）；
- 代价：故意点不匹配卡拉低胜率——跑批目的是攒数据不冲胜率，可接受；
- 12 轮探索（s13~s24，三分支各 4 局）跑完后：按「WIN 局动作加权 / FAIL 局降权」做偏好训练，模型才可能学出「看主题选卡」。

**v4 偏好加权训练（2026-09-16 晚，s31~s42 采集后全量重训）**：

- 探索采集落地 12 局（s31~s42，left/mid/right 各 4，判定全部自洽）：WIN 4 / FAIL 8（故意点错卡的预期成本）；trainset 全量 27 局 195 样本（tap 65 / none 130，行内带局级 label）。
- `trainer/train.py` 新增 `--preference-weights "WIN=1.0,FAIL=0.3"`：逐样本权重 = 类权重 × 局级偏好权重，cls/coord 双损失按权重和归一；**不传参数时数值路径与旧版完全等价**（向后兼容，其他游戏训练不受影响）。
- **结果（如实）**：val_acc=66.67% **= 多数类基线**，分类头仍塌缩到 none；坐标头继续收敛（选装帧推理 (0.454,0.788) vs 真值 (0.5,0.782)，误差 ~0.047）。Go 侧 stucheck 加载+推理全通。
- **结论强化**：偏好加权改变了损失分布但改变不了**输入信息量**——64×48 灰度图既看不清主题（无法学「匹配」），也让选装页与 PK 演出页难以区分。分类头的出路只剩两条：彩色输入（改网络第一层通道）或干脆**砍掉分类头**（场景识别交给 plan 的像素判据，学生只做坐标回归）。已按「不把生成结果说成测量结果」原则记录，v4 链路验证版，非能力交付。

**v5~v9：砍分类头 + 彩色输入 ——「按建议执行」完整实录（2026-09-16 晚第二轮）**：

两条线（减法验证 + 信息量验证）依次落地，全程 195 样本、27 局（s01~s42）：

| 版本 | 配置 | 分类头 | 坐标误差 | 备注 |
|---|---|---|---|---|
| v4 | 灰度 双头 | 塌缩 66.67%=基线 | ~0.047 | 偏好加权不救塌缩 |
| v5 | 灰度 coord-only | 未训练 | **0.040** | 分类损失未干扰坐标学习（隔离后精度相当） |
| v6 | **RGB 双头** | **82.05% 首破塌缩**（召回 tap 0.769 / none 0.846） | — | 但训练侧 BICUBIC / 推理侧 NEAREST 错配 |
| v7 | RGB coord-only | 未训练 | **0.0304** | 彩色 + coord-only 叠加增益 |
| **v8** | **RGB+NEAREST 双头** | **82.05%（末轮同值更稳）** | — | Go/Python parity：6/6 class 一致、坐标 ≤0.004 |
| **v9** | **RGB+NEAREST coord-only** | 未训练 | **0.0270** | 当前坐标最优 + 推理对齐 |

- **决定性变量 = 彩色输入**：三类证据——①分类头从「恒猜多数类」变为两类召回非零（tap 0.769 / none 0.846）；②坐标误差灰度 0.040 → 彩色 0.027（−33%）；③真机帧上首次出现正确的 `tap` 判定（v4 时代选装帧全部判 none）。
- **训练/推理预处理错配是隐藏的第二个坑**（v6 溯源发现）：PIL `resize()` 省略 resample 时对 RGB/L 默认 **BICUBIC**，而 Go 侧一直用**最近邻**——边界帧 logits 会翻转（同帧 BICUBIC 判 none 4.99/4.87 vs NEAREST 判 tap 5.24/5.49）。修复：`center_crop_resize` 显式 `Image.NEAREST`，与 Go `preprocess` 逐像素对齐（实测 Go vs Python NEAREST 坐标偏差 ≤0.002，仅剩两边 JPEG 解码器差异）。**旧模型（v1~v7）全部是错配产物，v8 起才严格对齐。**
- **工程侧改动**：`train.py` 新增 `--preference-weights` / `--coord-only` / `--rgb` 三参数（全部向后兼容，不传即旧行为）+ `import_weights_json` 按 conv1_w 长度自适应通道 + `center_crop_resize` 显式 NEAREST；`internal/student` 支持 3 通道（inC 由 conv1_w 长度推导、新增 `DecideImage` 通道自适应入口、`preprocessRGB`、灰度入口对彩色模型显式报错、`InChannels()` 访问器）；stucheck 走 DecideImage；新增彩色回归测试 3 个。
- **下一站**：`cmd/helper` 的 StudentActor 仍走灰度 `Decide` 路径——接入 `DecideImage`（抓帧链路要保留彩色，不能先转灰）后再考虑学生模型上真机跑批。分类头的「主题匹配」能力仍不在当前网络容量内（64×48 连主题要素都看不清），留作后续课题。

### 12.18 选装首点前等 1s：吞点时序二次修复（2026-09-16 晚，用户现场观察驱动）

**背景**：循环补点（§12.16）上线后用户仍观察到「有些局没选上装扮、系统随机穿」。s30~s34 五局复盘证实：

| 局 | 结果 | 未点上位置 |
|---|---|---|
| s30/s31 | WIN | 补点救回（最晚第 3 轮命中） |
| s32 | FAIL | **第 2 关 4 轮全被吞** → 倒计时随机穿 |
| s33 | FAIL | **第 1 关 4 轮全被吞** → 随机穿 |
| s34 | FAIL | 第 1 关拖到第 4 轮（≈7.5s）才命中 |

**规律**：未命中不固定在某关某卡 ⇒ 不是坐标/位置问题；旧补点节奏 t=0/2.5/5/7.5s 中首击必落在「页面刚加载的不可交互窗口」被白白吞掉，4 轮全吞的局全部输（随机穿 → 票数劣势 → FAIL）。

**改动（用户建议「等 1 秒再点」）**：4 份档案（`yoyastar/l/r/dressup_common`）× 4 个选装步 = 16 处：
1. 每个选装步前插 `ACTION WAIT` 缓冲步（`gap_ms=1000`）——首点从 t=0 推迟到 t≈1s；WAIT 无副作用、幂等，步骤数 14→18；
2. 补点加密：`max_repeat 4→5`、`gap_ms 2500→2000`、`timeout 13s→16s`——点击序列 ≈ t=1/3/5/7/9s，5 次机会覆盖倒计时前 9s。

**验证**：`go build` + 两包测试 PASS；档案补丁脚本原子写入（临时文件 + os.replace，避免跑批中 `go run` 编译读到半文件）。跑批分界：s36/s37 仍为旧参数（各局 WIN，补点救回），**s38 起新档案生效**（plan.log 出现新 note=13 处）；s36 起三关均无「5 轮未命中」。

**代价与残余风险**：选装步预算 13s→16s，浅色广告假成立时对广告中心多暴露 1 次点击（已知残留风险，靠每关后紧跟清广告步压制）；缓冲步把总时长拉长约 4s/局。

### 12.19 学生模式真机接入彩色 + 输入高度参数化 + 真机复核修正（2026-09-16）

**背景**：§12.17 收尾时点明「下一站」——`cmd/helper` 的 StudentActor 仍走灰度 `Decide` 路径、抓帧链路先转灰，彩色权重（v8/v9）根本没机会上真机。本轮把学生实时回路完整接上彩色链路，用 v10 权重做了真机验证，并在当日复核中修正了初版误判（见「三」）。

**一、实时回路接入彩色（4 处工程改动）**：

| 文件 | 改动 |
|---|---|
| `internal/agent/agent.go` | Actor 接口放宽：`Decide(img image.Image)`（原 `*image.Gray`）+ 新增 `NeedsColor() bool`；`RuleActor` 内置 `asGray`（已是灰度则零拷贝，否则 `draw.Draw` 转换），`NeedsColor()=false` |
| `cmd/helper/backend.go` | 接口补 `GrabColorFresh()` 声明——pc/adb 两实现早已有该方法，仅接口层缺声明（编译报 `be.GrabColorFresh undefined` 才暴露） |
| `cmd/helper/main.go` | 新增 `grabObs(be, actor, downWidth)` 按观测需求分派：灰度 actor 走原 `be.Grab`；彩色 actor 走 `GrabColorFresh` → `vision.Downscale`（box 平均降到 540 宽）。`meanGray` 参数由 `*image.Gray` 放宽为 `image.Image`（彩色走 4×4 抽样亮度） |
| `cmd/helper/student.go` | `Decide` 改调 `net.DecideImage(img)`（通道自适应主入口，灰度入口对彩色模型会报错）；新增 `NeedsColor() = net.InChannels()==3`；启动日志补打印 `inC` 与「灰度/彩色」标识 |

**二、输入高度参数化（v10 的核心修复）**：

- **根因（v8 时代选装页识别「像瞎猜」的真凶）**：旧网络硬编码 64×48（4:3 中心裁剪），竖屏手游里学生视野仅 y∈[0.33, 0.67]，**看不见选装卡片带**（y≈0.75~0.85）——训练集里的 tap 类很可能学的是广告页/无关浅色区，真机新主题帧自然误判。
- **改动**：权重 `meta.down_h` 携带输入高（`train.py` 新增 `--in-h`，默认 48 向后兼容，竖屏手游用 96）；Go 侧 `Net.inH` 从权重推导（缺省 48，合法区间 16~256 越界报错），前向尺寸链改为逐层由 `n.inH` 推导，预处理两路（灰度 `preprocess` / 彩色 `preprocessRGB`）同步参数化，二者由包级函数改为 `(*Net)` 方法；新增 `InputHeight()` 访问器；stucheck / `parity_v6.py` 同步支持可变 in_h。
- **v10 权重**：RGB + `in_h=96`（2:3 视野，y∈[0.15, 0.85]，完整覆盖卡片带），`--override-class-weights "tap=2.0,none=1.0"` + `--preference-weights "WIN=1.0,FAIL=0.3"` + 80 epoch，val_acc **82.05%**（与 v8 同水平），预测分布 tap:18 / none:21。文件 `models/yoyastar_pick_v10.weights.json`。
