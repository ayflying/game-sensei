# 图标档案方法：为什么需要、怎么建、实测边界

> 起因（2026-09-20）：三批视频学习的产物都是 **OCR 驱动的「文字 → 坐标」图谱**，
> 没有**图标**（无 OCR 文字的界面元素）的视觉特征库。后果是——真机上要找「眠枭庇护所」，
> 试了 5 次点击全部落空，只能盲试坐标。
> 本文记录为此建立的工具链、实测结论（含**负面结论**）与正确流程。

---

## 一、缺口定位

| 学习批次 | 产出 | 是否含图标层 |
|---|---|---|
| S1 录屏 200P | OCR 全量 + 界面聚类 + UI 坐标图谱 | ❌ 只有文字坐标 |
| S1 攻略 6 视频 | 同上 | ❌ |
| S4 攻略 28 视频 | 同上 + VLM 关键帧判读 | ❌ |

**"文字在哪"和"图标在哪"是两种能力**。文字靠 OCR（成熟、可靠），
图标只能靠视觉特征匹配。此前只做了前者，所以每次遇到无文字图标就要从零摸索。

## 二、工具链（本轮建立）

### 2.1 定位工具：`tools/icon_extract.py`

确定性像素算法，**只回答"图标在哪"**，不做语义判断。

判据设计（三层过滤）：
1. **三路颜色系**：高饱和 `S>120,V>110` / 高亮近白 `V>205,S<70` / 深色 `V<75`
2. **形状过滤**：面积、bbox 尺寸、**宽高比 0.35~2.8**（挡掉长条文字）、**填充率 ≥0.35**
3. **边缘密度 ≥0.12**（关键判据）：图标有清晰描边与图案，地形是渐变平缓色块

实测效果（2340×1080 地图截图）：
- 无边缘判据：2609 个连通域 → 183 个候选（地形色块污染严重）
- 加边缘判据：→ **91 个候选**，且蓝簇候选与既有 `tools/find_icons.py`
  的锚点判据（1877,901 / 1989,722）**完全吻合** ⇒ 工具可信

### 2.2 命名工具：`tools/icon_annotate.py`

把候选裁剪图交本地 VLM（qwen3.5:9b @ 127.0.0.1:11435）命名。

## 三、实测结论：VLM 不能做小图标分类（负面结论）

两轮对照实验：

| 方式 | 结果 |
|---|---|
| **孤立图标**放大 3 倍 | 30 个里出现「任务标记」×4、「角色头像」×4，还冒出「减号」「建造按钮」等幻觉 |
| **带上下文**（±130px 周边地图）+ 红框标出目标 | 重复度下降，但**仍不可用**——两个**已由 find_icons 交叉验证为蓝色传送锚点**的候选，被判成「建筑」和「营地」 |

**根因**：9B 级本地模型没有足够的世界知识，把"64×42 像素的模糊图案"
映射到"某游戏的魔力之源传送点"这种具体概念。它只能从先验里挑高频词，于是输出"营地/建筑/NPC"这类**看似合理但无信息量**的标签。

**边界**：
- ✅ VLM 适合 **整屏语义判读**（"这是什么界面""画面里有什么"）
- ❌ VLM 不适合 **小尺寸图标分类**（91 个图块逐个贴标签）
- ⚠️ 整图判读也有代价：2340×1080 全图会让本地后端超时，需先缩放或裁剪

## 四、正确的图标档案建设流程

```
① 确定性定位  tools/icon_extract.py        → 候选清单（坐标可靠）
② 人工确认一次  关键图标通常 <20 类，看一眼即可命名
③ 存模板      确认后的裁剪图存入 icon_atlas/templates/
④ 模板匹配    后续任意截图用多尺度 NCC 匹配定位（不依赖 VLM）
              → 已实现 tools/icon_match.py；--at 出可点坐标、--tap 直接点击（§5.2）
⑤ VLM 只做整屏语义判读，不碰小图标
```

**核心原则**：图标库是**一次人工 + 长期复用**的资产；
VLM 命名是歧路（每次都要跑、还不准），模板匹配才是正解（一次确认、永久可靠）。

## 五、关键突破：人工一次确认 → 模板匹配复用（2026-09-20 当天打通）

前四章的排查卡在"庇护所图标长什么样、在哪"。**用户看了一眼候选网格图，指出"第 3 行第 2 个是眠枭"**，
由此闭环。但过程里有一个重要反转，值得完整记下：

| 环节 | 事实 |
|---|---|
| 用户指认的候选 | 网格第 3 行第 2 个 = I021 = **(1564,135)**，42×28 蓝色 |
| 用 I021 当模板搜当前画面 | v11 上 0.817 命中 **(1036,499)** ⇒ 说明两处图案相似但**不是同一个图标** |
| 点 I021 本体 (1564,135) | **画面零变化**（v10/v11 像素逐位相同）⇒ 它不是可点热区 |
| 点 (1036,499) | **弹出「大型眠枭庇护所」面板** ✅ 这才是真图标 |
| 交叉验证 | v05 vs v11 在 (1036,499) 邻域 **mean\|diff\|=0.00**（完全一致）；(1564,135) 邻域 **=85.95**（变了） |
| `icon_extract` 91 个候选里 | **没有 (1036,499)** ⇒ 提取器漏检了目标图标本身（见 §六①） |

**做法修正**：模板必须取自**"确认可点"的样本**（点一下弹对面板才算确认），
不能取自"看起来像"的候选。据此新增 `tools/icon_match.py`：

```bash
# ① 建模板（每个图标只做一次，需人确认一次）
python tools/icon_match.py --make "眠枭庇护所" --from-shot v11.png --bbox 1015,485,1056,512
# ② 复用（任意截图、任意时刻）
python tools/icon_match.py --find "眠枭庇护所" --shot 任意截图.png
python tools/icon_match.py --list          # 看图标库现有条目
```

**实测（"图标库能用"的硬证据）**：

| 验证项 | 结果 |
|---|---|
| v11 自匹配 | **1.000** @ (1036,499) |
| 回搜 v05（同一视口的另一时刻帧） | **1.000** @ (1036,499) |
| 点匹配坐标 | 弹出「大型眠枭庇护所」面板 —— **端到端打通** |
| 用未确认样本（I021）当模板 | v11 上仅 0.817，且指向**另一个图标** ⇒ 印证"必须用确认样本" |

多尺度 0.85–1.15 + 重叠抑制，同尺寸图标实测无需调参。
图标库落盘 `.workbuddy/nrc/icon_atlas/library/`，`library.json` 记录尺寸/来源/备注。

**避坑（已写进工具注释）**：`cv2.imwrite` 走 C++ 文件 API，**中文文件名会静默写成 GBK 乱码名**
（实测「眠枭庇护所.png」→「鐪犳灜搴囨姢鎵€.png」），必须 `cv2.imencode` + `np.ndarray.tofile`。

### 5.1 补齐轮：跨视口复验 + 新增「星光对决」（2026-09-20 当日续做）

用户要求"把图标库补齐"。本轮把已有两条**跨视口**复验一遍，并新增一条：

| 模板 | 来源 | 跨视口复验 | 结论 |
|---|---|---|---|
| 眠枭庇护所 | v11.png 中心 (1035,498) | 旧视口 k0 **0.951** @(861,299)；新视口 q2 **0.986** @(1577,433) | **地图上所有蓝色盾牌传送点共用此图形**——两处点击分别弹出「小型/大型眠枭庇护所」面板 |
| 家园 | hm1.png 中心 (2154,1028) | q2 **0.948** @(2155,1028) | 固定 UI，**不随视口移动**（视口从奥贝斯坦湖换到风息山口，坐标不变） |
| 星光对决（**新增**） | g2.png bbox 1648,434,1727,510 | g2 与 m2 均 **1.000** @(1688,472) | 地图上的 S4 活动入口（蓝色徽章形），点击弹「星光对决」面板（倒计时 810 小时 / 欢呼声 0-15 / 可能获得 x5） |

**⇒「蓝色传送锚点」这条待办可以销掉**：它与「眠枭庇护所」是**同一个图形**
（地图上的「蓝底 + 白城堡」盾牌），只有面板标题才区分「XX庇护所 / XX的魔力之源」。
一次确认的样本即可覆盖整类传送点，**不必按名字各建一条**。

**⇒ 阈值分档（补入 `--min-score` 默认值与注释）**：真命中 **≥0.95**（本轮 0.951/0.948/0.986/1.000），
误报集中在 **0.55~0.65**（风息山口帧用 0.55 搜出 3 处，只有 0.986 那处点得出面板，
另两处点开的是「标记」面板 = 空白地图）。默认阈值已由 0.70 上调到 **0.85**。

**⚠️ 本轮踩到的新坑：面板「传送」按钮与地图「标记」按钮几乎同坐标。**
点开眠枭面板后，按"关面板"的惯例点 (1868,983)，而眠枭面板底部的**「传送」按钮在 (1869,1006)**
——两者只差 23px，结果**把角色传送走了**（画面出现加载文案与场景切换），
后续两轮点击全部打在错误界面上，白费三轮。⇒ 关面板前必须先 OCR 确认当前是哪个面板。

### 5.2 点击链路打通：`--at` / `--tap`（2026-09-20 傍晚）

模板匹配此前只能"报坐标"，还得人工把坐标拷给 `drv.py`。本轮把这一步也做掉，
让 `icon_match` 一条命令完成 **认出图标 → 点它**：

```bash
# 机器可读：只回一行「名称 分数 x y」；无命中回 MISS 且返回码 1
python tools/icon_match.py --find 眠枭庇护所 --shot tapD.png --at
#   → 眠枭庇护所 0.986 1577 433        (rc=0)
#   → MISS 阈值 0.85  w1.png           (rc=1)

# 直接点击：命中最佳位置后调 .workbuddy/nrc/drv.py tapx
python tools/icon_match.py --find 眠枭庇护所 --shot tapD.png --tap
#   → 眠枭庇护所 0.986 1577 433        + stderr: tap#1 (1577,433) / tap#2 (1577,433)
```

`--at` 走"机器可读模式"（不打人读标题、只回一行），便于 shell `read 名 分 x y` 取坐标。
`--find-all --at` 回**全局最高分**那一处；要多处清单用不带 `--at` 的普通输出。

**`--tap` 默认点两次** —— 本地图"首点被吞"极常见（开地图按钮、家园按钮都要点两次；
本轮又复现一次：右上 ✕ (2169,49) **首点只关了面板、次点才关地图**）。
`--tap-times` / `--tap-wait` 可调。

**端到端实测（真机 MIX3，风息山口视口，本轮）**：

| 步骤 | 结果 |
|---|---|
| `--find 眠枭庇护所 --shot tapD.png --tap` | `眠枭庇护所 0.986 1577 433`，rc=0，自动点 (1577,433) ×2 |
| 抓帧验证（tapD→tapE） | 帧差 **23.52**；OCR 读出「大型眠枭庇护所」+「在庇护所中放入果实，会吸引新的精灵来此处栖息」+「传送」(1869,1006) |

⇒ **一条命令 = 完整闭环**（认图标 → 点击 → 面板弹出），不再需要人工搬坐标。
`--at` 的 `MISS` + 返回码 1 让外层脚本可自动走"图标不在屏"分支（呼应 §六② 的显隐问题）。

## 六、待改进与边界（累计七条）

**① `icon_extract` 会漏检"贴在大色块上的图标"** —— 眠枭图标 (1036,499) 不在 91 个候选里。
推测原因：它与周围蓝色元素（水域/光效）连通，连通域 bbox 超出 `--max-side` 被整体滤掉。
⇒ 需从"绝对颜色切分"改为"**局部对比度切分**"（图标与紧邻背景有稳定色差），才能切出这类图标。

**② 地图图标是动态显隐的（重要，影响定位可靠性）** —— 同一视口下：
v05 有 **18** 个蓝色图标簇，几秒后的 v11 只剩 **8** 个；其中 (1564,135) 那片在数秒内就变了
（邻域 mean\|diff\|=85.95）。而地名坐标两图完全一致（皇家办事处 (1281,510)、隐秘滩涂 (1096,672)、
月牙镇 (795,1024)…）⇒ **不是视口平移，是图标本身会显隐**。
⇒ 结论：**用图标库定位时，必须先确认图标当前在屏再点击**，不能假设图标恒定存在。
⇒ 顺带修正旧认知：把地图上的"蓝簇"一律当固定图标是错的（v05 那 18 个里含临时元素）。

**③ VLM 的定位再确认** —— 只做整屏语义判读；小图标判读不可用（§三）。
本轮又验证一次：2B 模型把一个实心圆角矩形按钮描述成"右上角有一个白色的 × 关闭按钮"，纯幻觉，
照它点的两个坐标全部无效。

**④ 无退出入口的界面（已复现两次）** —— 果实选择界面：返回键被吞、面板上无 × 按钮
（右上角那个近白方块是实心圆角矩形而非 ×，实测点击无效）。与地图面板同类，正解仍是**重启游戏**。
这类界面应连同"进入路径"记入坐标速查，避免下次重复试错。

**⑤ 地图「标记」面板没有干净退出项（本轮第三次复现）** —— 点空白地图会进入
「标记（点击修改名称）」编辑态，底部只有「标记」按钮：**返回键被吞、没有 ×**；
点「标记」按钮虽能退出，但**每退一次地图上就多一个标记**（常规标记数 4→5→6，本轮留下 2 个垃圾标记）。
⇒ 找图标时**不要靠"点空白试探"**，先用 `icon_match` 定位、再点确认。

**⑥ 纯色判据（`find_icons.is_anchor`）在大地图上会大量命中水体** —— 奥贝斯坦湖与风息山口视口
各命中 9~13 个"蓝簇"，但逐个点过去，**可交互的只有模板匹配 ≥0.95 的那一个**：
其余点下去要么 Δ=0.00（完全无响应，是湖面高光），要么直接开「标记」面板（是空地）。
⇒ **地图图标定位首选 `icon_match`**，`find_icons` 只当"候选提示"用，
且每个候选都必须以"点一下看弹出什么"收口。

**⑦ `drv.py judge` 会把「地图界面」判成 `WORLD`** —— 本轮实测：明明停在地图界面
（OCR 有「地图 / 卡洛西亚大陆 / 精灵踪迹：11/15」+ 右下角「家园」），`judge_path` 却报
`WORLD minimap=43831`。根因是该判据只看"右上小地图亮像素 >15000"，而地图界面右上同样是大片亮区。
⇒ **判界面态不能只信 `judge`**：地图态必须用语义特征收口（OCR 是否出现「卡洛西亚大陆 / 精灵踪迹」）。
反面同样成立：已开地图时 `shot` 打印 `WORLD`，很容易被误判成"我在野外"。
