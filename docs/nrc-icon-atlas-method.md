# 图标档案方法：为什么需要、怎么建、实测边界

> 起因（2026-09-20）：三批视频学习的产物都是 **OCR 驱动的「文字 → 坐标」图谱**，
> 没有**图标**（无 OCR 文字的界面元素）的视觉特征库。后果是——真机上要找「眠枭庇护所」，
> 试了 5 次点击全部落空，只能盲试坐标。
> 本文记录为此建立的工具链、实测结论（含**负面结论**）与正确流程。

---

## 一、缺口定位

| 学习批次 | 产出 | 是否含图标层 |
|---|---|---|
| S1 录屏 200P | OCR 全量 + 界面聚类 + UI 坐标图谱 | ❌ 只有文字坐标 |
| S1 攻略 6 视频 | 同上 | ❌ |
| S4 攻略 28 视频 | 同上 + VLM 关键帧判读 | ❌ |

**"文字在哪"和"图标在哪"是两种能力**。文字靠 OCR（成熟、可靠），
图标只能靠视觉特征匹配。此前只做了前者，所以每次遇到无文字图标就要从零摸索。

## 二、工具链（本轮建立）

### 2.1 定位工具：`tools/icon_extract.py`

确定性像素算法，**只回答"图标在哪"**，不做语义判断。

判据设计（四路提取 + 三层过滤）：
1. **三路颜色系**：高饱和 `S>120,V>110` / 高亮近白 `V>205,S<70` / 深色 `V<75`
2. **一路局部对比度**（§5.3 新增）：`|灰度 − BoxBlur(15)| > max(18, p90×1.5)` —— 专门切出
   "与周围底色同色、被并进同一个颜色连通域"的图标（可用 `--no-texture` 关闭）
3. **形状过滤**：面积、bbox 尺寸、**宽高比 0.35~2.8**（挡掉长条文字）、**填充率 ≥0.35**
   （texture 路像素天然稀疏，门槛另设 ≥0.20）
4. **边缘密度 ≥0.10**（关键判据）：图标有清晰描边与图案，地形是渐变平缓色块

实测效果（2340×1080 地图截图）：
- 无边缘判据：2609 个连通域 → 183 个候选（地形色块污染严重）
- 加边缘判据：→ **91 个候选**（v05 帧），且蓝簇候选与既有 `tools/find_icons.py`
  的锚点判据（1877,901 / 1989,722）**完全吻合** ⇒ 工具可信
- 再加局部对比度路（k0 帧）：129 → **180 个候选**，且"被同色大块吞并的大图标"
  （星光对决 79×76）由**全漏**变为稳定切出 ⇒ 量化对比见 §5.3

### 2.2 命名工具：`tools/icon_annotate.py`

把候选裁剪图交本地 VLM（qwen3.5:9b @ 127.0.0.1:11435）命名。
**实测不可用**（§三），保留作负面结论的证据。

### 2.3 复用与收尾工具

| 工具 | 作用 | 何时用 |
|---|---|---|
| `tools/icon_match.py` | 人工确认一次 → 模板 → 任意截图确定性定位（`--rename`/`--drop` 管库） | 定位已入库图标（`--at` 出坐标 / `--tap` 直接点） |
| `tools/icon_regression.py` | 提取算法的**回归判据**（覆盖率 + 尺寸达标率 → 退出码） | 改动 `icon_extract` 后必跑 |
| `tools/icon_intake.py` | **批量学习收尾**：关键帧目录 → 待确认清单 + 总览图 → 批量入库 | 每批学习结束后（§5.4） |
| `tools/icon_probe_click.py` | **点击探针**：逐候选"点一下看反应" → 四类判定 → 自动命名入库 | 想知道"这个图标是什么"时（**首选**，§5.5） |
| `tools/icon_crossframe.py` | **跨帧巡检**：多帧比对，分清「固定 UI」与「随视口移动」 | **每次扩库后**（决定用坐标还是模板，§5.6） |
| `tools/nrc_soak.py` | **真机跑批**：N 轮完整闭环压测（默认 4 个固定 UI 目标轮换），出成功率/复位率/各阶段耗时/分目标明细 | 想确认"稳不稳、顺不顺"时（§5.8、§5.9） |

## 三、实测结论：VLM 不能做小图标分类（负面结论）

两轮对照实验：

| 方式 | 结果 |
|---|---|
| **孤立图标**放大 3 倍 | 30 个里出现「任务标记」×4、「角色头像」×4，还冒出「减号」「建造按钮」等幻觉 |
| **带上下文**（±130px 周边地图）+ 红框标出目标 | 重复度下降，但**仍不可用**——两个**已由 find_icons 交叉验证为蓝色传送锚点**的候选，被判成「建筑」和「营地」 |

**根因**：9B 级本地模型没有足够的世界知识，把"64×42 像素的模糊图案"
映射到"某游戏的魔力之源传送点"这种具体概念。它只能从先验里挑高频词，于是输出"营地/建筑/NPC"这类**看似合理但无信息量**的标签。

**边界**：
- ✅ VLM 适合 **整屏语义判读**（"这是什么界面""画面里有什么"）
- ❌ VLM 不适合 **小尺寸图标分类**（91 个图块逐个贴标签）
- ⚠️ 整图判读也有代价：2340×1080 全图会让本地后端超时，需先缩放或裁剪

## 四、正确的图标档案建设流程

```
① 确定性定位  tools/icon_extract.py        → 候选清单（坐标可靠）
② 人工确认一次  关键图标通常 <20 类，看一眼即可命名
③ 存模板      确认后的裁剪图存入 icon_atlas/library/
④ 模板匹配    后续任意截图用多尺度 NCC 匹配定位（不依赖 VLM）
              → 已实现 tools/icon_match.py；--at 出可点坐标、--tap 直接点击（§5.2）
⑤ VLM 只做整屏语义判读，不碰小图标
⑥ 批量学习收尾  每学完一批素材，用 tools/icon_intake.py 把该批关键帧里的图标
              一次收进库（跨帧聚合 + 已入库自动跳过 + 人工只指认新增的）→ §5.4
```

**核心原则**：图标库是**一次人工 + 长期复用**的资产；
VLM 命名是歧路（每次都要跑、还不准），模板匹配才是正解（一次确认、永久可靠）。

### 扩库收尾五步（2026-09-20 起固定动作，每加一批图标跑一遍）

```bash
# ① 先看候选、不点击（自动跳过已入库，重复跑只列新图标）
python tools/icon_probe_click.py --fresh --top 20 --dry-run
# ② 真机点击探测 + 自动命名入库
python tools/icon_probe_click.py --fresh --top 20 --apply
# ③ 人工扫一遍名称（OCR 必错几条）→ 改名 / 剔除误判
python tools/icon_match.py --list
python tools/icon_match.py --rename "旧名=新名" --note "依据"
python tools/icon_match.py --drop "误判条目"
# ④ 跨帧定性（决定后续用坐标还是模板），--annotate 写回库
python tools/icon_crossframe.py --shots v11.png,hm1.png,probe_base.png --annotate
# ⑤ 改动过 icon_extract 才需要；只加图标可跳
python tools/icon_regression.py
```

⚠️ 第③步**不能省**：实测 9 条新名里错了 4 条（1 条机制性误识 + 2 条引号噪声 + **1 条整条误判**）。
⚠️ 第④步**不能省**：点击探针只判"是不是图标"，**不判"会不会动"**——
固定 UI 写死坐标就够，随视口移动的必须模板匹配，混用会白跑（§5.6）。

## 五、关键突破：人工一次确认 → 模板匹配复用（2026-09-20 当天打通）

前四章的排查卡在"庇护所图标长什么样、在哪"。**用户看了一眼候选网格图，指出"第 3 行第 2 个是眠枭"**，
由此闭环。但过程里有一个重要反转，值得完整记下：

| 环节 | 事实 |
|---|---|
| 用户指认的候选 | 网格第 3 行第 2 个 = I021 = **(1564,135)**，42×28 蓝色 |
| 用 I021 当模板搜当前画面 | v11 上 0.817 命中 **(1036,499)** ⇒ 说明两处图案相似但**不是同一个图标** |
| 点 I021 本体 (1564,135) | **画面零变化**（v10/v11 像素逐位相同）⇒ 它不是可点热区 |
| 点 (1036,499) | **弹出「大型眠枭庇护所」面板** ✅ 这才是真图标 |
| 交叉验证 | v05 vs v11 在 (1036,499) 邻域 **mean\|diff\|=0.00**（完全一致）；(1564,135) 邻域 **=85.95**（变了） |
| `icon_extract` 91 个候选里 | **没有 (1036,499)** ⇒ 提取器漏检了目标图标本身（见 §六①） |

**做法修正**：模板必须取自**"确认可点"的样本**（点一下弹对面板才算确认），
不能取自"看起来像"的候选。据此新增 `tools/icon_match.py`：

```bash
# ① 建模板（每个图标只做一次，需人确认一次）
python tools/icon_match.py --make "眠枭庇护所" --from-shot v11.png --bbox 1015,485,1056,512
# ② 复用（任意截图、任意时刻）
python tools/icon_match.py --find "眠枭庇护所" --shot 任意截图.png
python tools/icon_match.py --list          # 看图标库现有条目
```

**实测（"图标库能用"的硬证据）**：

| 验证项 | 结果 |
|---|---|
| v11 自匹配 | **1.000** @ (1036,499) |
| 回搜 v05（同一视口的另一时刻帧） | **1.000** @ (1036,499) |
| 点匹配坐标 | 弹出「大型眠枭庇护所」面板 —— **端到端打通** |
| 用未确认样本（I021）当模板 | v11 上仅 0.817，且指向**另一个图标** ⇒ 印证"必须用确认样本" |

多尺度 0.85–1.15 + 重叠抑制，同尺寸图标实测无需调参。
图标库落盘 `.workbuddy/nrc/icon_atlas/library/`，`library.json` 记录尺寸/来源/备注。

**避坑（已写进工具注释）**：`cv2.imwrite` 走 C++ 文件 API，**中文文件名会静默写成 GBK 乱码名**
（实测「眠枭庇护所.png」→「鐪犳灜搴囨姢鎵€.png」），必须 `cv2.imencode` + `np.ndarray.tofile`。

### 5.1 补齐轮：跨视口复验 + 新增「星光对决」（2026-09-20 当日续做）

用户要求"把图标库补齐"。本轮把已有两条**跨视口**复验一遍，并新增一条：

| 模板 | 来源 | 跨视口复验 | 结论 |
|---|---|---|---|
| 眠枭庇护所 | v11.png 中心 (1035,498) | 旧视口 k0 **0.951** @(861,299)；新视口 q2 **0.986** @(1577,433) | **地图上所有蓝色盾牌传送点共用此图形**——两处点击分别弹出「小型/大型眠枭庇护所」面板 |
| 家园 | hm1.png 中心 (2154,1028) | q2 **0.948** @(2155,1028) | 固定 UI，**不随视口移动**（视口从奥贝斯坦湖换到风息山口，坐标不变） |
| 星光对决（**新增**） | g2.png bbox 1648,434,1727,510 | g2 与 m2 均 **1.000** @(1688,472) | 地图上的 S4 活动入口（蓝色徽章形），点击弹「星光对决」面板（倒计时 810 小时 / 欢呼声 0-15 / 可能获得 x5） |

**⇒「蓝色传送锚点」这条待办可以销掉**：它与「眠枭庇护所」是**同一个图形**
（地图上的「蓝底 + 白城堡」盾牌），只有面板标题才区分「XX庇护所 / XX的魔力之源」。
一次确认的样本即可覆盖整类传送点，**不必按名字各建一条**。

**⇒ 阈值分档（补入 `--min-score` 默认值与注释）**：真命中 **≥0.95**（本轮 0.951/0.948/0.986/1.000），
误报集中在 **0.55~0.65**（风息山口帧用 0.55 搜出 3 处，只有 0.986 那处点得出面板，
另两处点开的是「标记」面板 = 空白地图）。默认阈值已由 0.70 上调到 **0.85**。

**⚠️ 本轮踩到的新坑：面板「传送」按钮与地图「标记」按钮几乎同坐标。**
点开眠枭面板后，按"关面板"的惯例点 (1868,983)，而眠枭面板底部的**「传送」按钮在 (1869,1006)**
——两者只差 23px，结果**把角色传送走了**（画面出现加载文案与场景切换），
后续两轮点击全部打在错误界面上，白费三轮。⇒ 关面板前必须先 OCR 确认当前是哪个面板。

### 5.2 点击链路打通：`--at` / `--tap`（2026-09-20 傍晚）

模板匹配此前只能"报坐标"，还得人工把坐标拷给 `drv.py`。本轮把这一步也做掉，
让 `icon_match` 一条命令完成 **认出图标 → 点它**：

```bash
# 机器可读：只回一行「名称 分数 x y」；无命中回 MISS 且返回码 1
python tools/icon_match.py --find 眠枭庇护所 --shot tapD.png --at
#   → 眠枭庇护所 0.986 1577 433        (rc=0)
#   → MISS 阈值 0.85  w1.png           (rc=1)

# 直接点击：命中最佳位置后调 .workbuddy/nrc/drv.py tapx
python tools/icon_match.py --find 眠枭庇护所 --shot tapD.png --tap
#   → 眠枭庇护所 0.986 1577 433        + stderr: tap#1 (1577,433) / tap#2 (1577,433)
```

`--at` 走"机器可读模式"（不打人读标题、只回一行），便于 shell `read 名 分 x y` 取坐标。
`--find-all --at` 回**全局最高分**那一处；要多处清单用不带 `--at` 的普通输出。

**`--tap` 默认点两次** —— 本地图"首点被吞"极常见（开地图按钮、家园按钮都要点两次；
本轮又复现一次：右上 ✕ (2169,49) **首点只关了面板、次点才关地图**）。
`--tap-times` / `--tap-wait` 可调。

**端到端实测（真机 MIX3，风息山口视口，本轮）**：

| 步骤 | 结果 |
|---|---|
| `--find 眠枭庇护所 --shot tapD.png --tap` | `眠枭庇护所 0.986 1577 433`，rc=0，自动点 (1577,433) ×2 |
| 抓帧验证（tapD→tapE） | 帧差 **23.52**；OCR 读出「大型眠枭庇护所」+「在庇护所中放入果实，会吸引新的精灵来此处栖息」+「传送」(1869,1006) |

⇒ **一条命令 = 完整闭环**（认图标 → 点击 → 面板弹出），不再需要人工搬坐标。
`--at` 的 `MISS` + 返回码 1 让外层脚本可自动走"图标不在屏"分支（呼应 §六② 的显隐问题）。

### 5.3 局部对比度路：修掉「贴大色块图标漏检」（2026-09-20 晚）

**先纠正一个错误结论**：§六① 曾断言「眠枭不在 91 个候选里」。本轮用 `k0.png` 复测，
**眠枭其实一直在候选里**（I022，52×28，真值 41×27）——当时看漏了。
所以"漏检"的真实形态不是"整个找不到"，而是下面两种：

| 失败形态 | 实例 | 现象 | 原因 |
|---|---|---|---|
| **被同色大块吞并** | 星光对决 79×76 | 2/2 帧**完全无候选** | 蓝色徽章与同色地图底属同一颜色连通域，整块超 `--max-px/--max-side` 被丢 |
| **碎片化** | 家园 55×28 | 只切出 16×14 | 按钮由多块色组成，颜色 mask 只抓到一小块 |

**对策：新增第四路「局部对比度」**（`texture`）——图标内部必然有纹理、周围底色平滑，
`|灰度 − 局部均值|` 能把"贴在大色块上的图标"干净切出来：

```bash
python tools/icon_extract.py shot.png --out dir/                  # texture 路默认开启
python tools/icon_extract.py shot.png --out dir/ --no-texture      # 关闭，复现旧行为
```

两处配套修正（都是实测踩出来的）：

- **texture 路 bbox 偏松**（mask 稀疏，外围零散纹理点撑大 bbox：眠枭 64×58 vs 真值 41×27）
  ⇒ 新增 `refine_bbox()`：按命中像素的 **5~95 分位**收缩到主体（64×58 → 51×51）；
  对实心块（星光对决）几乎不收缩，两类图标都安全
- **去重必须「颜色路优先」**：原按面积降序，texture 的松 bbox 会把颜色路的精确 bbox 挤掉
  （实测 q2/tapD 的眠枭被 51×51 顶掉 52×28）⇒ 排序键改为 `(是否 texture, -面积)`

**量化前后对比**（同一批 5 帧、10 个已知图标点，用新增的回归判据
`tools/icon_regression.py` 自动核对；真值见 `.workbuddy/nrc/icon_atlas/regression.json`）：

| 指标 | 改前 | 改后 |
|---|---|---|
| 覆盖（有候选盖住真值中心） | 8/10 | **10/10** |
| 尺寸达标（bbox/真值 在 0.7~1.6） | 5/10 | **7/10** |
| 眠枭（5 帧） | 52×28 ✓ | 52×28 ✓（未被 texture 顶掉） |
| 星光对决（2 帧） | **全漏** | 59×61 ✓ |
| 家园（3 帧） | 16×14 ✗ | 16×14 ✗（固定 UI，见下） |

**家园为什么没修好、也不必修**：它是**固定 UI**（不随视口移动），定位靠坐标即可
（热区 (2151,1029)，模板早已建好并跨视口验证 0.948）。自动提取给的 16×14 虽小，
但中心 (2161,1028) 与真值中心 (2154,1028) **只差 7px**——人工看网格图一眼就能认出并裁准。
⇒ 自动提取的验收标准是「**位置指对了没有**」，不是「bbox 精不精」。

**端到端验证（自动候选直接建模板）**：取 k0 上自动切出的星光对决候选
（bbox 1641,447,1699,507 = 59×61）建模板后回搜——`g2` **1.000**、
异视口 `q2` **0.995 @(931,996)**（星光对决在风息山口视口确实可见）。
⇒ **自动提取的 bbox 质量已足够直接建可用模板**，人工只需完成"确认是哪个图标"这一步。

单帧提取耗时约 **1.7s**（2340×1080，scale=2），候选数 129 → 180（+40%，人工看网格图仍可承受）。

**顺带补上"能捕获败局"的判据**：`tools/icon_regression.py` —— 读真值清单
（帧 + 图标名 + 真值中心 + 真值尺寸），对每帧跑 `icon_extract`，报**覆盖率**与**尺寸达标率**，
并按门槛回退出码：

```bash
python tools/icon_regression.py                # → 覆盖 10/10、尺寸 7/10，rc=0（通过）
```

### 5.4 批量学习收尾接入器：`tools/icon_intake.py`（2026-09-20 深夜）

**动机**：§一 的缺口（"批量学习只产出文字图谱"）不是一次补完就完了——
每学完一批新素材都会重新留下同一块缺口。所以「建图标档案」必须成为**固定收尾步骤**，
而不是"哪天想起来再补"。

**流水线**（一条命令，输入=学习产出的关键帧目录）：

```bash

python tools/icon_intake.py --frames-dir <关键帧目录> --pick k0,g2,q2,tapD,v11 \
    --out .workbuddy/nrc/icon_atlas/intake/<批次>
# ② 回填后批量入库（自动跑一次回归，确认没搞坏旧模板）
python tools/icon_intake.py --apply <批次>/checklist.md --regress
```

| 步 | 做什么 | 关键设计 |
|---|---|---|
| ① | 逐帧调 `icon_extract` 取候选 | 复用 CLI，不复制提取逻辑（避免两份逻辑漂移） |
| ② | **跨帧聚合** | **内容签名**（灰度缩略图零均值归一化 + 相关系数 ≥0.90）——不能用坐标，视口会平移 |
| ③ | **标注已入库** | 用库内模板回搜每帧，命中的候选标 `known`，人工确认时自动跳过 ⇒ **只问一次** |
| ④ | 出三件套 | `candidates.json`（数据）+ `grid.png`（总览图）+ `checklist.md`（待回填） |
| ⑤ | `--apply` 批量建模板 | 从清单回填的名称直接建模板 + 回归校验 |

**实测（5 帧 / 3 个视口 / 950 个原始候选）**：

```
950 候选 → 尺寸门槛滤掉 450 → 500 候选 → 216 组 → 列出 50 组
已入库自动识别：星光对决 1.000、眠枭庇护所 1.000、家园 0.989（3 个图标，无需人工处理）
```

**闭环验证（关键）**：`--apply` 入库 2 个临时模板 → **重跑 intake，这两个被自动识别为
`known`（分数 1.0）并从待确认清单消失** ⇒ "人工只确认一次"成立。
（验证后已把临时模板从库里清掉，正式库仍为 3 条。）

#### 三条反直觉实测结论

**① 极小候选的内容签名没有区分度 ⇒ 跨视口误聚。**
首轮跑出「50 组全是 marker、频次 5、spread 1463」的假高频——根因是 10×10~16×12 这类
极小候选缩到 16×16 后任意两块相关系数都 >0.9，把不同视口里毫不相干的小块串成一组。
⇒ 加尺寸门槛（最长边 ≥18px 且面积 ≥150px²），950 → 500 候选，假高频消失。
**真实可点图标不会只有十几像素。**

**② 「频次高 = 重要」在本场景不成立（重要认知修正）。**
地形元素（石头/树丛）在每个视口都出现，频次虚高；而**真图标会动态显隐**
（§六②：眠枭在 5 帧里只出现 2 帧），频次反而低。
⇒ 清单排序改为**按面积降序**（未入库优先），频次只作参考列。

**③ 类型自动分类**（从频次 + 坐标方差 + 同帧重复度推出，是工具最有价值的一条判据）：

| 类型 | 判据 | 含义 | 处理 |
|---|---|---|---|
| `marker` | 跨帧出现 + **坐标漂移** | 随视口移动的地图图标 | **最需要模板**（排序最前） |
| `ui` | 跨帧出现 + 坐标不动（spread ≤24） | 屏幕常驻 HUD | 用坐标即可，不必建模板 |
| `repeat` | **同帧内就出现多次** | 重复地形图案（树/石/草） | 剥掉，垫底 |
| `single` | 只在单帧出现 | 临时元素/噪声 | 优先级最低 |

**类型分类有个使用前提**：它靠「坐标是否漂移」区分，所以 `--pick` 的帧要**尽量覆盖不同视口/不同界面**。
若给的全是同一视口的多帧（内容相同、坐标一致），会把一切都判成 `ui`
（实测：只给 k0+g2 两帧同视口 → 5 组全是 `ui`；加入 q2/tapD/v11 三个视口后才分出 marker）。

**命名环节仍必须人工**：`grid.png` 是 8 列总览图，人看一眼指认即可
（§三已证 9B 本地 VLM 无法可靠命名小图标）。工具的价值是**把 950 个候选收敛到 50 组 + 一张图**。

### 5.5 点击探针：点一下就知道是什么（2026-09-20 深夜，安酱给的判据）

安酱原话：

> 「大地图上面的图标，点上去就会有提示的，会告诉你是什么东西，
>   点击没反应的，就不是按钮，没有意义」

**这句话把「图标识别」从"看图猜"变成了"点一下看反应"** ——
不需要 VLM（小图标命名已证不可用，§三），不需要人工逐个认，
而且**提示文字本身就是图标名**。工具：`tools/icon_probe_click.py`。

#### 三种反应（实测，MIX3 横屏 2340×1080）

| 反应 | 现象 | 判据 | 例 |
|---|---|---|---|
| `icon` | 弹出带名称的面板/提示 | 非空白态、有新文字 | 炼金釜：「炼金釜 / 旅行的魔法师留下的炼金釜… / 传送」 |
| `blank` | 进入「标记」编辑态 | OCR 含「修改名称」或「常规标记数」 | 点任何空地 |
| `mark` | 弹出**玩家自己放的标记**详情 | 新文字含「N米」或「前往」 | 「前往魔法师之家 / 1125米 / 触碰」 |
| `dead` | 完全无反应 | 帧差 <3 **且** 无新文字 | 水体高光、渐变色块 |

⚠️ **`dead` 必须"帧差小 **且** 无新文字"两个条件同时成立**：
实测点地图上的小图标只弹一个**小名称标签**，帧差仅 3.18~3.36（贴着阈值 3.0），
只看帧差会把这些真图标误杀。

#### 两条硬踩出来的操作坑

**① 关标记编辑态要用右上 ✕，不能用底部「标记」按钮。**
实测：✕ 是**无损退出**（标记数 8→8、退出后帧与退出前逐像素一致 meandiff 0.00）；
点底部「标记」按钮会**保存**该标记 ⇒ 每退一次玩家的地图上就多一个垃圾标记。
（地图侧 ✕ 是分层关闭：面板态关面板、编辑态退编辑、干净地图态才关地图 ⇒ 退出后要确认"还在地图上"。）

**② 点击某些地图元素会让地图自己平移（视口漂移）。**
证据：点 (2150,993) 后的探测帧出现「聆风镇 / 西区工厂 / 隐秘滩涂」，
而基准帧用 `min_conf 0.25` 也**根本没有**这些文字 ⇒ 不是 OCR 漏识，是地图真的动了。
⇒ 视口一变，**后续候选坐标全部失准**。工具做法：用"地图顶部的当前视口地名"当指纹，
一变就复位视口（关地图重开＝回到以角色为中心的默认位置）并重设基准帧。

### 5.6 跨帧巡检：分清「固定 UI」与「随视口移动」（2026-09-20 夜）

**为什么必须分**：库里的模板混了两类，用错方式定位会白跑，而**点击探针分不出来**
（它只判"是不是图标"，不判"会不会动"）：

- **固定 UI**（家园 / 七彩炫舞的小屋 / 皮卡月刊 / 眠枭庇护所(地图UI)）：多帧坐标**逐像素不动**
  ⇒ **写死坐标就够**，不需要每次跑模板匹配；
- **随视口移动**（眠枭庇护所 / 星光对决 / 魔法师之家 / 炼金釜）：3 帧 3 个位置
  ⇒ **必须模板匹配**，写死坐标必错。

```bash
# 至少给 2 帧，且必须覆盖不同视口
python tools/icon_crossframe.py --shots v11.png,hm1.png,probe_base.png
# 把结论写回 library.json 各条 note（覆盖旧的同类标注）+ 留一份矩阵
python tools/icon_crossframe.py --shots v11.png,hm1.png,probe_base.png \
    --annotate --out .workbuddy/nrc/icon_atlas/crossframe.md
```

而**地图界面自带的按钮**（家园、区域进度、资讯、招待所）全都钉在固定坐标。
⇒ 拿不准时先跑巡检，别猜。

「单帧出现」也要换帧才能定性。想全面定性就多给几个不同视口的帧。
（另注：`--fresh` 每跑一次都会重抓基准帧，而**地图视口可能已被上一轮点击平移过**，
所以不同批次的 `probe_base.png` 未必同视口 —— 巡检时别把它当成"固定参照"。）

⚠️ **所选帧必须覆盖不同视口**：同视口多帧会把一切都判成「固定 UI」。
⚠️ 「单帧出现」的 3 条要换帧补验（本轮只用了 3 帧，它们可能只是在这几帧里没显隐出来）。

### 5.7 库维护与重复跑（2026-09-20 夜）

**重复跑只探新图标**（探针默认跳过已入库）：`drop_known()` 用库内模板回搜基准帧，
**匹配点落在候选 bbox 内**（±4px）即跳过。实测本帧 33 个候选中跳过 **13 个已入库**，
只剩 20 个新候选 ⇒ 边际成本趋近 0。
（判据不能用"中心距"：模板匹配点与 extract 的 bbox 中心是两个口径，大图标可差 18px。）
关闭用 `--no-skip-known`。

**库维护命令**（都不必手工改 JSON——手工改名会漏掉模板文件）：

```bash
python tools/icon_match.py --list                          # 看库（含 note）
python tools/icon_match.py --rename "旧名=新名" --note "原因"  # 改名（文件名+清单键一起改，库内顺序不变）
python tools/icon_match.py --drop "名称,名称2"               # 下架（模板文件移入 library/_dropped/，不真删）
```

`--drop` 是**移走不是删除**：模板的可复现性依赖来源帧，而来源帧多是临时截图、会被清理，
误删了没法重建 ⇒ 留 `_dropped/` 可恢复。

**修掉一个排查陷阱：探针的帧名与候选 id 曾错位一位。**
原是 `tag = f"pr{i:03d}"`（i＝**按面积排序后的序号**），而 `id` 来自 `icon_extract`
的分配顺序——两者顺序不同，于是 `pr003_a.png` 里装的是 `I002` 的画面、
`I003` 的画面在 `pr004_a.png`。后果：`probes.json` 的 `shot` 字段把人带偏
（本次排查就因此绕了弯路，一度以为"点击弹出的文字和帧对不上"）。
已改为 `tag = f"pr{c['id']}"`（如 `prI003_a.png`），帧名与 id 直接对上、可追溯。

**紧接着又踩到第二层：光用 id 会让后一批覆盖前一批。**
候选 id **每批都从 I000 重新编号**，而所有批次都往同一个截图目录写
⇒ 实测 `run6` 的 `prI015_a.png` 把 `run5` 的同名文件**盖掉了**（`run5` 那条证据是
「小型眠枭庇护所」面板，被换成 `run6` 的标记编辑态帧，且工具不会报错）。
⇒ 帧名最终定为 **`<批次目录名>_<候选id>`**（如 `run6_I015_a.png`），两层问题一起解决。
⚠️ 教训：**"让命名可追溯"要一次想全** —— 批次内唯一 ≠ 跨批次唯一。

### 5.8 真机跑批：把链路放进闭环里压（2026-09-21）

工具：`tools/nrc_soak.py`。它回答的不是"能不能做一次"，而是
**"连着跑 N 轮稳不稳、每一步要等多久"** —— 这是"玩起来顺不顺"的唯一可复算口径。

一轮做的事（刻意只用**退出路径已实测无损**的动作，不破坏游戏状态）：

```
抓帧 → 全库定位(24 模板) → 点「眠枭庇护所(地图UI)」→ 抓帧验证反应 → 复位回地图
```

**为什么只点这一个图标**：家园会切地图层级、皮卡月刊是资讯入口，它们的退出路径
未实测；拿它们做压测会把"链路不稳"和"状态被搞乱"混成一个数字。

#### 坑①：盲点两次 = 帧差 0.00（toggle 图标）

`--tap` 与早期巡检都默认**点两次**（依据是"本地图首点常被吞"）。这次压测发现：
**这个图标是 toggle —— 点一次开面板、再点一次关面板**，盲点两次时
若两次都生效 ⇒ 开+关 ⇒ **逐像素回到原状（帧差 0.00）**，
看起来和"点击根本没发出去"一模一样。

判定实验（`tap_min3.py`，同一脚本内交替点、每步只点一次）：

| 动作 | 帧差 | 判读 |
|---|---|---|
| 探针：点地图中部 (1200,700) | 23.19 | 链路活着（无热区 ⇒ 地图平移） |
| 目标：点 (188,187) | **18.42** | 面板弹出 ✓ |
| 目标：再点一次 (188,187) | **18.42** | 与起点同画面 ⇒ 面板被关掉 ✓ |

⇒ 两次 diff 完全相同，正是"开了又关"的指纹。
修法：`tap_once_verified()` —— **点一次 → 抓帧 → 只有帧差 < 3.0 才补点一次**。
自适应之后，无论"首点被吞"还是"首点就生效"，都收敛到"面板开着"。

#### 坑②：我把上面这条假象归因错了，还照着改了代码

当时观察到「python 内 `subprocess` 调 `drv.py tapx` 点不动、命令行直接调就有效」，
于是写下结论：**"沙箱会静默拦掉经 ≥2 层 python 的 input 注入"**，
并据此改了三处代码（`icon_match.tap_hit` 换 DEVNULL、`nrc_soak.tap_px` 改直连 adb、
加了一段"必须直连"的注释）。

**这个因果推断是错的。** 真相是那批对照实验里"有效/无效"两次的
**点击次数不同**（一次 vs 两次），撞上了坑①的 toggle 行为。
链路从头到尾都是好的。

⇒ 两条教训（比结论本身更值钱）：
1. **拿"点不动"当结论前，先固定点击次数做对照**。跨次数、跨状态的观察
   不能支撑因果推断 —— 我拿"点两次无效 / 点一次有效"的对比，
   推出了一个关于**调用层级**的结论，两者毫无关系。
2. **诊断脚本要"一个变量"**：这次连续做了 D（直连 adb）、E（DEVNULL）、
   F（不 spawn python）三组实验，每一组都同时变了两个以上的东西，
   所以每组"结果"都无法定位原因。后来把点击次数固定住，一次就通了。

#### 复位状态机（别再盲点两次 ✕）

实测复位路径恒为 **panel → world → map**：
- 面板态点一次 ✕ ⇒ **直接落回大世界**（不是回地图）；
- 大世界点右上导航钮 ⇒ 回地图（单点即可）。

所以连点两次 ✕ 会把地图也关掉、人落在野外，下一轮自然"目标未在屏"。
正确做法是**每点一次就抓帧判态**，回 map 就停（`reset_to_map()`）。

#### 性能：单轮 55.8s → 21.1s（两阶段提速，-62%）

##### 第一阶段：去掉重复劳动（55.8s → 32.5s）

第一次 3 轮实测的单轮耗时构成（50s 级）：

| 阶段 | 耗时 | 备注 |
|---|---|---|
| 复位 | 20.2s | 3 次抓帧 + **3 次整帧 OCR** + 2 次点击 |
| 抓帧 | 11.4s | 6 次 × 1.9s |
| 点击 | 3.6s | 含点击后抓帧 |
| 全库定位 | 3.2s | 24 模板单尺度全图匹配 |
| OCR（base/after） | ~7s | 整帧 OCR 实测 **3.6s/次** |

两条**免 OCR 快路径**（判据不变，只省重复劳动）：

1. **复用定位结果判态**：定位本来就要跑，若结果里同时命中「家园」+
   「眠枭庇护所(地图UI)」两个**固定 UI 锚点** ⇒ 必在地图界面（零额外成本）。
2. **帧差判态**：与一张已确认是地图的参考帧逐像素接近（< 1.0）⇒ 地图界面。
   复位末步"回到 map"正是这种情况。

外加省掉两处重复劳动：复位第 1 步**复用点击后那一帧**（同一画面）；
`--pre-check` 关掉时不再多抓"点击前复核帧"（实测该帧与 base 逐像素一致、状态恒为 map）。

实测：**单轮 55.8s → 32.5s（-42%）**。

##### 第二阶段：把 OCR 与定位从关键路径上挪开（32.5s → 21.1s）

先更正上面一条初判：`-crop` 裁到条带只从 3.6s 降到 2.9s，当时记成
"瓶颈是引擎启动、不是面积"——**只对了一半**。把冷启动与单帧识别拆开量之后是
**冷启动 2.2s + 单帧识别 1.9s**，而单帧识别与像素数只是**弱相关**
（650×80 的条带仍要 0.7s，不是按面积线性缩）。⇒ 缩小区域收益有限，
能做的是三件事，**全都不动判据**：

| 手段 | 做法 | 收益 |
|---|---|---|
| 合并调用 | `ocr -in base -in after` 一次识别两张，而不是两次独立调用 | 省一次冷启动 2.2s |
| **常驻通道** | `ocr -serve`（本轮新增）：全程复用同一进程，冷启动**整批只付一次** | 4 轮省 6.6s |
| **并行** | base 的 OCR 与「全库定位」互不依赖（一个只用文字、一个只用像素），用线程让它们重叠 | ~1.9s/轮 |
| 去掉纯展示的 OCR | 复位成功时不再识别复位帧（`reset_texts` 只用于报告；**失败时才识别**——那才是需要诊断的时刻） | 4.1s |

`ocr -serve` 是 `cmd/ocr` 新增的常驻模式（stdin 收 `{"file":...}`、
stdout 回 `{"file":...,"items":[...]}`，见该命令注释）。它存在的理由正是上面那个拆解：
`internal/ocr` 内部已是常驻 python 子进程，但**命令行每次调用仍是一个新进程**，
跨调用的 2.2s 冷启动省不掉。同一台机器、同一张 2340×1080 帧实测：

```
CLI 两次独立调用   = 8.28s（两次冷启动 + 两次识别）
CLI 一次调用两张   = 6.06s（一次冷启动 + 两次识别）
常驻模式两张       = 约 4.5s（整批只付一次冷启动；单帧纯识别 2.25s）
```

⚠️ 并行的代价是**竞态**：通道是单条 stdin/stdout，两个线程同时发请求会把请求行
与应答行交错（拿到别人的结果）。所以取结果全程持锁，并**在拿到锁后再查一次缓存**
（等锁期间预热线程可能已把同一帧算完）。实测 4 线程并发请求同一/不同帧，结果无串台。

⚠️ 另一条必须防的错：**帧级 OCR 缓存的键要含 mtime 与文件大小**。抓帧会
**覆盖同名文件**（`reset_probeNN` 之类），只按路径做键会把旧结果当成新帧的
—— 这与坑④（自证式判据）是同一类错误：判据指向了"不是它该指向的那份数据"。

实测（4 轮多图标）：**32.5s → 25.2s（常驻）→ 21.1s（并行）**，成功率与复位均 4/4。
两阶段累计 **55.8s → 21.1s（-62%）**。

##### 第三阶段：抓帧兜底（长测暴露的偶发卡顿）

16 轮长测里有一轮单轮 64.8s，其中**一次抓帧花了 39.2s**（同轮其他抓帧都是 2.1s），
而且那一帧的帧差 **60.64**、与同目标其他轮的 30.98 明显不同 ——
**慢帧通常抓在画面过渡态上，内容不可信**，会直接把"点击反应"的判定带偏。

原实现只把耗时记进统计、不做任何兜底（`run()` 默认 180s 超时，39.2s 一路放过）。
加了三件事，**判据不变**：

| 兜底 | 做法 | 理由 |
|---|---|---|
| 子进程超时 | 单次抓帧 60s 上限 | 正常 2.1s，给 30 倍余量，避免无限等 |
| 慢帧重抓 | 单次 > 8s ⇒ 丢弃重抓一次（最多 2 次） | 慢帧 = 过渡态，不可信 |
| **新鲜度校验** | 拿到的帧 mtime 必须晚于本次抓帧开始时间 | 见下 |

**新鲜度校验是离线单测挖出来的真 bug**（不是推测）：`shot()` 在拿不到 `drv.py`
回传路径时会兜底到 `SHOTDIR/<tag>.png` —— 但那是**同名复用**的文件，
抓帧失败时**上一轮的旧帧还躺在那里**，于是"抓帧失败"被静默变成"拿到旧帧"，
本轮点击/复位的判据全建在旧画面上，而且**不报任何错**。
这与坑④（自证式判据）、以及"帧名跨批次覆盖"是**同一个病根**：
判据指向了不是它该指向的那份数据。

三个配套细节：
- 被丢弃的慢帧**挪到 `<tag>.png.slow`** —— 否则它继续占着 `<tag>.png`，
  下一次抓帧失败时仍会被兜底捡回来当结果。`.slow` 不匹配 `*.png`，不会被误当正常帧。
- 记账口径：**最终采用那次**的耗时进 `shot_ms`（汇总统计口径不变），
  被丢弃的进 `shot_retry_ms`，重抓次数进 `shot_tries`；汇总单列一行「抓帧兜底」。
- 离线单测 7 个场景（慢→正常 / 失败→正常 / 都慢 / 无文件全失败 / **旧帧全失败** /
  一次正常 / 慢帧后失败）全部通过 —— 其中 ④b「旧帧全失败」就是上面那个真 bug 的复现用例。
- **真机验证**：16 轮正常跑批里一次慢帧都没出现（最慢 2325ms），兜底没被触发
  ⇒ 用 `--shot-slow-ms 500` **强制**让每帧都判慢帧（每帧重抓一次）跑 2 轮：
  成功率仍 **2/2**、复位 2/2、帧差与正常跑批**完全一致**（17.85 / 30.98），
  汇总报「2 轮出现慢帧 / 丢弃重抓 8 次（最慢被弃 4090ms）」。
  ⇒ **重抓只影响耗时（21s → 67s），不影响判据**。

> 教训：**"兜底"必须有"这份数据是不是本次产生的"这一问。** 只看"文件在不在"，
> 兜底就会把上一轮的残留当成这一轮的结果；而这类错误**不报错、指标还好看**
> （帧差、耗时都正常），只有把"失败路径"单独测一遍才会露出来。

#### 10 轮稳定性基线（2026-09-21，MIX 3）

**起点故意设为"面板态"（异常起点）**，让起点守卫真正被执行一次 ——
只从正常状态连续起跑是测不出守卫的（见坑③）。

#### 坑③：自证式判据 —— 复位抓帧覆盖了基准帧，帧差退化成恒 0

上面那份 10 轮基线是**从地图界面连续起跑**拿到的，所以起点守卫一次都没触发。
补做"异常起点恢复"加严测试（故意把界面留在面板态 / 大世界再跑）时，
立刻暴露一个**我自己刚引入的严重缺陷**：

```
轮1 起点=world → 守卫复位 ['world','map'] → 定位 21 条 ✓ → 点击 ✓ → panel
轮1 复位 → 路径 ['panel','map']（少了 world！）→ reset_diff = 0.0 → 判"复位成功"
轮2 起点=map（错！实际是 world）→ 定位只 7 条 → 目标未在屏 ⇒ 未决
轮3 同上
```

**链条**：起点守卫的复位把"它判为地图的那一帧"赋给本轮的 `base`（当 ref 用），
而**复位过程的抓帧与守卫的抓帧共用同一个文件名** `reset_probeNN`（不带轮次）
⇒ 复位第 2 步抓帧**覆盖了 base 指向的文件** ⇒ `detect_state(复位帧, ref=base)`
实际是**同一个文件自己跟自己比 ⇒ 帧差恒 0** ⇒ 快路径永远判"已回到地图"。

后果不止"复位假成功"：`prev_map` 于是存下了一张**大世界**画面，
下一轮的起点守卫拿它当 ref ⇒ 帧差 1.29 < 3.0 ⇒ **继续误判成 map** ⇒
状态一直错下去，而且**判据自己证明自己**，没有任何环节会报错。

修三处（命名隔离 + 让假信号无法产生 + 收紧阈值）：

1. `reset_to_map(tag_prefix=...)`：帧名改为 **`soak%02d_reset_probeNN`** /
   `soak%02d_start_probeNN`，**起点守卫与本轮复位不再共用文件名**。
2. `diff_two(a, b)`：**同一个文件返回 `None` 而不是 0.0**（"自己跟自己比"不是
   有效测量）。调用方拿到 None 就走真判据（OCR），宁慢不错。
3. ref 快路径阈值从 `SWALLOW_DIFF`(3.0) 收紧到 **`MAP_SAME_DIFF`(1.0)**：
   这里要的是"**同一视口、同一界面**"（真回到地图实测帧差 0.0），
   放宽到 3.0 会把"地图 + 几个标记点"这类近似画面（如标记编辑态）也放进来。

修复后复测（从大世界起点）：**复位路径恢复为真实的 `panel → world → map`**，
3/3 成功、31.2s/轮（轮 1 含起点复位 55.8s）。

⇒ 教训：**判据不能拿"可能被自己覆盖的东西"当基准**。
凡是"用 A 判断 B"的设计，先问一句"**A 会不会在判断过程中被改写**"；
以及任何**帧差/相似度判据都要防"同源比较"** —— 一旦两边指向同一份数据，
它会稳定地给出"完美通过"，而且**看起来比真判据还可靠**（0.0 比 0.9 更"干净"）。

#### 多图标跑批：把目标从 1 个扩到 4 个（2026-09-21）

单图标跑 40 轮 100% 只证明"**这一个**图标点得动"。要回答"能不能更顺地玩"，
必须扩到多目标 —— 但**前提是先逐个实测退出路径**，否则点进去出不来。

实测四个固定 UI 图标的反应与退出（每个都手工走一遍，确认可无损退出）：

| 目标 | 点击反应 | 实测帧差 | 退出方式 |

| 眠枭庇护所(地图UI) | 区域进度面板（风眠省 15/15 + 子区域列表） | 17.9 | 右上 ✕ ×1 |

⇒ 跑批脚本加 `TARGETS` 表，每轮按序轮换一个目标，每个目标自带 `exit` 策略：

- `exit="close"`：点右上 ✕ 一次（面板 / 标记态 / 家园浮层都适用）
- `exit="retap"`：再点同位置一次 —— **皮卡月刊必须用这个**：
  它是 toggle 名字标签，在标签态点 ✕ 会把**地图一起关掉**、落回大世界

**新踩的坑：同一个 toggle 陷阱换了个马甲。**
首版跑批 4 轮，3 个面板类目标全过，**皮卡月刊帧差 0.00 判"无反应"**。
根因不是它点不动，而是补点判据没跟着目标类型走：

```
点一次 → 出名字标签（帧差 2.04）
       → 2.04 < 补点门槛 SWALLOW_DIFF(3.0) ⇒ 判"首点被吞" ⇒ 补点一次
       → 标签被收回 ⇒ 帧差回到 0.00 ⇒ 判"点了没反应"
```

这跟前面"盲点两次 = 开了又关"是**同一个 toggle 陷阱**，只是这次触发它的是
**自适应补点逻辑本身**。修法两条并用：

1. 目标表加 `min_diff`：面板类 8.0、标签类 1.5（门槛必须与被判对象的量级匹配）
2. 标签类加 `verify=False`：**量级天然很小的反应直接关掉补点**，别靠调门槛擦边
   （2.04 vs 1.5 只差 0.5，擦边不稳）

修复后 4 轮：**目标在屏 4/4、成功率 100%、复位 4/4**，皮卡月刊帧差 2.01 → 判 `label` ✓。
