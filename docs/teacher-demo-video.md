## 9.4 Phase 2：老师在线示范（-demo）

Phase 1 的老师只在**旁路**看回放写评语；Phase 2 让它直接**驱动**游戏：
看图 → 出动作 → 执行 → 再看图，同时把 `(学生观测, 老师动作)` 存成示范数据集，
供后续蒸馏学生（模仿学习 / DAgger）。

```bash
# 先空跑验证链路（老师照常决策，但不碰手机）
go run ./cmd/helper -target android -serial <sn> -app com.tencent.nrc \
  -demo -demo-steps 5 -demo-color \
  -demo-hints "虚拟摇杆中心在 x=0.21 y=0.69" \
  -goal "在开放世界里探索，靠近任务追踪里的目标"

# 确认无误后实况采集
go run ./cmd/helper -target android -serial <sn> -app com.tencent.nrc \
  -demo -live -demo-steps 200 -demo-wait 2500ms -demo-color \
  -demo-hints "虚拟摇杆中心在 x=0.21 y=0.69" \
  -goal "..." -demo-out .workbuddy/demos/session-01
```

| 参数 | 说明 |
|---|---|
| `-demo` | 启用示范模式（蕴含 `-teacher`），与实时回路互斥 |
| `-demo-steps` | 步数上限，`0` = 直到 Ctrl+C |
| `-demo-width` | 送审老师的彩色帧降采样宽度（默认 1024） |
| `-demo-wait` | 每步后等游戏响应的时间（默认 2s）。**必须给足**，否则下一帧拍到的还是旧画面 |
| `-demo-out` | 数据目录，空则 `.workbuddy/demos/<时间戳>` |
| `-demo-color` | 额外保存老师看到的彩色帧，便于人工复核 |
| `-demo-hints` | 额外界面先验，`;` 分隔（摇杆中心这类常量，不告诉它就得靠猜）。**只验档案先验不必开 demo**：用 `-print-protocol` 直接打印两态协议（不碰设备、不调模型，见 §9.5） |

**示范数据集格式**（`trainer/` 的输入，字段名已用单测钉住）：

```
<dir>/
├── meta.json         目标/模型/屏幕尺寸/步数/解析成功率/平均耗时
├── trajectory.jsonl  每行一个样本
├── frames/step_0001.png   学生观测（灰度降采样）—— 训练时的网络输入
└── color/step_0001.jpg    老师看到的彩色帧（可选）
```

**关键实现细节：**

- **`think` 开关必须放请求顶层**（`teacher.Options.Think`）。这是本轮最重要的修正：
  早前记录的「本机 Ollama 0.34.0 上 `think=false` 无效」是**错误结论**——
  当时写成了 `options.think`，Ollama 直接忽略。放对位置后，同图同提示词从
  **65s / 正文为空** 变成 **1.3s / 正文正常**，老师才可能跑在在线回路里。
- **学生观测与老师视野是两个通道**：`backend.Grab` 给灰度小图（学生输入），
  `backend.GrabColor` 给全分辨率彩色图（老师判读）。混用一个接口必然有一方将就。
- **送审用 JPEG 不用 PNG**：1024 宽下 130KB vs 1.5MB，编码与传输快一个量级，
  界面判读并不需要无损。降采样在 `internal/vision` 里做**区域平均**，
  2608→1024 这种比例下最近邻会把小图标糊成色块。
- **动作解析容错**（`agent.ParseAction`）：大小写不敏感、全半角标点都认、
  键值顺序任意、允许和中文说明混在一行。但**必须要求坐标成对出现**——
  否则「建议：点击右下角按钮」「摇杆: x=0.21 y=0.69」这类**描述**行
  会被当成动作执行，机器人会莫名去点左上角。

**实测（Redmi 25102RKBEC / Android 16 / qwen3.5:9b 本机 3060）：**

| 指标 | 实测值 |
|---|---|
| 单步耗时（think=false） | **1.8~2.0s**（34 tok 输出） |
| 单步耗时（默认思考） | 60s+，且正文常被思考挤空 |
| 动作格式合规率 | 20/20 步（两轮实况） |
| 端到端 | 截图 → 老师出动作 → ADB 触碰 → 落盘，全链路打通 |

**已暴露的局限（诚实记录，别当成已解决）：**

- ⚠️ **提示词里的具体数字会被照抄**。早期 `ActionProtocol()` 的示例写成
  `ACTION JOYSTICK cx=0.21 cy=0.69 tx=0.81 ty=0.69 dur=1200`，
  模型 8 步输出的动作**与示例逐字节相同** —— 看着像「模型不会决策」，
  实际是「示例被当成了答案」。已改为 `<占位符>` 形式。
  小模型对提示词里的具体数值极其敏感，写示例时务必用不可直接复制的形式。
- ⚠️ **单帧决策没有记忆**，容易在原地重复同一动作。已通过 `Demonstrator.PrevAction`
  把上一步喂回去缓解（并把 `prev_action` 一并存进数据集）。
  **但实测只靠这一条没能打破重复**（8 步动作仍逐字节相同），别把它当成已解决——
  真正的解法是让动作空间本身更适合小模型，见 §9.5 的分层设计。
- ⚠️ **动作质量尚未达标**：模型能正确读出画面地标（8/8 答对「帐篷」），
  但读小号距离数字不可靠，且决策偏向提示词的结构先验，
  离「朝 24 米外的目标走过去」这种目标导向导航还很远。
  这正是需要采集示范数据 + 蒸馏学生的原因，不是靠调提示词能解决的。
- ⚠️ **dry-run 下采不到多样数据**：画面不变 → 老师给同一动作。要有多样性必须 `-live`。

## 9.6 Phase 2.5：教学视频抽帧与判读（`cmd/video`）

§9.4 的在线示范有个绕不开的短板：**老师只能靠自己瞎猜**——实测动作分布熵极低，
几乎永远输出「摇杆推某方向」。更快的路子是**向已经玩明白的人类录像学**：
抽帧 → 去重 → 切成动作段 → 老师逐段判读，产出可读的策略清单。

```bash
# 只抽帧切段（不烧算力，先看关键帧质量）
go run ./cmd/video -in 教学视频.mp4 -out .workbuddy/videos/p01

# 抽帧 + 老师判读（需先 bash tools/serve_ollama.sh）
go run ./cmd/video -in 教学视频.mp4 -out .workbuddy/videos/p01 \
  -annotate -game nrc -goal "学会移动、捕捉精灵、推进新手流程"

# 先试水 8 段，确认提示词效果再跑全量
go run ./cmd/video -in 教学视频.mp4 -annotate -annotate-limit 8 -game nrc
```

**流水线：**

```
mp4 ──ffmpeg 定频抽帧──> 原始帧 ──dHash 去重──> 关键帧 ──距离突变切段──> 动作段
                                                                  └─每段取 3 帧送审──> 老师判读
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `-in` / `-out` | — | 输入视频；输出目录（默认 `.workbuddy/videos/<时间戳>`） |
| `-rate` / `-width` / `-q` | `2` / `640` / `3` | 抽帧频率；输出宽度（0 = 原分辨率）；JPEG 质量 |
| `-dedup` | `10` | 去重阈值（dHash 汉明距离），负数 = 不去重 |
| `-seg` / `-min-seg` | `26` / `8` | 切段阈值；段最小帧数（用于合并碎片段） |
| `-start` / `-end` | — | 只处理片段，如 `-start 10m -end 20m` |
| `-annotate` / `-annotate-limit` | 关 / `0` | 开启判读；最多判读多少段（试水用） |
| `-game` / `-goal` | — | 游戏档案（提供按钮名与界面先验）；游戏目标 |
| `-keep-raw` / `-quiet` | 关 / 关 | 保留未去重的原始帧；不显示 ffmpeg 进度 |

**产出：**

| 文件 | 内容 |
|---|---|
| `meta.json` | 源信息、参数、统计、关键帧清单（含每帧 dHash 与时间戳） |
| `clips.jsonl` | 每段一行：时间范围、代表帧、老师判读结果 |
| `frames/` | 去重后的关键帧，保留完整时序（第二阶段的输入） |
| `report.md` | 人读汇总：局面 / 操作 / 策略 |

**关键设计：**

- **不用 ffmpeg 的场景检测**（`select='gt(scene,X)'`）。录屏压缩后 scene 分数抖动大；
  更重要的是它的语义是「变化开启」而不是「去重」，一段静止的讲解画面会被整段漏掉——
  而操作教学里「停在某界面不动」往往正是重点。主路径改为「定频抽帧 + Go 侧 dHash 去重」：
  结果可复现、可单测，去重率本身还能当质量指标。
- **去重与切段解耦成两个独立阈值**：去重管「保留多少细节」（关键帧是第二阶段蒸馏的输入，
  不能太稀），切段管「划分粒度」（决定送审成本与判读跨度）。
- **用 dHash 而不是画面均值**：均值只看整体亮度，「镜头从左转到右」这种等亮度的剧烈变化
  会被判为没变。dHash 还天然免疫整体亮度漂移（单测：整图提亮 12 级，哈希一位不变）。
- **判读必须关思考**（`think=false`，且必须放请求顶层，见 §9.1 的坑），单段 2.0~3.1s。

**阈值标定（《洛克王国：世界》38 分钟新手录屏实测）：**

游戏画面是持续运动的（草地、云、UI 骨骼动画、镜头跟随），相邻帧 dHash 距离天然就有 8~20，
且**距离分布是连续单峰、没有天然分界点**。这意味着纯视觉手段切不出「玩家在做什么」的
语义边界，只能按「一屏操作的天然时长」来标定粒度：

| 参数 | 初值 | 标定值 | 依据 |
|---|---|---|---|
| `-dedup` | 6 | **10** | 关键帧 2848 → 2292，去重率 38.9% → 50.8% |
| `-seg` | 14 | **26** | 546 段 / 3.5 秒一段 → 120 段 / 18.3 秒一段 |
| `-min-seg` | 4 | **8** | 合并快速运动产生的碎片段 |

3.5 秒一段时老师根本看不出「一件事」，18 秒才够。**默认值只对运动画面成立**，
静止画面为主的演示类视频应显著调低。

**实测（1280x720 AV1 录屏，38.8 分钟）：**

| 项 | 实测值 |
|---|---|
| 抽帧 + 去重 + 切段 | 4658 帧 → 2292 关键帧（去重 50.8%）→ 120 段 |
| 单段判读（`qwen3.5:9b`，think=false） | **2.0~3.1 秒** |
| 全量判读 120 段 | 约 5 分钟，**成功 120/120** |

判读产出的样例（原样摘录，可见确实是从画面读出来的）：

- `00:17:03` 精灵整理阶段：**通过拖拽方式将新获得的精灵放入图鉴网格中进行收纳**
- `00:18:29` 移动技巧：**利用飞行或跳跃技能可以快速跨越障碍和地形，提升探索效率**
- `00:35:04` 过场处理：**在剧情节点前移动到指定位置触发事件，遇到可跳过的过场动画时选择跳过以节省时间**
- 27 段如实标注「本段无操作可学」（过场动画 / 加载 / 纯界面停留）

**⚠️ 诚实边界（别当成已解决）：**

- **视频里没有动作 ground truth**。录像只有画面、没有「手指按在哪」，老师推断出的
  「操作」是**弱标签**——数据里用 `weak_label: true` 标出，报告里也显式标注，
  **绝不能当训练真值**。本阶段真正可靠的产出是**局面**与**策略**。
- 想要真标签只有一条路：录制时打开 Android 开发者选项的「显示点按操作反馈」，
  让触点圆点直接画进画面，那才可以机械提取。
- **视觉段 ≠ 语义段**：dHash 只能给出「画面结构稳定的一段时间」，切不出「玩家在做同一件事」，
  段碎或段长是这类方法的固有问题。
- **hints 会被当成答案**。档案里写了「点任务追踪文字可以自动寻路」，实测 8 段里 6 段的
  「策略」都在照搬这句，连纯过场动画段也不例外。已在提示词里加约束（结论必须来自画面差异，
  并允许模型如实回答「本段无操作可学」），改后同类问题消失，单段耗时还从 3.6s 降到 2.4s。
  **决策侧（`ActionProtocol`）同期对齐**（2026-09-16）：原先两段式防护只在视频判读侧
  （`annotate.go`），老师动作决策侧是裸注入先验；现已补同一套约束（「先验只用来认画面 +
  动作名只能取【可用动作】列表里的」）。
- **已实测确认：视频判读不能当动作训练集**（2026-09-13）。用 `tools/video_to_dataset.py`
  把 1780 段判读按关键词映射成训练格式（映射率 79.7%，1419 有效样本），训了两版学生模型：
  `val_acc` 分别恒定 **63.49% / 52.36%**（恰好等于最多数类占比），40–50 个 epoch 纹丝不动——
  典型的 mode collapse：模型学会「无论看到什么都输出同一类」，毫无决策能力。
  **对照组更有说服力：真机示范只用 60 个样本就有 66.67%，视频 1419 样本反而更低。**
  根因是四条叠加：① 标签是**推断**的弱标签；② 段长 19.4 秒 ≫ 训练样本的单帧粒度；
  ③ 35.5% 的段是复合行为（移动+点击混在一起）；④ `tap` 占 51.9%、`up=256` 而 `down=6`
  严重不均衡。**铁律：标签质量 > 数据数量。**
  正确用法见 `outputs/game-sensei-视频训练可行性实测.md`：视频 → 流程知识（hints）、
  界面状态分类、视觉预训练；**动作克隆一律走真机示范**（`-demo`）。
  另记一个跨模块坑：`trainer/train.py` 的 `map_action()` 认的是**原始轨迹 kind**
  （`move`/`key`/`joy`），不是目标类别（`up`/`press`），按直觉输出会静默丢样本
  （实测 1472 只剩 841）。
- 若要把这版弱标签数据先训成**管线基线**、后续用真机示范 `--init` 加训，见 §11.14。
